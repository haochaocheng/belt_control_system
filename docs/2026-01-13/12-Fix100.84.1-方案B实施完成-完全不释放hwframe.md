## 一、方案C失败原因

###  1.1 错误信息

```
❌ [FIX 100.84] Failed to init hw_frames_ctx: Function not implemented
```

### 1.2 根本原因

**我们设置的配置**（Fix 100.84方案C）：
```c
frames_ctx->sw_format = AV_PIX_FMT_NV12;  // 23（强制NV12）
```

**编码器期望的配置**（rkmppenc.c Line 1270）：
```c
hwfc->sw_format = avctx->pix_fmt;  // I420 (0)，不是NV12！
```

**冲突**：
- 编码器期望使用 `avctx->pix_fmt`（I420），由PJSIP设置
- 我们在方案C中强制设置为NV12
- RKMPP硬件不支持这种配置 → `av_hwframe_ctx_init()` 失败

### 1.3 方案C的其他问题

1. **复杂度过高**：需要在PJSIP级别管理hw_frames_ctx
2. **配置困难**：需要匹配编码器内部期望的格式
3. **维护成本**：修改了多个文件，增加调试难度

## 二、方案B实施

### 2.1 核心原理

**让FFmpeg核心（avcodec_free_context）处理所有资源释放**

**修改前**（Fix 100.83）：
```c
// rkmpp_encode_close()
if (r->hwframe) {
    av_buffer_unref(&r->hwframe);  // ← 第一次释放
}
if (r->hwdevice) {
    av_buffer_unref(&r->hwdevice);  // ← 第一次释放
}
// 然后 avcodec_free_context 再次释放 → 崩溃
```

**修改后**（Fix 100.84.1）：
```c
// rkmpp_encode_close()
fprintf(stderr, "[FIX 100.84.1] Solution B: Skip hwframe/hwdevice unref\n");
// 完全不释放，清除指针
r->hwframe = NULL;
r->hwdevice = NULL;
fprintf(stderr, "[FIX 100.84.1] hwframe/hwdevice pointers cleared\n");
// avcodec_free_context 将正确释放所有资源 ✅
```

## 四、技术原理

### 4.1 资源生命周期

```
rkmpp_encode_init()
  ↓
创建 r->hwdevice (av_hwdevice_ctx_create)
  ↓
创建 r->hwframe (av_hwframe_ctx_alloc)
  ↓
引用计数：hwdevice=1, hwframe=1
  ↓
... 编码过程 ...
  ↓
rkmpp_encode_close()
  ↓
r->hwframe = NULL;  // ← 清除指针，不释放
r->hwdevice = NULL; // ← 清除指针，不释放
引用计数：hwdevice=1, hwframe=1（未改变）
  ↓
avcodec_free_context(&avctx)
  ↓
释放 avctx 内部的所有资源（包括hwframe/hwdevice）
引用计数：hwdevice=0, hwframe=0 → 内存释放 ✅
```

### 4.2 为什么方案B安全？

1. **FFmpeg内部管理**：avctx保存了所有硬件上下文的引用
2. **avcodec_free_context设计**：专门负责清理所有资源
3. **引用计数机制**：只要ref_count>0，资源就不会被释放

### 4.3 为什么不会内存泄漏？

**疑问**：我们不释放hwframe/hwdevice，会不会泄漏？

**答案**：不会！因为：

1. rkmpp_encode_init创建的`r->hwdevice`和`r->hwframe`并不是独立分配的
2. 它们是通过FFmpeg API创建的，与avctx关联
3. avcodec_free_context会遍历avctx的所有资源并释放
4. 即使编码器不释放，FFmpeg核心也会释放

**证据**：
- rkmppenc.c Line 1387-1402显示编码器可以检测到avctx中已有的hwdevice
- 这说明hwdevice与avctx是关联的，不是编码器私有的
