## 🔍 根本原因分析

### 可能性 1：Double-Free（最可能）⭐

**机制**：
1. rkmpp_encode_close() 释放了某些资源（hwframe, hwdevice）
2. avcodec_close() 尝试再次释放相同的资源
3. 导致 double-free 崩溃

**证据**：
- hwframe 和 hwdevice 在 rkmpp_encode_close() 中已 unref
- avcodec_close() 可能再次尝试释放这些资源
- 调用栈显示崩溃在 libc_free()（典型的 double-free 症状）

**相关代码**（rkmppenc.c Line 1186-1195）：
```c
if (r->hwframe) {
    av_buffer_unref(&r->hwframe);  // ← 释放 hwframe
    fprintf(stderr, "[FIX 100.83 DIAG-11] hwframe unref SUCCESS\n");
    fflush(stderr);
}
if (r->hwdevice) {
    av_buffer_unref(&r->hwdevice);  // ← 释放 hwdevice
    fprintf(stderr, "[FIX 100.83 DIAG-12] hwdevice unref SUCCESS\n");
    fflush(stderr);
}
```

**问题**：
- avcodec_close() 可能也会尝试释放 hwframe/hwdevice
- 但 rkmpp_encode_close() 已经释放过了
- 导致 double-free

---

### 可能性 2：Use-After-Free

**机制**：
1. rkmpp_encode_close() 释放了某些内存
2. 内存指针没有置为 NULL
3. avcodec_close() 继续访问已释放的内存

**证据不足**：
- rkmpp_encode_close() 中所有释放后都置为 NULL
- 不太可能是 use-after-free

---

### 可能性 3：AVCodecContext 内部状态不一致

**机制**：
1. rkmpp_encode_close() 修改了 AVCodecContext 的某些内部状态
2. 导致 avcodec_close() 的后续清理逻辑访问无效内存

**需要验证**：
- 检查是否修改了不应该修改的 AVCodecContext 字段

## 🔧 Fix 100.84 解决方案

### 核心策略

**不要在 codec->close() 中释放由 FFmpeg 管理的资源**

### 方案 A：移除 hwframe/hwdevice 的 unref（推荐）⭐

**原理**：
- hwframe 和 hwdevice 是通过 AVCodecContext 管理的
- FFmpeg 的 avcodec_close() 会自动释放这些资源
- codec->close() 只需释放编解码器特有的资源

**修改**：
```c
static av_cold int rkmpp_encode_close(AVCodecContext *avctx)
{
    RKMPPEncContext *r = avctx->priv_data;

    // ... MPP 清理 ...
    // ... 帧列表清理 ...

    // ❌ 2026-01-13 11:00 [FIX 100.84] 移除 hwframe/hwdevice unref
    // 原因：这些是 FFmpeg 管理的资源，avcodec_close() 会自动释放
    // 手动释放导致 double-free 崩溃
    // 参考：docs/2026-01-13/07-Fix100.83崩溃原因分析-Double-Free问题.md

    /* ❌ 移除以下代码（导致 double-free）
    if (r->hwframe) {
        av_buffer_unref(&r->hwframe);
    }
    if (r->hwdevice) {
        av_buffer_unref(&r->hwdevice);
    }
    */

    fprintf(stderr, "[FIX 100.84 DIAG-10] Skipping hwframe/hwdevice unref (managed by FFmpeg)\n");
    fflush(stderr);

    fprintf(stderr, "[FIX 100.84 DIAG-11] rkmpp_encode_close() EXIT SUCCESS\n");
    fflush(stderr);

    return 0;
}
```

---

### 方案 B：设置 hwframe/hwdevice 为 NULL（备选）

**原理**：
- unref 后立即设置为 NULL
- 防止 FFmpeg 再次释放

**修改**：
```c
if (r->hwframe) {
    av_buffer_unref(&r->hwframe);
    r->hwframe = NULL;  // ← 关键：设置为 NULL
    fprintf(stderr, "[FIX 100.84 DIAG-11] hwframe unref SUCCESS\n");
    fflush(stderr);
}
if (r->hwdevice) {
    av_buffer_unref(&r->hwdevice);
    r->hwdevice = NULL;  // ← 关键：设置为 NULL
    fprintf(stderr, "[FIX 100.84 DIAG-12] hwdevice unref SUCCESS\n");
    fflush(stderr);
}
```

**问题**：
- 即使设置为 NULL，也可能已经破坏了 AVCodecContext 的内部状态
- 方案 A 更彻底

---

### 推荐方案：方案 A

**理由**：
1. ✅ 符合 FFmpeg 编解码器设计原则
2. ✅ 避免 double-free
3. ✅ 避免资源管理冲突
4. ✅ 让 FFmpeg 统一管理 hwframe/hwdevice 生命周期

## 💡 技术启示

### FFmpeg 编解码器资源管理原则

**核心规则**：
> codec->close() 只释放编解码器特有的资源，不释放 AVCodecContext 管理的公共资源。

**资源分类**：

| 资源类型 | 谁创建 | 谁释放 | codec->close() 是否释放 |
|---------|--------|--------|------------------------|
| MPP 上下文（mctx） | rkmpp_encode_init() | rkmpp_encode_close() | ✅ 是 |
| MPP 配置（mcfg） | rkmpp_encode_init() | rkmpp_encode_close() | ✅ 是 |
| 帧列表（frame_list） | rkmpp_encode_init() | rkmpp_encode_close() | ✅ 是 |
| hwframe | FFmpeg (init_hwframes_ctx) | avcodec_close() | ❌ 否 |
| hwdevice | FFmpeg | avcodec_close() | ❌ 否 |
| AVCodecContext | FFmpeg | avcodec_free_context() | ❌ 否 |

**参考**：
- libavcodec 官方示例
- 其他硬件编解码器实现（vaapi, qsv, nvenc）
