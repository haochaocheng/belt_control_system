## 一、问题回顾

### 1.1 Fix 100.83 崩溃分析

**崩溃路径**：
```
1. 挂断视频通话
2. rkmpp_encode_close()
   → av_buffer_unref(&r->hwframe)    ← 第一次释放
   → av_buffer_unref(&r->hwdevice)   ← 第一次释放
   → return 0 (SUCCESS)

3. ffmpeg_codec_close()
   → avcodec_free_context(&ff->enc_ctx)
      → 内部调用编码器close (已完成)
      → av_buffer_unref(&avctx->hw_frames_ctx)  ← 第二次释放
      → ❌ CRASH: double-free in libc_free()
```

**根本原因**：
- rkmpp编码器内部创建`r->hwframe`（私有）
- 但编码器可能也设置了`avctx->hw_frames_ctx`指向同一buffer
- avcodec_free_context()尝试释放`avctx->hw_frames_ctx`
- 同一个buffer被释放两次 → double-free → 崩溃

### 1.2 方案对比

| 方案 | 修改位置 | 优势 | 劣势 |
|------|---------|------|------|
| **方案A** | rkmppenc.c（条件释放） | 最小改动 | 仍修改FFmpeg源码 |
| **方案B** | rkmppenc.c（完全不释放） | 简单直接 | 可能内存泄漏 |
| **方案C** | ffmpeg_vid_codecs.c + rkmppenc.c | 符合最佳实践 | 改动较大 |

**选择方案C**：
- ✅ 符合FFmpeg官方最佳实践（VA-API、NVENC、QSV）
- ✅ 明确资源所有权（PJSIP创建，编码器引用）
- ✅ 引用计数机制保证安全释放
- ✅ 避免内存泄漏和double-free

## 三、技术原理

### 3.1 引用计数机制

```
初始状态：
  hw_frames_ctx_local创建 → ref_count = 1

传递给编码器：
  ff->enc_ctx->hw_frames_ctx = av_buffer_ref(hw_frames_ctx_local)
  → ref_count = 2

释放本地引用：
  av_buffer_unref(&hw_frames_ctx_local)
  → ref_count = 1 (编码器仍持有)

编码器初始化：
  rkmpp_encode_init() 检测到 avctx->hw_frames_ctx
  → r->hwframe = av_buffer_ref(avctx->hw_frames_ctx)
  → ref_count = 2

编码器关闭：
  rkmpp_encode_close() 检测到 r->hwframe == avctx->hw_frames_ctx
  → 跳过释放 r->hwframe
  → ref_count = 1 (avctx->hw_frames_ctx仍持有)

最终清理：
  avcodec_free_context(&ff->enc_ctx)
  → av_buffer_unref(&avctx->hw_frames_ctx)
  → ref_count = 0
  → 真正释放内存 ✅
```

### 3.2 所有权模型

```
创建者：PJSIP (ffmpeg_vid_codecs.c)
  ↓
传递：ff->enc_ctx->hw_frames_ctx = av_buffer_ref(...)
  ↓
使用者：rkmpp编码器 (rkmppenc.c)
  - r->hwframe = av_buffer_ref(avctx->hw_frames_ctx)  // 增加引用
  - close时检测到外部所有权 → 不释放
  ↓
最终释放者：avcodec_free_context (FFmpeg核心)
  - 自动释放 avctx->hw_frames_ctx
```
