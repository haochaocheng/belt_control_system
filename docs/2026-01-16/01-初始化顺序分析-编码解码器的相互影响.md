# 初始化顺序分析 - 编码解码器的相互影响

**日期**: 2026-01-16 10:15
**问题**: 编码器初始化正常，编码时失败（x4->enc = NULL）
**调查方向**: 解码器初始化是否影响编码器状态

---

## 1. 用户关键观察 ⭐

> **"初始化正常，编码时不正确，是否和编码解码初始顺序有关"**

### 问题现象

1. **编码器初始化成功** ✅
   - `avcodec_open2(ff->enc_ctx, ff->enc)` 返回 0
   - 日志显示编码器打开成功

2. **编码时失败** ❌
   - `avcodec_send_frame()` 失败
   - `x4->enc = NULL`（编码器未初始化）

3. **关键矛盾** 🔍
   - 初始化时 `avcodec_open2()` 返回成功
   - 但编码时内部状态 `x4->enc` 为空

---

## 2. 当前初始化顺序

根据代码分析（`ffmpeg_vid_codecs.c` 的 `open_ffmpeg_codec()` 函数）：

### STEP 1: 分配上下文 (Line 2281-2311)
```c
if (ff->param->dir & PJMEDIA_DIR_ENCODING) {
    ff->enc_ctx = avcodec_alloc_context3(ff->enc);  // 编码器上下文
}
if (ff->param->dir & PJMEDIA_DIR_DECODING) {
    ff->dec_ctx = avcodec_alloc_context3(ff->dec);  // 解码器上下文
}
```

### STEP 2: 打开编码器 (Line 2894)
```c
err = AVCODEC_OPEN(ff->enc_ctx, ff->enc);  // ← 编码器先打开
```
- 编码器：`libx264`（软件）
- 此时解码器还未打开

### STEP 3: 打开解码器 (Line 3355)
```c
dec_err = avcodec_open2(ff->dec_ctx, ff->dec, NULL);  // ← 解码器后打开
```
- 解码器：`h264_rkmpp`（硬件）
- 使用 RKMPP 硬件加速

## 3. 假设：解码器初始化影响编码器

### 3.1 可能的影响机制

#### 机制 A: 全局资源竞争
- RKMPP 解码器初始化时占用全局资源（如 DRM, MPP service）
- 编码器内部状态被重置或覆盖

#### 机制 B: FFmpeg 内部状态变化
- 解码器初始化触发 FFmpeg 线程管理逻辑
- 可能影响编码器的 `thread_count` 或 `active_thread_type`
- 导致编码器上下文被重新创建（子上下文替换主上下文）

#### 机制 C: 共享内存/指针问题
- PJSIP 的 `ff->enc_ctx` 指针在解码器初始化后被修改
- 编码器和解码器共享某些内部结构

### 3.2 关键证据

#### 证据 1: 多线程初始化日志（FIX 100.211 测试）
```
初始化时：thread_count: 9, active_thread_type: 1  ← 多线程
编码时：  thread_count: 1, active_thread_type: 0  ← 单线程
```
- **初始化时**（编码器打开后，解码器打开前？）：多线程
- **编码时**（解码器已打开后）：单线程
- 说明编码器状态在两次调用之间发生了变化

#### 证据 2: x4->enc 为 NULL
```c
if (!x4->enc) {
    av_log(avctx, AV_LOG_ERROR, "x264_t* encoder is NULL!\n");
    return AVERROR(EINVAL);
}
```
- `X264_init()` 在初始化时被调用了 9 次（子上下文）
- 主上下文的 `x4->enc` 从未被初始化

#### 证据 3: 网上无类似问题
- 搜索 "PJSIP FFmpeg libx264" 无类似报告
- 搜索 "FFmpeg encoder decoder initialization order" 无相关讨论
- 说明我们的配置或环境可能是独特的

## 4. 测试方案 A: 交换初始化顺序

### 4.1 修改方案

**在 `ffmpeg_vid_codecs.c` 中交换编码器和解码器的打开顺序：**

```c
// 当前顺序：编码器 → 解码器
// 1. AVCODEC_OPEN(ff->enc_ctx, ff->enc);     // Line 2894
// 2. avcodec_open2(ff->dec_ctx, ff->dec...); // Line 3355

// 修改后：解码器 → 编码器
// 1. avcodec_open2(ff->dec_ctx, ff->dec...); // 先打开解码器
// 2. AVCODEC_OPEN(ff->enc_ctx, ff->enc);     // 后打开编码器
```

### 4.2 预期结果

#### 场景 A: 如果顺序有影响
- ✅ 编码器在解码器之后初始化
- ✅ 编码器不受解码器初始化的影响
- ✅ `x4->enc` 正确初始化
- ✅ 编码成功

#### 场景 B: 如果顺序无影响
- ❌ 仍然编码失败，`x4->enc = NULL`
- 说明问题不在初始化顺序
- 需要从其他方向调查

### 4.3 风险评估

- **风险等级**: 低
- **可逆性**: 是（可以轻松回退）
- **影响范围**: 仅修改初始化顺序，不修改编码器参数
- **测试时间**: 5-10 分钟（快速验证）

// 在 Line 3348 添加条件，跳过解码器打开

## 6. 其他可能原因

### 6.1 FFmpeg 多线程逻辑

参考：`docs/2026-01-15/33-FFmpeg线程问题完整根因分析.md`

- FFmpeg 在 `avcodec_open2()` 时检测 `thread_type` 和编码器能力
- 如果 `thread_type != 0`，可能创建多个子上下文
- 子上下文被初始化，主上下文未初始化

### 6.2 编码器参数问题

- `thread_count`, `thread_type` 被 FFmpeg 覆盖
- 默认值：`thread_type = FF_THREAD_SLICE | FF_THREAD_FRAME = 3`
- 导致错误的线程初始化逻辑

### 6.3 libx264 版本兼容性

- 网上无类似问题报告
- 可能是特定版本的 libx264 或 FFmpeg 的 bug
- 需要检查版本号并尝试升级/降级
