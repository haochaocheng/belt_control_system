# FIX 100.281 - 增加 GStreamer 缓冲区解决播放断续

**日期**: 2026-01-21 18:00
**问题**: 播放开头 2-3 秒内音频断续（卡 2-3 次）
**根因**: GStreamer 缓冲区不足，报告 BufferedMedia 过快（0ms）
**状态**: ✅ 代码修改完成，等待测试

---

## 问题回顾

### 用户反馈（最终澄清）

> "卡断不是每次播放之间，而是没一次播放开头2到3秒内，停顿很短时间，然后继续播放，能卡两到三次"

**现象**：
```
播放流程：
[用户按"启动"]
  ↓
[0s] 开始播放音频 "1号皮带启动.mp3"
  ↓
[0-3s] 音频播放但断续：
  "1号皮...（卡）...带启...（卡）...动"
  ↑ 2-3 次短暂停顿
  ↓
[3s+] 播放流畅 ✅
```

**每次播放都这样**（3 次测试全部如此）

## 失败的修复尝试

### FIX 100.279 失败 - 减小 ALSA 缓冲区

**修改**：`buffer_time 40000` (40ms)
**原因分析**：减小缓冲区应该减少启动延迟
**结果**：❌ "问题依旧，没有任何变化"
**错误**：方向错了，缓冲区太小反而容易 underrun

### FIX 100.280 失败 - 增大 ALSA 缓冲区

**修改**：`buffer_time 200000` (200ms)
**原因分析**：增大缓冲区应该避免 underrun
**结果**：❌ "问题依旧，没有任何变化"
**错误**：问题不在 ALSA 层，在 GStreamer 层

**Smoking Gun**：
```
[媒体状态]  "BufferedMedia" | 距上次状态变化: 0 ms
```

**说明**：
- GStreamer 报告 `BufferedMedia` 几乎是瞬间的（0ms）
- 这意味着 GStreamer **认为**它已经缓冲好了
- 但实际上**没有缓冲足够的数据**
- 播放开始后，缓冲区很快耗尽 → underrun → 停顿

## 技术原理

### 播放流程和缓冲层次

```
应用层：
  QMediaPlayer::play()
    ↓
GStreamer 层：（问题在这里！）
  1. 创建 pipeline
  2. 解码 MP3 → PCM
  3. 填充 GStreamer 内部队列
  4. ⚠️ 过早报告 BufferedMedia（0ms）
  5. 开始推送数据到 ALSA
    ↓
ALSA 层：（FIX 100.280 修改的层，但不是问题所在）
  1. 接收 PCM 数据
  2. 填充 ALSA 缓冲区（200ms）
  3. 推送到硬件
    ↓
硬件层：
  ES8388 音频芯片播放
```

**为什么 ALSA 层增大缓冲区没用？**

ALSA 缓冲区再大（200ms），也需要 GStreamer 持续供应数据。
如果 GStreamer 层的队列太小，数据供应不上，ALSA 缓冲区还是会空。

**比喻**：
```
ALSA 缓冲区 = 水桶（200升）
GStreamer 队列 = 水管（直径 2cm）

问题：
- 水桶很大（200L）✅
- 但水管太细（2cm）❌
- 水桶还是会空（underrun）

解决：
- 增粗水管（增大 GStreamer 队列）✅
```

### GStreamer 队列参数

GStreamer 使用 `queue` 元素来缓冲数据：

**关键参数**：
1. **GST_QUEUE_SIZE_BUFFERS**：队列能容纳的缓冲块数量
   - 默认：`200` 个块
   - 问题：对于 MP3 这种压缩格式，200 个块可能不够

2. **GST_QUEUE_MAX_SIZE_TIME**：队列能容纳的最大时间（纳秒）
   - 默认：`1000000000` ns = 1 秒
   - 问题：1 秒缓冲不够，播放开头容易 underrun

**当前问题**：
```
默认配置：
- BUFFERS = 200 个块
- MAX_TIME = 1 秒

播放流程：
[0ms] play() 调用
[5ms] GStreamer 开始解码 MP3
[10ms] 解码了 200 个块（约 0.5 秒数据）
[10ms] 报告 BufferedMedia ← 太快了！
[10ms] 开始播放
[500ms] 缓冲区耗尽（只有 0.5 秒数据）
[500ms] 停顿，等待更多数据 ❌
[700ms] 数据到达，继续播放
[1200ms] 又耗尽，又停顿 ❌
[1500ms] 数据到达，继续播放
[2000ms] 又耗尽，又停顿 ❌
[3000ms] 解码追上播放，形成稳定流水线 ✅
```

## 解决方案

### FIX 100.281：增加 GStreamer 队列参数

**修改文件**：`docker/rk3588/run-ubuntu24-apt.sh`

**修改位置**：Line 177（`-e XDG_RUNTIME_DIR=/tmp \` 之后）

**添加环境变量**：
```bash
-e GST_QUEUE_SIZE_BUFFERS=1000 \
-e GST_QUEUE_MAX_SIZE_TIME=5000000000 \
```

**参数说明**：

| 参数 | 默认值 | 新值 | 说明 |
|------|--------|------|------|
| `GST_QUEUE_SIZE_BUFFERS` | 200 | 1000 | 队列容纳 1000 个缓冲块（↑ 5 倍） |
| `GST_QUEUE_MAX_SIZE_TIME` | 1s | 5s | 队列最大时间 5 秒（↑ 5 倍） |

**预期效果**：
```
新配置：
- BUFFERS = 1000 个块
- MAX_TIME = 5 秒

播放流程：
[0ms] play() 调用
[5ms] GStreamer 开始解码 MP3
[500ms] 解码了 1000 个块（约 2.5 秒数据）← 更多数据
[500ms] 报告 BufferedMedia ← 延迟到有足够数据
[500ms] 开始播放
[500ms - 8000ms] 流畅播放，无 underrun ✅
```

## 风险评估

### 潜在风险

1. **起播延迟增加**：
   - 风险：用户按下按钮到听到声音的延迟可能从 ~150ms 增加到 ~600ms
   - 缓解：对于 5 秒的音频，600ms 延迟（12%）是可接受的
   - 结论：✅ 可接受（相比卡顿更好）

2. **内存占用增加**：
   - 风险：队列增大 5 倍可能增加内存占用
   - 实际：130KB MP3 × 1000 块 ÷ 200 块/秒 ≈ 650KB 增量
   - 结论：✅ 可忽略（RK3588 有 8GB 内存）

3. **参数不适用其他场景**：
   - 风险：其他音频格式（WAV）可能不需要这么大缓冲区
   - 缓解：WAV 不需要解码，即使缓冲大也不会增加延迟
   - 结论：✅ 无影响

**总体风险**：低 ✅

## 技术对比

### 为什么不在 ALSA 层解决？

| 层次 | 特性 | FIX 100.280 | FIX 100.281 |
|------|------|------------|------------|
| **ALSA 层** | 硬件缓冲区 | ✅ 200ms（已最大） | 保持 200ms |
| **GStreamer 层** | 软件队列 | ❌ 1s（太小） | ✅ 5s（充足） |

**问题定位**：
- ALSA 缓冲区 200ms 已经足够大 ✅
- 但 GStreamer 供应数据跟不上 ❌
- 增大 ALSA 缓冲区无效（如 FIX 100.280）
- **必须增大 GStreamer 队列**（FIX 100.281）

### 为什么 GStreamer 默认参数不够？

**MP3 解码特性**：
- MP3 是压缩格式，需要实时解码
- 解码速度受 CPU 负载影响
- RK3588 的 ARM CPU 解码 MP3 可能不够快
- 容器环境增加了调度延迟

**默认参数适用场景**：
- 桌面环境（高性能 CPU）
- 未压缩格式（WAV/PCM）
- 本地文件（低延迟 I/O）

**嵌入式环境挑战**：
- ARM CPU 性能有限
- Docker 容器增加开销
- 压缩格式需要解码

## 备选方案

### 如果 FIX 100.281 效果不佳

**方案 1**：进一步增大 GStreamer 队列（更激进）

```bash
-e GST_QUEUE_SIZE_BUFFERS=2000 \      # 10 倍（2000 个块）
-e GST_QUEUE_MAX_SIZE_TIME=10000000000 \  # 10 秒
```

**方案 2**：转换为 WAV 格式（无需解码）

```powershell
# 预处理脚本：将所有 MP3 转换为 WAV
.\scripts\2026-01-21\05-convert-mp3-to-wav.ps1
```

**优点**：
- WAV 不需要解码，直接播放
- 播放延迟降到最低（<100ms）

**缺点**：
- 文件大小增加（130KB → ~600KB）

**方案 3**：预加载音频到内存

```cpp
// CommonControl.cpp
QMap<QString, QByteArray> m_audioCache;

void CommonControl::preloadAudioFiles() {
    QStringList audioFiles = {
        "/app/AUDIO/语音文件/001.wav",
        "/app/AUDIO/语音文件/002.wav",
        "/app/AUDIO/语音文件/003.wav"
    };

    for (const QString &path : audioFiles) {
        QFile file(path);
        if (file.open(QIODevice::ReadOnly)) {
            m_audioCache[path] = file.readAll();
        }
    }
}
```
