## 🔍 根本原因分析

### 条件编译结构（encode_frame 函数）

**文件位置**：`ffmpeg_vid_codecs.c` (Lines 3096-3327)

```c
#if LIBAVCODEC_VER_AT_LEAST(58,137)        // Line 3096
    // ✅ FFmpeg 58.137+ API
    // ✅ 有完整的硬件帧处理逻辑
    // ✅ 能正确处理 DRM_PRIME 格式
    err = avcodec_send_frame(ff->enc_ctx, frame_to_encode);  // 带硬件转换

#elif LIBAVCODEC_VER_AT_LEAST(54,15)       // Line 3299 ← 当前执行这里！
    // ❌ FFmpeg 54.15+ API（旧版分支）
    // ❌ 没有硬件帧处理逻辑！
    // ❌ 直接传递帧，不做任何转换
    err = avcodec_send_frame(ff->enc_ctx, &avframe);  // 无硬件转换！

#else                                       // Line 3323
    // 更旧的 API
    err = avcodec_encode_video(ff->enc_ctx, ...);
#endif
```

### 版本判断错误

**当前环境**：
- FFmpeg 版本：6.1
- libavcodec 版本：**58.91.100**

**条件判断**：
```c
LIBAVCODEC_VER_AT_LEAST(58,137)
= (58 > 58 || (58 == 58 && 91 >= 137))
= (FALSE || (TRUE && FALSE))
= FALSE  ← 不进入第一个分支 ❌

LIBAVCODEC_VER_AT_LEAST(54,15)
= (58 > 54 || (58 == 54 && 91 >= 15))
= TRUE  ← 进入第二个分支（错误！）❌
```

### 为什么黑屏？

**完整数据流**：
```
1. 初始化阶段 ✅
   └─ h264_rkmpp 硬件编码器成功注册（Fix 100.17）

2. 视频接收阶段 ✅
   └─ RKMPP 解码器输出 DRM_PRIME 格式（GPU 内存）

3. 编码阶段 ❌
   └─ 进入错误的条件编译分支（line 3299-3322）
   └─ 该分支没有硬件帧转换逻辑
   └─ 直接调用 avcodec_send_frame(&avframe)
   └─ DRM_PRIME 帧 → h264_rkmpp 编码器
   └─ 编码器期望已转换的帧，但收到原始 DRM_PRIME 帧
   └─ 编码失败 → 无输出 → 黑屏
```

**关键代码** (Line 3302-3309)：
```c
PJ_LOG(1,(THIS_FILE, "⚠️⚠️⚠️ [DIAGNOSTIC] Entered FFmpeg 54.15+ API block (OLD VERSION)"));
PJ_LOG(1,(THIS_FILE, "    This branch does NOT have hardware frame handling!"));

// ❌ 直接传递 avframe，不做任何硬件帧转换
PJ_LOG(1,(THIS_FILE, "❗ [CRITICAL] Calling avcodec_send_frame() WITHOUT hardware conversion"));
err = avcodec_send_frame(ff->enc_ctx, &avframe);
```

## ✅ 解决方案（方案 A）

### 修改条件，让 FFmpeg 6.1 进入正确分支

**目标**：让 libavcodec 58.91.100 进入第一个分支（有硬件帧处理）

**修改位置**：Line 3096

**修改前**：
```c
#if LIBAVCODEC_VER_AT_LEAST(58,137)  // 58.91 < 58.137，不满足 ❌
```

**修改后**：
```c
#if LIBAVCODEC_VER_AT_LEAST(58,0)    // 58.91 >= 58.0，满足 ✅
```

### 原理

- FFmpeg 6.x 使用 libavcodec 58.x 或 60.x
- 58.137 这个版本号太高了（可能对应 FFmpeg 5.x 的某个小版本）
- 改为 58.0 后，所有 libavcodec 58.x 都会进入第一个分支
- 确保硬件帧处理逻辑能够执行

### 预期效果

**修改后的条件判断**：
```c
LIBAVCODEC_VER_AT_LEAST(58,0)
= (58 > 58 || (58 == 58 && 91 >= 0))
= (FALSE || (TRUE && TRUE))
= TRUE  ← 进入第一个分支 ✅

// 不会再进入 #elif 分支
```

**预期日志**：
```
✅✅✅ [DIAGNOSTIC] Entered FFmpeg 58.137+ API block  ← 实际是 58.0+
    About to prepare frame and call avcodec_send_frame()
（硬件帧转换逻辑执行）
```

## 📊 技术细节

### 为什么 58.137 这个版本号？

**推测**：
- 原开发者可能基于 FFmpeg 5.x 的某个版本（libavcodec 58.137+）
- 在那个版本之后，FFmpeg 引入了新的硬件帧处理 API
- 但 FFmpeg 6.1 的 libavcodec 版本号回退到 58.91

**实际情况**：
- FFmpeg 版本号（6.1）和 libavcodec 版本号（58.91）不完全对应
- 不同发行版可能有不同的版本号策略
- 应该基于功能而非具体版本号来判断

### 为什么改为 58.0？

**原理**：
- libavcodec 58.x 系列都支持 `avcodec_send_frame()` API
- 硬件帧处理逻辑不依赖特定的小版本号
- 58.0 是保守的选择，覆盖所有 58.x 版本

**安全性**：
- 第二个分支（#elif）仍保留，作为 fallback
- 如果第一个分支有问题，代码会进入第二个分支
- 不会影响更低版本的 FFmpeg（< 58.0）
