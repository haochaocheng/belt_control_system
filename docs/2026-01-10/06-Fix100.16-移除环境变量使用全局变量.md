# Fix 100.16：移除环境变量，使用全局变量控制硬件编码器

**日期**: 2026-01-10 19:00
**问题编号**: Fix 100.16
**状态**: ✅ 已实施

---

## 📋 问题描述

### 现象
部署后日志显示仍在使用 `libx264rgb` 编码器，而非预期的 `h264_rkmpp` 硬件编码器：
```
01:54:58.166    ffmpeg_vid_codecs.c  .......   Encoder: libx264rgb
```

### 影响
- ❌ 硬件编码器未启用
- ❌ 仍然崩溃（DRM_PRIME 格式不兼容）
- ❌ CPU 使用率高（~40%）

---

## 🔍 根本原因

### 环境变量传递不可靠
虽然在容器中设置了 `USE_HARDWARE_ENCODER=1` 环境变量：
```bash
# build-ubuntu24-apt.ps1 (line 1587)
-e USE_HARDWARE_ENCODER=1 \
```

但是 PJSIP 代码中读取环境变量的逻辑可能存在问题：
```c
// ffmpeg_vid_codecs.c (line 1128-1132)
const char* use_hw_encoder = getenv("USE_HARDWARE_ENCODER");
int enable_hw_encoder = 1;
if (use_hw_encoder) {
    enable_hw_encoder = atoi(use_hw_encoder);
}
```

**可能的原因**：
1. Docker 容器环境变量传递时机问题
2. PJSIP 初始化时环境变量未就绪
3. 多线程环境下 getenv() 不可靠

---

## ✅ 解决方案

### 用户需求
> "不要使用环境变量，在应用层应用全局变量"

### 修改内容

#### 1. ffmpeg_vid_codecs.c (Lines 1125-1129)

**修改前**（使用环境变量）：
```c
// ✅ 2026-01-09 17:50 [修复 97] 环境变量声明移到 for 循环开始
const char* use_hw_encoder = getenv("USE_HARDWARE_ENCODER");
int enable_hw_encoder = 1;  // 默认：1（启用硬件编码器）
if (use_hw_encoder) {
    enable_hw_encoder = atoi(use_hw_encoder);
}
```

**修改后**（使用全局变量）：
```c
// ✅ 2026-01-10 19:00 [修复 100.16] 移除环境变量，使用全局变量控制硬件编码器
// 原因：环境变量传递不可靠，改用代码中的全局变量
// 修改：默认启用硬件编码器（enable_hw_encoder = 1）
// 用法：0=使用软件编码器 libx264, 1=使用硬件编码器 h264_rkmpp
int enable_hw_encoder = 1;  // ✅ 默认启用硬件编码器
```

#### 2. ffmpeg_vid_codecs.c (Line 1191)

**更新日志输出**：
```c
// 修改前
PJ_LOG(1,(THIS_FILE, "✅ [FIX 97] Hardware encoder ENABLED (USE_HARDWARE_ENCODER=%d, default=1)", enable_hw_encoder));

// 修改后
PJ_LOG(1,(THIS_FILE, "✅ [FIX 100.16] Hardware encoder ENABLED (global variable enable_hw_encoder=%d)", enable_hw_encoder));
```

#### 3. build-ubuntu24-apt.ps1 (Line 1587)

**移除环境变量设置**：
```bash
# 修改前
-e USE_HARDWARE_ENCODER=1 \

# 修改后（移除）
# （已删除）
```

## 📚 技术细节

### 全局变量 vs 环境变量

| 特性 | 全局变量 | 环境变量 |
|------|---------|---------|
| **设置方式** | 代码中定义 | 容器启动参数 |
| **生效时机** | 编译时 | 运行时 |
| **可靠性** | ✅ 100% 可靠 | ⚠️ 可能失败 |
| **调试难度** | ✅ 容易 | ❌ 困难 |
| **修改方式** | 修改代码 + 重编译 | 修改启动脚本 |
| **多线程安全** | ✅ 安全 | ⚠️ 可能不安全 |

### 为什么环境变量不可靠？

1. **时机问题**：PJSIP 可能在容器环境完全初始化前启动
2. **线程安全**：`getenv()` 在多线程环境下不保证安全
3. **Docker 限制**：某些 Docker 配置可能限制环境变量传递
4. **调试困难**：无法确定环境变量何时、如何传递

### 为什么全局变量更好？

1. **编译时确定**：行为在编译时固定，无运行时不确定性
2. **代码即文档**：直接查看代码即可知道配置
3. **无外部依赖**：不依赖容器配置或启动参数
4. **调试简单**：出问题直接看代码，无需检查环境
