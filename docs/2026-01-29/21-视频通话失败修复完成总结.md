# 视频通话失败修复完成总结

**日期**: 2026-01-29
**状态**: ✅ 已修复
**优先级**: ⚠️ 高（视频功能完全失效）

---

## 🎯 问题总结

**用户报告**：
- 本机能显示本机的画面，不能显示对方的画面
- 对方也只能显示本机的画面，不能显示工控机的画面
- 日志显示：`#1 video deactivated`

**错误信息**：
```
video channel_update failed for call_id 0 media 1:
Codec internal creation error (PJMEDIA_CODEC_EFAILED)
```

---

## 🔍 根因分析

### 1. 错误追踪链条

```
GitHub 回滚 → 重新部署
    ↓
device-build/libs/ 缺少 MPP 库
    ↓
Docker 镜像缺少 libmpp_ext.so
    ↓
RKMPP 解析器无法注册
    ↓
H.264 解码器初始化失败
    ↓
编解码器上下文创建失败 (dec_ctx=nil, enc_ctx=nil)
    ↓
视频通道更新失败 (PJMEDIA_CODEC_EFAILED)
    ↓
视频流被销毁，只有音频
```

### 2. 关键日志证据

**日志 Line 1739-1741**：
```
mpp[1]: mpp_info: mpp version: b13eb80 author: Herman Chen
        2026-01-08 feat[mpp_ext]: Move parsers to libmpp_ext.so
mpp[1]: mpp_dec: mpp_parser_init parser h264 is not registered
mpp[1]: mpp_dec: mpp_dec_init could not init parser
```

**日志 Line 1828**：
```
🔍 [FIX 100.66 DIAG] dec_ctx=(nil), enc_ctx=(nil)
```

**日志 Line 1835**：
```
video channel_update failed for call_id 0 media 1:
Codec internal creation error (PJMEDIA_CODEC_EFAILED)
```

### 3. 根本原因

**MPP 库架构变化**（2026-01-08）：
- **旧版本**：解析器内置在 `librockchip_mpp.so` 中
- **新版本**：解析器分离到独立的 `libmpp_ext.so` 库

**部署缺失**：
- `device-build/libs/` 目录缺少 `libmpp_ext.so`
- Docker 镜像构建时未包含此库
- 运行时 RKMPP 解码器无法加载 H.264 解析器

---

## ✅ 修复方案

### 方案 1：手动复制 MPP 库（临时修复）

**执行命令**：
```bash
cp -v docker/rk3588/rk3588-libs/lib/libmpp_ext.so* docker/rk3588/device-build/libs/
cp -v docker/rk3588/rk3588-libs/lib/librockchip_mpp.so* docker/rk3588/device-build/libs/
```

**结果**：

### 方案 2：修改构建脚本（长期方案）

**修改文件**：`build-ubuntu24-apt.ps1` Line 1305

**修改内容**：
```powershell
# ✅ 2026-01-29 [FIX 视频通话失败] 添加 libmpp_ext.so.*
# 原因：2026-01-08 MPP 更新将 H.264 解析器移到 libmpp_ext.so
# 缺少此库导致 RKMPP 解码器初始化失败，视频通话失败

                   "libogg.so.*", "libspeex.so.*", "libtheora*.so.*", "libvorbis*.so.*",
                   "libyuv.so.*", "libwebp.so.*", "libwebpmux.so.*", "libwebpdemux.so.*",
                   "libaribb24.so.*", "libaom.so.*", "libcodec2.so.*", "libdav1d.so.*",
                   "libgsm.so.*", "libopencore-amrnb.so.*", "libopencore-amrwb.so.*",
                   "libopenjp2.so.*", "libshine.so.*", "libsnappy.so.*", "libtwolame.so.*",
                   "libvo-amrwbenc.so.*", "libwavpack.so.*", "libxvidcore.so.*", "libzvbi.so.*",
                   "libva.so.*", "libva-*.so.*", "libvdpau.so.*", "libOpenCL.so.*", "libsoxr.so.*",
                   "librockchip_mpp.so.*", "libmpp_ext.so.*", "librga.so.*")
                   #                       ^^^^^^^^^^^^^^^^^ 新增
```

**效果**：
- 每次运行 `build-ubuntu24-apt.ps1` 都会自动复制 `libmpp_ext.so`
- 不再需要手动复制
- 防止未来再次遗漏

## 📊 技术细节

### MPP 库依赖关系

```
libavcodec.so.60 (FFmpeg 视频编解码器)
  └── librockchip_mpp.so.1 (RKMPP 硬件编解码器)
      └── libmpp_ext.so.1 (RKMPP 解析器扩展)
          └── H.264/H.265/VP8/VP9 解析器
```

- **PJMEDIA_CODEC_EFAILED** = 220081
- **含义**：编解码器内部创建错误
- **原因**：RKMPP 解码器初始化失败（解析器未注册）

- **版本**：b13eb80
- **日期**：2026-01-08
- **变更**：feat[mpp_ext]: Move parsers to libmpp_ext.so
- **作者**：Herman Chen

## 🎓 经验教训

### 1. 库依赖管理的重要性

**问题**：
- 外部库更新导致依赖关系变化
- 构建脚本未及时更新
- 部署时缺少关键库文件

**教训**：
- 定期检查外部库的更新日志
- 构建脚本应包含所有必要的库文件
- 添加自动化检查，验证库文件完整性

### 2. 日志分析的价值

**关键日志**：
```
mpp[1]: mpp_dec: mpp_parser_init parser h264 is not registered
mpp[1]: mpp_dec: mpp_dec_init could not init parser
```

**价值**：
- 直接指出问题根源（解析器未注册）
- 提供版本信息（b13eb80, 2026-01-08）
- 说明架构变化（Move parsers to libmpp_ext.so）

**教训**：
- 仔细阅读所有错误日志
- 关注库的版本信息和变更说明
- 使用日志追踪问题链条

**问题**：
- 手动复制库文件容易遗漏
- 每次部署都需要记住复制步骤

**解决**：
- 修改构建脚本自动复制
- 使用模式匹配批量处理
- 添加详细的注释说明

**好处**：
- 减少人为错误
- 提高部署效率
- 确保一致性
