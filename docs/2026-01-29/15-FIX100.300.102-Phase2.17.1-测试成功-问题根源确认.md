### 证据链

1. **Phase 2.1 - 2.16**：
   - 修复了递归布局、动态绑定、ReferenceError 等问题

   - 尝试移除 RowLayout
   - 但因语法错误失败

3. **Phase 2.17.1**：
   - 修复语法错误，正确注释掉整个 RowLayout
   - **程序不再卡住**
   - **Qt.callLater 回调成功执行**
   - **事件循环正常工作**

## 📊 问题分析

### RowLayout 的复杂度

**被注释掉的 RowLayout**（Line 286-800，共 **515 行代码**）：

```qml
RowLayout {
    width: parent.width - 20
    spacing: 20

    // 左列：5 个输入控件
    ColumnLayout {
        // 保护名称 (0)
        // 模块类型 (2)
        // 寄存器地址 (4)
        // 通道编号 (6)
        // 保护延时 (8)
    }

    // 右列：4 个输入控件
    ColumnLayout {
        // 播放次数 (1)
        // 播放时长 (3)
        // TTS文字 (5)
        // 音频文件 (7)
    }
}
```

### 复杂度来源

1. **嵌套布局**：
   - RowLayout → 2 个 ColumnLayout → 9 个 RowLayout → 大量控件
   - 嵌套层级深，布局计算复杂

2. **大量绑定表达式**：
   - 每个控件都有焦点指示器（Rectangle）
   - 每个焦点指示器有 2 个绑定（border.color, border.width）
   - 9 个控件 × 2 个绑定 = **18 个绑定表达式**

3. **复杂的焦点逻辑**：
   - 两列交叉导航（0, 2, 4, 6, 8 vs 1, 3, 5, 7）
   - 每个绑定都依赖 `root.focusSubArea` 和 `root.focusParamIndex`
   - 任何焦点变化都会触发大量绑定重新计算

4. **虚拟键盘集成**：
   - 每个输入控件都传递 `keyboardManager`
   - 增加了额外的复杂度

### 为什么会卡住？

**假设**：在 QDS 预览模式下，当 RowLayout 加载时：

1. **布局计算**：
   - RowLayout 需要计算两列的宽度和高度
   - 每个 ColumnLayout 需要计算子元素的布局
   - 每个 RowLayout 需要计算子元素的布局
   - 嵌套层级深，计算量大

2. **绑定初始化**：
   - 18 个焦点指示器绑定同时初始化
   - 每个绑定都依赖 `root.focusSubArea` 和 `root.focusParamIndex`
   - 可能触发大量绑定重新计算

3. **事件循环阻塞**：
   - 布局计算和绑定初始化占用大量时间
   - 事件循环无法处理其他事件
   - Qt.callLater 回调无法执行
   - 程序卡住

## 🔄 下一步行动

### 方案 1: 简化 RowLayout（推荐）

**目标**：逐步恢复 RowLayout 的部分内容，找到具体导致卡住的控件或绑定

**步骤**：
1. **Phase 2.18**：恢复 RowLayout 框架，但不添加任何控件
   - 只保留 RowLayout 和两个空的 ColumnLayout
   - 测试是否卡住

2. **Phase 2.19**：添加左列的第一个控件（保护名称）
   - 测试是否卡住
   - 如果不卡住，继续添加下一个控件

3. **Phase 2.20**：逐步添加其他控件
   - 每次添加一个控件，测试是否卡住
   - 找到具体导致卡住的控件

4. **Phase 2.21**：优化导致卡住的控件
   - 简化绑定表达式
   - 减少嵌套层级
   - 使用更高效的布局方式

### 方案 2: 使用单列布局（备选）

**目标**：放弃两列交叉导航，使用单列顺序布局

**优势**：
- 布局简单，计算量小
- 绑定表达式少
- 不会卡住

**劣势**：
- 失去两列交叉导航的功能
- 用户体验可能不如两列布局

### 方案 3: 使用 ListView 代替 RowLayout（高级）

**目标**：使用 ListView 的 delegate 机制，按需加载控件

**优势**：
- ListView 只渲染可见的 delegate
- 性能更好
- 不会卡住

**劣势**：
- 需要重新设计数据模型
- 实现复杂度高

## 🎓 经验教训

### 1. 复杂布局的性能问题

**问题**：
- 嵌套布局层级深
- 大量绑定表达式
- 复杂的焦点逻辑

**教训**：
- 在 QDS 预览模式下，复杂布局可能导致性能问题
- 需要权衡功能和性能
- 优先考虑简单的布局方式

### 2. 系统性排查的重要性

**方法**：
- 从简单到复杂，逐步排除可能原因
- 使用日志和调试工具验证假设
- 不要盲目修复，要找到根本原因

**成果**：
- 经过 17 个修复尝试，终于找到问题根源
- 排除了所有其他可能原因
- 确认问题在 RowLayout 的复杂度

### 3. 简化测试的价值

**方法**：
- 移除复杂的部分，使用简单的测试代码
- 验证基本功能是否正常
- 逐步恢复复杂的部分

**成果**：
- Phase 2.17.1 使用简单的 Text 组件
- 成功验证事件循环正常
- 确认问题在 RowLayout

### 4. QDS 预览模式的限制

**发现**：
- QDS 预览模式可能与实际运行环境不同
- 某些复杂布局在 QDS 中可能有性能问题
- 需要在实际设备上验证

**建议**：
- 优先在实际设备上测试
- QDS 预览模式仅用于快速验证
- 复杂功能需要在实际环境中测试
