## 📋 问题描述

用户在测试 COM5 (RS485) 串口通信时，发现接收区存在格式显示和乱码问题：

### 问题1：日志格式标签不一致

**现象**：
- 接收区格式选择：HEX
- 日志显示：`[ASCII] "\u0001\u0003\u0000\u0000\u0000\n��"`
- 格式标签和实际数据不一致

**原因**：
- 日志输出根据 `m_receiveHexMode` 决定格式标签
- 但用户选择 HEX 模式时，日志仍然显示 `[ASCII]`

### 问题2：ASCII 模式下乱码

**现象**：
- ASCII 模式下，二进制数据显示为方块（乱码）
- 例如：`01 03 00 00 00 0A C5 CD` 显示为 `□□□□□□□□`

**原因**：
- MODBUS 协议数据是二进制数据，不是 ASCII 文本
- `QString::fromUtf8()` 无法正确处理二进制数据
- 不可打印字符（0x00-0x1F, 0x7F-0xFF）显示为乱码

```cpp
} else {
```

```cpp
    QString asciiData;
    for (int i = 0; i < data.size(); ++i) {
        unsigned char byte = static_cast<unsigned char>(data[i]);
        if (byte >= 32 && byte <= 126) {
            // 可打印 ASCII 字符（空格到~）
            asciiData += QChar(byte);
        } else if (byte == '\r') {
            asciiData += "\\r";
        } else if (byte == '\n') {
            asciiData += "\\n";
        } else if (byte == '\t') {
            asciiData += "\\t";
        } else {
            // 不可打印字符：显示为十六进制 \xHH
            asciiData += QString("\\x%1").arg(byte, 2, 16, QChar('0')).toUpper();
        }
    }
    m_receiveBuffer += timestamp + asciiData + "\n";
}
```

## 💡 技术要点

### 1. ASCII 字符分类

**可打印 ASCII 字符**（32-126）：
```
空格 !"#$%&'()*+,-./0123456789:;<=>?
@ABCDEFGHIJKLMNOPQRSTUVWXYZ[\]^_
`abcdefghijklmnopqrstuvwxyz{|}~
```

**不可打印字符**（0-31, 127-255）：
- 控制字符：0x00-0x1F, 0x7F
- 扩展 ASCII：0x80-0xFF

**特殊字符**：
- `\r` (0x0D)：回车
- `\n` (0x0A)：换行
- `\t` (0x09)：制表符

### 2. 字符显示规则

```cpp
if (byte >= 32 && byte <= 126) {
    // 可打印 ASCII 字符：直接显示
    asciiData += QChar(byte);
} else if (byte == '\r') {
    // 回车：显示为 \r
    asciiData += "\\r";
} else if (byte == '\n') {
    // 换行：显示为 \n
    asciiData += "\\n";
} else if (byte == '\t') {
    // 制表符：显示为 \t
    asciiData += "\\t";
} else {
    // 不可打印字符：显示为 \xHH
    asciiData += QString("\\x%1").arg(byte, 2, 16, QChar('0')).toUpper();
}
```

### 3. 十六进制格式化

```cpp
QString("\\x%1").arg(byte, 2, 16, QChar('0')).toUpper()
```

**参数说明**：
- `byte`：要格式化的字节值
- `2`：字段宽度（2位）
- `16`：进制（十六进制）
- `QChar('0')`：填充字符（0）
- `.toUpper()`：转换为大写（0x0A → 0x0A）

**输出示例**：
- `0x01` → `\x01`
- `0x0A` → `\x0A`
- `0xFF` → `\xFF`

### 4. 为什么日志始终显示 HEX

**原因**：
1. **调试需要**：HEX 格式便于分析二进制协议
2. **避免乱码**：日志中不会出现不可打印字符
3. **一致性**：日志格式固定，便于解析

**用户体验**：
- 用户可以在接收区选择 HEX 或 ASCII 模式
- 日志始终显示 HEX，不影响用户选择
- 两者互不干扰

## 🔄 相关问题

### 1. 为什么不直接使用 QString::fromUtf8()？

**问题**：
- `QString::fromUtf8()` 假设输入是有效的 UTF-8 文本
- 对于二进制数据（如 MODBUS 协议），会产生乱码
- 不可打印字符显示为方块或问号

**解决方案**：
- 逐字节检查，区分可打印和不可打印字符
- 可打印字符正常显示
- 不可打印字符显示为 `\xHH` 格式

### 2. ASCII 模式适用场景

**适用场景**：
- 接收文本数据（如 AT 命令响应）
- 调试串口通信（查看可读文本）
- 混合数据（文本 + 控制字符）

**不适用场景**：
- 纯二进制协议（如 MODBUS）
- 图像数据
- 加密数据

**建议**：
- 对于 MODBUS 等二进制协议，使用 HEX 模式
- 对于 AT 命令等文本协议，使用 ASCII 模式

### 3. 性能影响

**ASCII 模式性能**：
- 逐字节检查和转换
- 对于大量数据（>1KB），可能有轻微性能影响
- 对于正常串口通信（<100字节/次），性能足够

**优化建议**：
- 如果接收数据非常频繁（>100次/秒），考虑使用 HEX 模式
- 或者限制接收缓冲区大小（见 Phase 7.38.11 文档）

### 4. 为什么特殊字符显示为 \r \n \t？

**原因**：
- 这些是常见的控制字符
- 显示为转义序列更易读
- 符合编程习惯

**示例**：
```
原始数据：Hello\r\nWorld
显示为：Hello\r\nWorld
而不是：Hello\x0D\x0AWorld
```

## 📝 注意事项

1. **日志格式**：
   - 日志始终显示 HEX 格式
   - 便于调试和分析
   - 不受用户选择影响

2. **ASCII 模式**：
   - 智能显示可打印和不可打印字符
   - 不会出现乱码方块
   - 适合文本协议

3. **HEX 模式**：
   - 所有数据显示为十六进制
   - 适合二进制协议
   - 便于分析数据包

4. **性能考虑**：
   - ASCII 模式逐字节处理
   - 对于正常串口通信，性能足够
   - 大量数据时，优先使用 HEX 模式

5. **用户体验**：
   - 用户可以随时切换 HEX/ASCII 模式
   - 切换后，新数据按新格式显示
   - 旧数据保持原格式
