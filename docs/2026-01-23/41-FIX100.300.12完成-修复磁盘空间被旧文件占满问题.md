## 🔍 根本原因

### 诊断过程

**Step 1: 检查磁盘空间**
```bash
$ ssh pi@192.168.1.8 "df -h"
Filesystem      Size  Used Avail Use% Mounted on
overlay          25G   25G     0 100% /    ⬅️ 100% 满！
```

**发现**: 容器的 overlay 文件系统 100% 满，0 字节可用空间。

**Step 2: 检查空间占用**
```bash
$ ssh pi@192.168.1.8 "du -sh /* 2>/dev/null | sort -h | tail -5"
667M    /var
3.2G    /tmp
4.6G    /usr
17G     /home    ⬅️ /home 占用 17GB
```

**Step 3: 检查 /home/pi 目录**
```bash
$ ssh pi@192.168.1.8 "du -sh /home/pi/* 2>/dev/null | sort -h | tail -10"
187M    /home/pi/belt-control-data
1.5G    /home/pi/resources-extract          ⬅️ 未清理的解压目录
2.9G    /home/pi/resources-20260123-183804.zip
2.9G    /home/pi/resources-20260123-185004.zip
2.9G    /home/pi/resources-20260123-185347.zip
2.9G    /home/pi/resources-20260123-185745.zip
2.9G    /home/pi/resources-20260123-190553.zip
```

**发现**:
- **5 个旧的资源压缩包**，每个 2.9GB，总共 **14.5GB**
- **1 个未清理的解压目录**，1.5GB
- **总浪费空间**: ~16GB

### 问题根源

**部署脚本的清理逻辑缺陷**：

1. **正常流程**（部署成功）：
   ```
   上传 zip → 解压 → 部署 → 清理 zip 和解压目录 ✅
   ```

2. **异常流程**（部署失败）：
   ```
   上传 zip → 解压失败 → 脚本退出 → zip 文件未清理 ❌
   ```

3. **多次重试后**：
   ```
   第1次失败 → 留下 resources-xxx1.zip (2.9GB)
   第2次失败 → 留下 resources-xxx2.zip (2.9GB)
   第3次失败 → 留下 resources-xxx3.zip (2.9GB)
   第4次失败 → 留下 resources-xxx4.zip (2.9GB)
   第5次失败 → 留下 resources-xxx5.zip (2.9GB)
   总计: 14.5GB → 磁盘 100% 满 → 第6次失败
   ```

**恶性循环**：
- 部署失败 → 文件未清理 → 磁盘空间减少
- 再次部署 → 上传新文件 → 磁盘更满
- 继续失败 → 继续累积 → 最终磁盘 100% 满
- 无法部署 → 无法清理 → 死锁

## 🎓 技术要点

### 1. Docker Overlay 文件系统

**特点**：
- Docker 容器使用 overlay 文件系统
- 容器内所有目录（`/tmp`、`/home`、`/var` 等）都在同一个 overlay 上
- 总空间有限（本例中 25GB）

**误区**：
- ❌ 以为 `/tmp` 和 `/home` 是不同分区
- ✅ 实际上都在同一个 overlay 文件系统上

### 2. 清理策略设计

**错误策略**（修复前）：
```
上传 → 处理 → 成功时清理
```
**问题**: 失败时不清理，文件累积

**正确策略**（修复后）：
```
清理旧文件 → 上传 → 处理 → 清理当前文件
```
**优点**:
- 上传前清理 → 确保有足够空间
- 失败时文件残留 → 下次部署自动清理
- 始终只保留1个文件 → 空间可控

### 3. 防御性编程

**原则**: 假设任何操作都可能失败

**实践**:
```bash
# 使用 2>/dev/null 忽略"文件不存在"错误
rm -f /home/$DeviceUser/resources-*.zip 2>/dev/null

# 使用 ; 而非 && 确保后续命令执行
rm -f file1; rm -f file2; echo "Done"
```

### 4. 磁盘空间诊断方法

**快速诊断**：
```bash
# 1. 检查分区使用率
df -h

# 2. 检查目录占用（根目录）
du -sh /* 2>/dev/null | sort -h | tail -10

# 3. 检查目录占用（用户目录）
du -sh /home/user/* 2>/dev/null | sort -h | tail -10

# 4. 查找大文件
find /home -type f -size +1G 2>/dev/null | xargs ls -lh
```

## 📝 经验教训

### 教训 1: 清理逻辑要在操作前，而非操作后

**问题**: 清理放在最后，失败时不执行

**原因**:
- 脚本遇到错误会提前退出
- 清理代码永远不会执行
- 文件累积占满磁盘

**正确做法**:
- 清理放在操作前
- 确保有足够空间再开始
- 失败时下次部署自动清理

### 教训 2: 容器文件系统不等于宿主机文件系统

**误区**: 以为 `/tmp` 和 `/home` 是不同分区

**真相**:
- Docker 容器使用 overlay 文件系统
- 所有目录都在同一个 overlay 上
- 总空间有限（25GB）

**启示**:
- 诊断问题要先看 `df -h`
- 理解容器文件系统结构
- 不要假设有无限空间

### 教训 3: 多次失败会累积问题

**现象**: 第1次失败还好，第5次失败就死锁了

**原因**:
- 每次失败留下 2.9GB 文件
- 5次失败累积 14.5GB
- 磁盘从 60% 满到 100% 满

**启示**:
- 失败后要清理现场
- 不要让问题累积
- 设计要考虑多次失败场景

### 教训 4: 用户说"还是不行"要深入诊断

**用户反馈**: "为什么还是空间不足"

**我的反应**:
- ❌ 不要假设是同样的问题
- ✅ 直接SSH进设备查看
- ✅ 用 `df -h` 和 `du -sh` 诊断

**启示**:
- 用户反馈是最真实的
- 不要依赖猜测
- 直接看数据才能找到真相
