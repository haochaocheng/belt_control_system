## 📋 问题描述

用户在部署资源文件时，虽然文件成功解压，但部署脚本仍然报错 "❌ 部署失败"。

**现象**：
- 解压成功（`resources-extract` 目录存在且包含文件）
- UTF-8 警告出现但被正确处理（退出码 1）
- 部署脚本仍然失败

## 🔍 根本原因

### 诊断过程

**Step 1: 检查解压目录**
```bash
$ ssh pi@192.168.1.8 "ls -la /home/pi/resources-extract/"
drwxr-xr-x 15 pi pi 4096 Jan 23  2026 AUDIO
drwxr-xr-x  5 pi pi 4096 Jan 23  2026 asr_models
drwxr-xr-x  9 pi pi 4096 Jan 23  2026 tts_models
```
✅ 文件已成功解压

**Step 2: 检查目标目录权限**
```bash
$ ssh pi@192.168.1.8 "ls -la /home/pi/belt-control-data/"
drwxr-xr-x 15 pi   pi   4096 Jan 23  2026 audio
drwxr-xr-x  4 root root 4096 Jan 23 10:33 models  ⬅️ 所有者是 root！
```

**发现**: `models` 目录的所有者是 `root:root`，而不是 `pi:pi`

### 问题根源

**部署脚本的操作**：
```bash
# 部署 TTS 模型
rm -rf /home/pi/belt-control-data/models/tts_models  # ❌ 权限不足
mv $EXTRACT_DIR/tts_models /home/pi/belt-control-data/models/tts_models  # ❌ 权限不足
```

**为什么 models 目录是 root 拥有的？**
- 之前的部署脚本在最后使用 `sudo chown` 设置权限
- 但如果部署中途失败，`models` 目录可能已经被 `sudo` 创建
- 下次部署时，普通用户无法删除或修改 root 拥有的目录

**错误链**：
```
第1次部署 → 使用 sudo 创建 models 目录 → 部署失败
第2次部署 → 尝试删除 models/tts_models → 权限不足 → 失败
第3次部署 → 同样失败 → 死锁
```

## 🎓 技术要点

### 1. Linux 文件权限问题

**权限模型**：
```
用户:组  权限  文件/目录
pi:pi   rwx   可以读写执行
root:root rwx  只有 root 可以修改
```

**常见问题**：
- 使用 `sudo` 创建的文件/目录默认属于 `root:root`
- 普通用户无法删除或修改 root 拥有的文件
- 需要 `sudo chown` 修改所有权

### 2. 防御性权限修复

**策略**：
```bash
# 在操作前先修复权限
sudo chown -R user:user /path/to/dir 2>/dev/null || true

# 2>/dev/null - 忽略错误输出（如目录不存在）
# || true - 即使失败也继续执行（不中断脚本）
```

**优点**：
- 确保后续操作有正确权限
- 不会因为权限问题中断脚本
- 自动修复之前的权限错误

### 3. 部署脚本的权限管理

**错误做法**：
```bash
# 只在最后修复权限
mkdir -p /path/dir
mv files /path/dir
sudo chown -R user:user /path/dir  # 太晚了，mv 可能已经失败
```

**正确做法**：
```bash
# 先修复权限，再操作
sudo chown -R user:user /path/dir 2>/dev/null || true
mkdir -p /path/dir
mv files /path/dir
```

### 4. UTF-8 警告 vs 实际错误

**现象**：
```
AUDIO/ZCM/集控停车启动.mp3:  mismatching "local" filename
         continuing with "central" filename version
```

**理解**：
- 这是 **警告**，不是错误
- unzip 退出码 1 = 警告但成功
- 文件实际上已经正确解压
- 不要被警告信息误导

**验证方法**：
```bash
# 检查退出码
unzip file.zip
echo $?  # 0=成功, 1=警告但成功, >1=失败

# 检查文件是否存在
ls -la extracted_dir/
```

## 📝 经验教训

### 教训 1: 警告不等于错误

**问题**: 看到 UTF-8 警告就以为部署失败

**真相**:
- unzip 警告 ≠ 失败
- 退出码 1 = 警告但成功
- 文件实际上已经正确解压

**启示**:
- 检查实际结果，不要只看警告
- 理解工具的退出码含义
- 验证文件是否真的存在

### 教训 2: sudo 操作要谨慎

**问题**: 使用 sudo 创建的目录属于 root

**后果**:
- 普通用户无法修改
- 下次部署失败
- 需要手动修复

**正确做法**:
- 尽量避免使用 sudo 创建用户文件
- 如果必须使用，立即 chown 回用户
- 或者在操作前先修复权限

### 教训 3: 部署脚本要有自愈能力

**问题**: 之前的失败导致后续失败

**原因**:
- 权限错误累积
- 没有自动修复机制
- 需要手动干预

**正确做法**:
- 操作前先修复已知问题
- 使用 `|| true` 防止中断
- 设计要考虑失败恢复

### 教训 4: 诊断要看实际状态

**用户反馈**: "部署失败"

**我的诊断**:
- ❌ 不要假设是同样的问题
- ✅ 检查解压目录是否存在
- ✅ 检查目标目录权限
- ✅ 找到真正的失败原因

**启示**:
- 每次失败可能是不同原因
- 要看实际文件和权限状态
- 不要依赖错误信息猜测
