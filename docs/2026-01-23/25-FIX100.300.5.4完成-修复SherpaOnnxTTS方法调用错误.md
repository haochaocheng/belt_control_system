## 🎓 技术要点

### 1. SherpaOnnxTTS API 设计模式

**设计理念**: 参数设置与合成分离

**优点**:
- 参数可以独立设置，不需要每次合成都传递
- 参数在多次合成中保持有效
- 代码更清晰，职责分离

**使用流程**:
```cpp
// 1. 初始化时或配置变化时设置参数
tts->setSpeakerId(0);
tts->setRate(1.0);
tts->setVolume(0.8);

// 2. 多次合成时只需传递文本和输出路径
tts->synthesizeToFile("文本1", "/tmp/test1.wav");
tts->synthesizeToFile("文本2", "/tmp/test2.wav");
tts->synthesizeToFile("文本3", "/tmp/test3.wav");
```

### 2. 为什么不是 generateSpeech()?

**原因分析**:
1. **命名一致性**: 类中已有 `synthesizeToFile()` 方法，保持命名风格统一
2. **参数管理**: 说话人ID、语速、音量是状态属性，不是每次合成的参数
3. **代码复用**: 参数设置后可用于多次合成，避免重复传递

### 3. 测试TTS的完整流程

**流程图**:
```
用户点击测试按钮
    ↓
QML 调用 testTts(text)
    ↓
读取 Test 场景配置
    ↓
设置 TTS 参数
  - setSpeakerId(speakerId)
  - setRate(rate)
  - setVolume(volume)
    ↓
调用 synthesizeToFile(text, path)
    ↓
生成 /tmp/tts_test.wav
    ↓
发送 Toast 提示
```

**关键点**:
- 使用 Test 场景配置（不影响其他场景）
- 参数设置在合成前完成
- 生成临时文件用于测试
- 通过 errorOccurred 信号显示结果

## 📝 经验教训

### 教训 1: 不要假设 API 方法名

**问题**: 我在实现 FIX 100.300.5.3 时假设了 `generateSpeech()` 方法存在

**正确做法**:
1. 先查看头文件确认可用方法
2. 理解 API 设计模式
3. 使用正确的方法调用

### 教训 2: 理解参数设置模式

**SherpaOnnxTTS 使用状态模式**:
- 参数通过 setter 方法设置
- 参数在对象中保持状态
- 合成方法只需要文本和输出路径

**不是函数式模式**:
- 不是每次调用都传递所有参数
- 参数不是临时的，而是持久的

### 教训 3: 编译错误优先修复

**流程**:
1. 遇到编译错误 → 立即查看头文件
2. 确认正确的 API → 修复调用代码
