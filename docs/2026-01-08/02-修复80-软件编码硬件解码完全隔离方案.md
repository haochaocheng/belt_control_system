# 修复 80：软件编码+硬件解码完全隔离方案

## 背景

**用户架构需求**：
- ✅ 编码器：libx264（软件）
- ✅ 解码器：h264_rkmpp（硬件）

**修复78失败**：虽然DRM render node创建成功，但立即崩溃（exit 139）

## 修复80方案

### 1. 核心策略

**完全隔离编码器和解码器的DRM上下文**：

```c
// 编码器：强制hw_device_ctx为NULL
if (ff->enc && pj_ansi_strstr(ff->enc->name, "libx264") != NULL) {
    ff->enc_ctx->hw_device_ctx = NULL;  // 完全不访问DRM资源
}

// 解码器：独立使用DRM render node
av_hwdevice_ctx_create(&ctx->hw_device_ctx, AV_HWDEVICE_TYPE_RKMPP,
                       "/dev/dri/renderD128", NULL, 0);
```

### 2. 关键修改

#### 修改1：解码器hwdevice（Line 2073-2095）

```c
#ifdef USE_HARDWARE_DECODER
    if (ff->dec && (pj_ansi_strstr(ff->dec->name, "rkmpp") != NULL)) {
        int ret;

        // 使用 DRM render node（共享，不独占）
        ret = av_hwdevice_ctx_create(&ctx->hw_device_ctx, AV_HWDEVICE_TYPE_RKMPP,
                                     "/dev/dri/renderD128", NULL, 0);
        if (ret < 0) {
            // 失败日志 + 回退软件解码
            ctx->get_format = pjmedia_ffmpeg_get_format;
        } else {
            // 成功：I420 output, RGA3硬件转换到NV12
            ctx->pix_fmt = AV_PIX_FMT_YUV420P;
            ctx->get_format = pjmedia_ffmpeg_get_format;
        }
    }
#endif
```

#### 修改2：编码器DRM隔离（Line 2223-2230）

```c
// 强制设置hw_device_ctx为NULL，完全隔离编码器和解码器的DRM上下文
if (ff->enc && (pj_ansi_strstr(ff->enc->name, "libx264") != NULL ||
                pj_ansi_strstr(ff->enc->name, "x264") != NULL)) {
    ff->enc_ctx->hw_device_ctx = NULL;
    PJ_LOG(...);  // 日志记录
}
```

### 3. 与修复78的区别

| 项目 | 修复78 | 修复80 |
|------|--------|--------|
| DRM设备 | render node | render node ✅ |
| 解码器hwdevice | 创建 | 创建 ✅ |
| 编码器隔离 | **未明确设置NULL** | **强制设置NULL** ✅ |
| 诊断日志 | 基本 | 增强 ✅ |

**关键差异**：修复78没有明确确保编码器的hw_device_ctx为NULL，可能导致FFmpeg在打开编码器时尝试访问DRM资源（即使是软件编码器）。

### 4. 理论依据

#### libx264应该完全无DRM访问

```c
// libx264是纯软件编码器，不应该访问任何硬件资源
// 但FFmpeg的avcodec_open2()可能包含硬件检测代码
// 通过强制设置hw_device_ctx = NULL，确保不会尝试任何DRM访问
```

#### RKMPP解码器独立DRM上下文

```c
// RKMPP解码器使用独立的DRM render node
// render node是共享的，不会与其他进程冲突
// 理论上与libx264（无DRM访问）不应该有任何冲突
```

### 6. 如果仍然崩溃

#### 可能原因A：RKMPP解码器内部硬编码DRM路径
```c
// rkmppdec.c 中可能的代码：
drm_fd = open("/dev/dri/card0", ...);  // 如果硬编码card0
// 而不是使用hwdevice中传递的renderD128
```

**验证方法**：检查ffmpeg-rockchip源码中`libavcodec/rkmppdec.c`的DRM设备打开逻辑

#### 可能原因B：MPP驱动层全局资源冲突
```c
// 即使DRM层面隔离完美
// /dev/mpp_service可能仍然有全局资源冲突
// 这是内核驱动层面的问题，无法在应用层解决
```

**验证方法**：
```bash
# 检查MPP服务的打开情况
lsof | grep "mpp_service"

# 如果显示被占用，说明是驱动层问题
```
