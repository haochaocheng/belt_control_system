# 快速调试方案 - 避免全量编译

**日期**: 2026-01-08 17:00
**目的**: 提供快速验证方法，避免每次修改都全量编译

## 🚀 方案 1：GDB 容器内实时调试（最推荐）⭐

### 优势
- ✅ 无需重新编译
- ✅ 实时查看崩溃位置、变量、堆栈
- ✅ 可以设置断点单步调试
- ✅ 准确定位问题

### 实施步骤

#### Step 1: 在设备 188 上启动容器并附加 GDB

```bash
# SSH 连接到设备
ssh root@192.168.10.188

# 查找容器内的主进程 PID
docker exec belt-control-latest ps aux | grep belt_control_system

# 进入容器
docker exec -it belt-control-latest bash

# 使用 GDB 附加到进程（假设 PID 是 1）
gdb -p 1

# GDB 命令
(gdb) set logging on           # 启用日志记录
(gdb) set pagination off       # 禁用分页
(gdb) continue                 # 继续运行

# 崩溃时自动停止，然后执行：
(gdb) bt full                  # 查看完整堆栈
(gdb) info registers           # 查看寄存器
(gdb) info locals              # 查看局部变量
(gdb) frame 0                  # 切换到崩溃帧
(gdb) list                     # 查看崩溃位置代码
```

#### Step 2: 设置断点精确定位

```bash
# 在 FFmpeg 解码器打开处设置断点
(gdb) break ffmpeg_vid_codecs.c:2107    # avcodec_open2 调用处
(gdb) break avcodec_open2                # FFmpeg 内部函数
(gdb) continue

# 到达断点时：
(gdb) print ff->dec->name      # 查看解码器名称
(gdb) print ff->dec_ctx        # 查看解码器 context
(gdb) print ctx->hw_device_ctx # 查看硬件设备 context
(gdb) step                     # 单步进入 avcodec_open2
```

## 🔥 方案 2：启用 Core Dump（查看崩溃现场）

### 优势
- ✅ 崩溃后保留完整内存状态
- ✅ 可以离线分析
- ✅ 包含所有变量、堆栈信息

### 实施步骤

#### Step 1: 启用 Core Dump

```bash
# 在设备上执行
ssh root@192.168.10.188

# 启用 core dump
docker exec belt-control-latest bash -c 'ulimit -c unlimited && echo "/tmp/core.%e.%p" > /proc/sys/kernel/core_pattern'

# 重启容器触发崩溃
docker restart belt-control-latest
```

#### Step 2: 分析 Core Dump

```bash
# 查找 core 文件
docker exec belt-control-latest ls -lh /tmp/core.*

# 使用 GDB 分析
docker exec -it belt-control-latest bash
gdb /app/belt_control_system /tmp/core.belt_control_system.XXX

# GDB 命令
(gdb) bt full              # 完整堆栈
(gdb) info registers       # 寄存器状态
(gdb) info threads         # 所有线程
(gdb) thread apply all bt  # 所有线程堆栈
```

## ⚡ 方案 3：增量编译部署（快速）

### 优势
- ✅ 只编译修改的 PJSIP 库（1-2分钟）
- ✅ 直接替换容器内的 .so 文件
- ✅ 跳过应用程序编译和 Docker 镜像构建

### 实施步骤

#### Step 1: 只编译 PJSIP 库

```powershell
# 删除 PJSIP 静态库触发重新编译
Remove-Item docker\rk3588\rk3588-libs\lib\libpjmedia-codec*.a -Force

# 只运行 PJSIP 编译步骤（修改 build-ubuntu24-apt.ps1 临时跳过其他步骤）
.\build-ubuntu24-apt.ps1 188 -StepOnly PJSIP
```

#### Step 2: 提取动态库并部署

```powershell
# 从编译容器提取 PJSIP 动态库
docker cp pjsip-builder-persistent:/workspace/pjsip-build/lib/*.so docker/rk3588/lib/

# 替换设备容器内的库
scp docker/rk3588/lib/libpjmedia-codec.so.2 root@192.168.10.188:/tmp/
ssh root@192.168.10.188 "docker cp /tmp/libpjmedia-codec.so.2 belt-control-latest:/app/lib/"

# 重启容器
ssh root@192.168.10.188 "docker restart belt-control-latest"
```

## 🔬 方案 4：详细日志 + 二分法定位

### 优势
- ✅ 无需 GDB
- ✅ 快速定位崩溃的准确行号

### 实施方法

在每个可能崩溃的操作后立即输出日志，例如：

```c
PJ_LOG(1,(THIS_FILE, "🔍 [DEBUG] Checkpoint 1"));
ctx->get_format = pjmedia_ffmpeg_get_format;
PJ_LOG(1,(THIS_FILE, "🔍 [DEBUG] Checkpoint 2 - get_format assigned"));

dec_err = avcodec_open2(ff->dec_ctx, ff->dec, NULL);
PJ_LOG(1,(THIS_FILE, "🔍 [DEBUG] Checkpoint 3 - avcodec_open2 called"));
```

通过日志输出判断崩溃在哪两个 checkpoint 之间。

## 💡 推荐调试流程

### 立即执行（5分钟内验证）

1. **SSH 连接设备**：`ssh root@192.168.10.188`
2. **进入容器**：`docker exec -it belt-control-latest bash`
3. **启动 GDB**：`gdb -p 1`（假设主进程 PID=1）
4. **继续运行**：`(gdb) continue`
5. **等待崩溃**：miniSIP 拨打视频通话
6. **查看堆栈**：`(gdb) bt full`

### 定位崩溃位置

GDB 堆栈会显示类似：
```
#0  0x00007f8c12345678 in avcodec_open2 () from /app/lib/libavcodec.so.60
#1  0x00000055a1234567 in open_ffmpeg_codec () at ffmpeg_vid_codecs.c:2107
#2  ...
```

**精确到行号** → 立即知道是 `avcodec_open2` 内部崩溃还是之前崩溃
