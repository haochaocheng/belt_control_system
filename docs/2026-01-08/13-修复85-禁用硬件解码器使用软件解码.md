## 🔍 根本原因分析

### RKMPP 解码器的硬编码行为

**结论**：RKMPP 解码器**强制输出 DRM_PRIME 格式**，无论是否创建 hwdevice。

**证据链**：

1. **Fix 80-82**：创建 hwdevice → 输出 DRM_PRIME (format 179) ❌
2. **Fix 83**：尝试 `av_opt_set("output_format", "nv12")` → 失败 (ret=-1414549496) ❌
3. **Fix 84**：移除 hwdevice → **仍然输出 DRM_PRIME (format 179)** ❌

**技术分析**：

| 项目 | Fix 84 测试 | 预期 | 实际 |
|------|------------|------|------|
| **hwdevice 创建** | ❌ 不创建 | `get_format` 被调用 | ❌ 未被调用 |
| **hwdevice 指针** | `(nil)` | NULL | ✅ NULL |
| **get_format 回调** | 已设置 | 正常调用 | ❌ **从未调用** |
| **解码器输出格式** | 179 | 23 (NV12) 或 0 (I420) | ❌ **179 (DRM_PRIME)** |

**为什么 get_format 没被调用**：
- RKMPP 解码器驱动硬编码输出格式为 DRM_PRIME
- 不经过 FFmpeg 的格式协商机制
- **完全跳过 `get_format` 回调**

**RKMPP 解码器设计行为**（无法改变）：
```c
// RKMPP 解码器内部逻辑（我们无法修改）
int rkmpp_decoder_init() {
    // 硬编码输出格式
    ctx->pix_fmt = AV_PIX_FMT_DRM_PRIME;  // format 179

    // 不调用 get_format 回调
    // ctx->get_format() 被完全忽略

    return 0;
}
```

**为什么这样设计**：
- RKMPP 设计目标：**最高性能**（VPU → GPU 内存，零拷贝）
- 适用场景：GPU 渲染管线（OpenGL/Vulkan 直接访问）
- **不适用**：软件处理管线（PJSIP RemoteVideoManager）

---

## ✅ Fix 85 解决方案

### 核心思路

**禁用硬件解码器，使用纯软件解码器（h264）**

RKMPP 硬件解码器无法满足需求，我们改用纯软件解码器：
- ✅ 输出系统内存格式（NV12/I420）
- ✅ RemoteVideoManager 可以访问
- ✅ 兼容性最好，100% 可靠
- ⚠️ CPU 占用略高（~25-35%），但可接受

### 修改方案

**禁用 `USE_HARDWARE_DECODER` 宏定义**

### 教训

**RKMPP 硬件解码器的限制**：
1. **强制 DRM_PRIME 输出**（无法通过 FFmpeg API 改变）
2. **不调用 get_format 回调**（硬编码格式）
3. **只适用于 GPU 渲染管线**（不适用于软件处理）

**正确的技术选择**：
- 如果需要 GPU 渲染（OpenGL/Vulkan）→ 使用 RKMPP 硬件解码器
- 如果需要软件处理（PJSIP/FFmpeg）→ **必须使用软件解码器**
