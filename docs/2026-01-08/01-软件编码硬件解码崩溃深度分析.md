# 软件编码+硬件解码崩溃深度分析

## 背景

**用户架构**：
- 编码器：libx264（软件）✅ 已正常工作
- 解码器：h264_rkmpp（硬件）❌ 需要修复

**问题**：修复78使用DRM render node后仍然崩溃（exit 139）

## 崩溃时间线（voip.md Line 726-730）

```
11:11:23.333  ✅ [FIX 78] Detected RKMPP decoder: h264_rkmpp
11:11:23.333     Strategy: Use DRM Render Node to avoid encoder/decoder conflict
11:11:23.334     ✅ RKMPP hwdevice created using DRM render node (/dev/dri/renderD128)
11:11:23.334     ✅ DRM render node is SHARED (no conflict ← 日志被截断
Application exited with code: 139  ← 仅1毫秒后崩溃
```

## 关键观察

### 1. hwdevice创建成功
- `av_hwdevice_ctx_create()` 返回成功（ret >= 0）
- DRM render node `/dev/dri/renderD128` 打开成功
- 说明DRM设备层面没有权限问题

### 2. 崩溃发生在avcodec_open2()
从时间线来看（11:11:23.334），崩溃发生在hwdevice创建后立即。根据代码流程：

```c
// Line ~2051 (修复78代码，已被替换)
ret = av_hwdevice_ctx_create(&ctx->hw_device_ctx, AV_HWDEVICE_TYPE_RKMPP,
                             "/dev/dri/renderD128", NULL, 0);
if (ret >= 0) {
    PJ_LOG(...); // 成功日志
    ctx->pix_fmt = AV_PIX_FMT_YUV420P;
    ctx->get_format = pjmedia_ffmpeg_get_format;
}
// 函数返回后，调用 avcodec_open2(ff->dec_ctx, ff->dec, NULL) - Line 2445
```

**结论**：崩溃发生在 `avcodec_open2(ff->dec_ctx, ff->dec, NULL)` 内部。

## 可能原因分析

### 原因A：RKMPP解码器内部硬编码DRM路径

**假设**：
- 我们通过`av_hwdevice_ctx_create()`传递了`/dev/dri/renderD128`
- 但RKMPP解码器内部代码可能硬编码访问`/dev/dri/card0`
- 导致权限冲突或资源竞争

**验证方法**：
检查ffmpeg-rockchip源码中RKMPP解码器的DRM设备打开逻辑。

**相关文件**：
- `E:\2025\3_gongkongji\NewFolder\ffmpeg-rk-temp\ffmpeg-rockchip-master\libavcodec\rkmppdec.c`

### 原因B：libx264编码器占用了DRM资源

**假设**：
- libx264虽然是软件编码器，但`avcodec_open2()`可能包含硬件检测代码
- 检测逻辑中尝试打开`/dev/dri/card0`（DRM master）
- 导致后续RKMPP解码器无法访问（即使用render node）

**验证方法**：
1. 检查libx264打开后是否有DRM文件描述符
   ```bash
   lsof | grep "libx264" | grep "/dev/dri"
   ```
2. 调整打开顺序：先打开解码器，后打开编码器

### 原因C：ctx->hw_device_ctx设置后的副作用

**假设**：
- `av_hwdevice_ctx_create()` 成功
- 但设置`ctx->hw_device_ctx`后，FFmpeg内部状态变化
- `avcodec_open2()`时触发某些RKMPP特定的初始化逻辑崩溃

**验证方法**：
检查RKMPP解码器的`init()`函数中对`hw_device_ctx`的处理。

### 原因D：MPP驱动层冲突（即使软件编码）

**假设**：
- 虽然编码器是libx264（软件），但由于PJSIP初始化时检测到RKMPP硬件
- 某些全局MPP驱动资源可能已被占用
- 导致后续RKMPP解码器无法访问`/dev/mpp_service`

**验证方法**：
检查`/dev/mpp_service`的打开情况：
```bash
lsof | grep "mpp_service"
```

## 下一步调试方案

### 方案1：源码级调试
检查RKMPP解码器源码中的DRM设备打开逻辑：
```c
// rkmppdec.c 中可能的代码
int rkmpp_init() {
    // 关键：这里打开的是哪个DRM设备？
    drm_fd = open("/dev/dri/card0", ...);  // 如果是硬编码card0，就解释了崩溃
    // 还是使用 hw_device_ctx 中的设备？
}
```

### 方案2：调整初始化顺序
尝试先打开解码器，后打开编码器：
```c
// 当前顺序（Line 2177-2460）：
1. 打开编码器（libx264）
2. 打开解码器（RKMPP）← 崩溃

// 尝试顺序：
1. 打开解码器（RKMPP）
2. 打开编码器（libx264）
```

### 方案3：检查libx264的DRM访问
添加日志检测libx264是否尝试访问DRM：
```c
// 在编码器打开前后添加
PJ_LOG(1,(THIS_FILE, "Before encoder open: checking /dev/dri/* status"));
err = AVCODEC_OPEN(ff->enc_ctx, ff->enc);
PJ_LOG(1,(THIS_FILE, "After encoder open: err=%d", err));
system("lsof | grep /dev/dri");  // 检查DRM文件描述符
```

### 方案4：完全隔离DRM上下文
为编码器和解码器创建完全独立的DRM contexts：
```c
// 编码器：不使用任何DRM资源（纯软件）
ff->enc_ctx->hw_device_ctx = NULL;

// 解码器：独立的DRM render node
av_hwdevice_ctx_create(&ff->dec_ctx->hw_device_ctx,
                       AV_HWDEVICE_TYPE_RKMPP,
                       "/dev/dri/renderD128", NULL, 0);
```
