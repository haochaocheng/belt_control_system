## 方案 A：Core Dump 分析（最推荐）⭐⭐⭐⭐⭐

### 原理
程序收到 SIGSEGV 信号时，Linux 内核自动将进程内存镜像保存为 core 文件。即使容器停止，core 文件仍存在，可以用 GDB 事后分析。

### 操作步骤

#### Step 1：设置 Core Dump（崩溃前执行一次）
```powershell
.\scripts\2026-01-09\06-setup-core-dump.ps1 188
```

**脚本功能**：
- 启用 core dump：`ulimit -c unlimited`
- 设置 core 文件路径：`/tmp/core.%e.%p`
- 清理旧的 core 文件

**验证**：
```bash
# SSH 到设备
ssh linaro@192.168.10.188
docker exec belt-control-app bash -c 'ulimit -c'
# 应显示：unlimited
```

#### Step 2：触发崩溃
- 启动程序
- 进行视频通话测试
- 等待程序崩溃
- **容器会停止，这是正常的**

#### Step 3：分析 Core Dump（崩溃后执行）
```powershell
.\scripts\2026-01-09\07-analyze-core-dump.ps1 188
```

**脚本功能**：
- 查找最新的 core 文件
- 用 GDB 自动分析：
  - `bt` - 崩溃堆栈
  - `info registers` - 寄存器状态
  - `info locals` - 局部变量
  - `thread apply all bt` - 所有线程堆栈
- 保存分析结果到 `docs/log/core_dump_*.log`

### 优势
✅ **可靠性最高**：core 文件不会丢失
✅ **信息最完整**：包含崩溃时的内存快照
✅ **无需实时操作**：事后分析
✅ **容器停止不影响**：重启容器后仍可分析

### 示例输出
```
===============================================
GDB 分析结果
===============================================

Core was generated by `/app/belt_control_system'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x00007f2180c3d4 in PJ_LOG (level=3, ...) at ffmpeg_vid_codecs.c:2885
#1  0x00007f2180c850 in ffmpeg_codec_encode (...) at ffmpeg_vid_codecs.c:2890
#2  0x00007f2181f234 in pjmedia_vid_codec_encode (...)

Local variables:
  avframe = {data = {0x7f2171c558, 0x7f2176d558, 0x7f21781958, ...}}
  ff = 0x5592c1dd10
```

## 方案 B：Strace 系统调用追踪 ⭐⭐⭐⭐

### 原理
使用 `strace` 记录程序的所有系统调用。即使程序崩溃，日志文件已记录崩溃前的操作序列。

### 操作步骤

#### Step 1：设置 Strace（崩溃前执行）
```powershell
.\scripts\2026-01-09\08-setup-strace.ps1 188
```

**脚本功能**：
- 安装 strace
- 创建 strace 启动脚本
- 停止当前容器

#### Step 2：手动启动程序
```bash
# SSH 到设备
ssh linaro@192.168.10.188

# 启动容器
docker start belt-control-app

# 使用 strace 运行程序（会阻塞终端，这是正常的）
docker exec belt-control-app /tmp/run_strace.sh
```

#### Step 3：触发崩溃
- 在另一个终端进行视频通话测试
- 等待程序崩溃
- strace 会记录所有系统调用到 `/tmp/strace.log`

#### Step 4：下载和分析日志
```powershell
.\scripts\2026-01-09\09-download-strace-log.ps1 188
```

### 优势
✅ **无需 GDB**：直接使用 strace
✅ **系统调用序列**：看到崩溃前的最后操作
✅ **找到触发点**：最后的 write()、mmap() 等

### 日志示例
```
12:05:43.593 write(2, "    Plane[0]: linesize=768, data=0x7f2171c558\n", 46) = 46
12:05:43.593 write(2, "    Plane[1]: linesize=384, data=0x7f2176d558\n", 46) = 46
12:05:43.593 write(2, "    Plane[2]: linesize=384, data=0x7f21781958\n", 46) = 46
12:05:43.594 --- SIGSEGV {si_signo=SIGSEGV, si_code=SEGV_MAPERR, si_addr=0x7f21781958} ---
12:05:43.594 +++ killed by SIGSEGV (core dumped) +++
```

**分析**：
- 最后的 write() 是日志打印 Plane[2]
- 紧接着收到 SIGSEGV 信号
- 访问地址 `0x7f21781958` 导致段错误

## 方案 C：实时 GDB 调试 ⭐⭐⭐

### 原理
在 GDB 中运行程序，崩溃时 GDB 捕获信号，保持在调试状态。

### 限制
❌ **需要交互操作**：无法自动化
❌ **容器必须运行**：崩溃后容器会停止
❌ **崩溃太快**：可能来不及输入命令

### 操作步骤

#### 方式 1：手动 GDB（适合可重现的崩溃）
```bash
ssh -t linaro@192.168.10.188 "docker exec -it belt-control-app gdb /app/belt_control_system"

# 在 GDB 中
(gdb) run

# [等待程序启动，触发视频通话]
# [程序崩溃]

(gdb) bt           # 查看堆栈
(gdb) info locals  # 查看变量
(gdb) p avframe    # 检查 avframe
(gdb) quit
```

#### 方式 2：修改容器启动命令
修改 Docker Compose 或启动脚本，让程序在 GDB 中启动：
```yaml
command: ["gdb", "-ex", "run", "-ex", "bt", "-ex", "quit", "/app/belt_control_system"]
```

## 🔧 故障排除

### Q1：Core 文件未生成

**检查 1**：ulimit 设置
```bash
docker exec belt-control-app bash -c 'ulimit -c'
# 应该是 unlimited
```

**检查 2**：core_pattern 设置
```bash
docker exec belt-control-app cat /proc/sys/kernel/core_pattern
# 应该是 /tmp/core.%e.%p
```

**检查 3**：磁盘空间
```bash
docker exec belt-control-app df -h /tmp
# 确保有足够空间
```

### Q2：GDB 显示 "No debugging symbols"

**原因**：Release 模式编译，未包含调试符号

**解决**：
- 仍然可以看到堆栈地址和函数名
- 使用 `info symbol <地址>` 查看函数
- 使用 `disassemble` 查看汇编代码

### Q3：Strace 日志太大

**优化**：只记录特定系统调用
```bash
# 只记录内存和信号相关
strace -e trace=memory,signal -f -o /tmp/strace.log /app/belt_control_system
```
