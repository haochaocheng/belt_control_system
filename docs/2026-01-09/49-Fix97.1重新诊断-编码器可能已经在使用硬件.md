## 📊 RKMPP 编码器工作原理

### 输入格式 vs 内部处理

根据 [文档 46](46-Fix97.1诊断-编码器日志误导性问题.md) 的分析：

```
输入：I420 软件帧（pix_fmt = 0）
  ↓
RKMPP 编码器接收帧
  ↓
检查 hw_device_ctx
  ↓ （如果 hw_device_ctx 存在）
内部分配 r->hwframe（DRM_PRIME buffer）
  ↓
自动转换 I420 → DRM_PRIME（使用 RGA 硬件加速）
  ↓
硬件编码器处理 DRM_PRIME 帧
  ↓
输出：H.264 编码数据
```

**关键**：
- `pix_fmt=0` (I420) 是**输入格式**
- RKMPP 编码器**内部**会自动转换为 DRM_PRIME 并使用硬件加速
- 不需要我们手动转换格式

### 验证方法

**如何确认编码器是否使用硬件加速**:

| 方法 | 软件编码 | 硬件编码 | 命令 |
|------|---------|---------|------|
| **CPU 使用率** | 60-80% | 10-15% | `top -p $(pgrep belt_control)` |
| **VPU 负载** | 无 | 80-90% | `cat /sys/kernel/debug/mpp_service/session` |
| **编码延迟** | 30-50ms | 5-10ms | 查看日志时间戳 |

## 🔍 Line 776-777 错误的来源

### 错误信息分析

```
Line 776: glx: failed to create dri3 screen
Line 777: failed to load driver: rockchip
```

**关键词**:
- `glx`: OpenGL X Window System 扩展
- `dri3`: Direct Rendering Infrastructure 3
- 这些通常用于 **GPU 图形渲染**，不是编解码器

### 可能的错误来源

#### 可能性 1: Qt 图形系统
- Qt 应用启动时尝试初始化 OpenGL 渲染
- 在 EGLFS 模式下，GLX 不可用（正常）
- 错误被输出到 stderr，混入 FFmpeg 日志

#### 可能性 2: Mesa/DRI 驱动加载
- FFmpeg 内部某些组件尝试加载 Mesa DRI 驱动
- DRI3 不可用，回退到其他渲染路径
- **不影响 RKMPP 编码器**（RKMPP 不依赖 Mesa）

#### 可能性 3: FFmpeg 内部探测
- FFmpeg 内部可能尝试探测可用的硬件加速方式
- 探测 OpenGL/VAAPI/VDPAU 等失败
- 但 RKMPP 路径（通过 hw_device_ctx）是独立的

### 验证假设

**检查错误来源**:
```bash
# 在容器内运行
LIBGL_DEBUG=verbose /app/bin/belt_control_system 2>&1 | grep -i "glx\|dri"
```

**如果是 Qt 图形系统**:
```bash
# 设置 Qt 环境变量禁用 OpenGL
docker run -e QT_QPA_PLATFORM=eglfs -e QT_OPENGL=software ...
```
