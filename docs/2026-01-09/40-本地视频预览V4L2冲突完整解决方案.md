# 本地视频预览 V4L2 冲突完整解决方案（Fix 69）

**日期**: 2026-01-09 16:30
**问题**: Linux V4L2 不支持多进程访问摄像头
**状态**: ✅ **已解决 - 使用视频会议桥复用 Capture Port**

---

## 🎯 问题背景

### 用户需求

用户在视频通话过程中，需要**同时显示本地摄像头预览**：
- ✅ 对方视频窗口（RemoteVideoManager）
- ✅ 本地视频预览（LocalVideoManager）

### 平台差异

| 平台 | 摄像头访问机制 | 多路访问支持 | 本地预览 |
|------|--------------|------------|---------|
| **Windows** | DirectShow / MediaFoundation | ✅ 支持 | ✅ 正常 |
| **Linux** | Video4Linux2 (V4L2) | ❌ **单进程独占** | ❌ 冲突 |

---

## 🔍 V4L2 冲突根本原因

### Linux V4L2 架构

```
┌──────────────────────────────┐
│   用户空间应用程序             │
│  ┌─────────┐   ┌─────────┐   │
│  │ PJSIP   │   │  Qt     │   │
│  │ (通话)  │   │ (预览)  │   │
│  └────┬────┘   └────┬────┘   │
└───────┼─────────────┼─────────┘
        │ open()      │ open()
        ↓             ↓
┌────────────────────────────────┐
│      内核空间 (V4L2 驱动)       │
│   /dev/video0 (摄像头设备)     │
│                                │
│   ❌ 只允许一个进程打开！       │
│   第二次 open() 返回 EBUSY    │
└────────────────────────────────┘
```

**关键限制**:
- V4L2 驱动设计为**单进程独占访问**
- 第一个进程打开 `/dev/video0` 成功
- 第二个进程尝试打开 → **"Device or resource busy" (EBUSY)**

### 实际场景冲突

**通话中启动本地预览**:
```cpp
// Step 1: PJSIP 通话时自动打开摄像头（成功）
pjsua_call_make_call(...)
  → pjmedia_vid_stream_create(...)
    → pjmedia_vid_capture_create(...)
      → open("/dev/video0") ✅ 成功

// Step 2: 用户点击"打开本地预览"（失败）
LocalVideoManager::startPreview()
  → pjsua_vid_preview_start(...)
    → pjmedia_vid_capture_create(...)
      → open("/dev/video0") ❌ EBUSY（设备繁忙）
```

**错误日志**:
```
❌ LocalVideoManager: Failed to start preview, status: -2147483647
❌ pjmedia_vid_dev_stream_start: Device or resource busy
```

## 🎯 解决方案：视频会议桥架构（Fix 69）

### 核心思路

**单次打开，多路分发**：
- 摄像头只打开一次（PJSIP 通话时）
- 使用 PJSIP 视频会议桥（Vid Tee）将数据分发到多个消费者
- 本地预览不重新打开摄像头，而是**连接到现有的 Capture Port**

### 完整架构

```
┌─────────────────────────────────────────────┐
│              用户空间应用                    │
│                                             │
│  ┌──────────────────────────────────────┐  │
│  │   PJSIP 视频会议桥 (Vid Conference)  │  │
│  │                                      │  │
│  │   ┌────────────────────────┐        │  │
│  │   │   Vid Tee (Splitter)   │        │  │
│  │   │   一对多数据分发        │        │  │
│  │   └──────────┬──────────┬──┘        │  │
│  │              │          │            │  │
│  │   ┌──────────↓─────┐ ┌─↓──────────┐ │  │
│  │   │ Encoder Port   │ │ Renderer   │ │  │
│  │   │ (RTP 发送)     │ │ Port       │ │  │
│  │   │ 对方看到的视频 │ │ (本地预览) │ │  │
│  │   └────────────────┘ └────────────┘ │  │
│  │              ↑                       │  │
│  │   ┌──────────┴─────────┐            │  │
│  │   │   Capture Port     │            │  │
│  │   │   摄像头捕获端口    │            │  │
│  │   └──────────┬─────────┘            │  │
│  └──────────────┼──────────────────────┘  │
└─────────────────┼───────────────────────────┘
                  │ open() 一次！
┌─────────────────↓───────────────────────────┐
│           内核空间 (V4L2)                    │
│      /dev/video0 (摄像头设备)                │
│      ✅ 只打开一次，多路复用                 │
└─────────────────────────────────────────────┘
```

### 数据流详解

**通话 + 本地预览同时运行**:
```
Camera (硬件) → V4L2 驱动 → Capture Port (PJSIP)
                               ↓
                          Vid Conference Bridge (Tee)
                               ↓
                    ┌──────────┴──────────┐
                    ↓                     ↓
              Encoder Port          Renderer Port
                    ↓                     ↓
               H.264 编码            I420 原始帧
                    ↓                     ↓
              RTP 网络发送          本地 QVideoSink
                    ↓                     ↓
              对方屏幕显示          本地预览窗口
```

### 实施步骤

#### Step 1: 检测活跃通话的 Capture Slot

**函数**: `findActiveCallCaptureSlot(int capDevId)` (Line 676-731)

```cpp
pjsua_conf_port_id LocalVideoManager::findActiveCallCaptureSlot(int capDevId)
{
    pjsua_call_id call_ids[PJSUA_MAX_CALLS];
    unsigned call_count = PJSUA_MAX_CALLS;

    // 获取所有活跃通话
    pj_status_t status = pjsua_enum_calls(call_ids, &call_count);
    if (status != PJ_SUCCESS || call_count == 0) {
        return PJSUA_INVALID_ID;  // 无活跃通话
    }

    // 遍历通话，查找视频媒体
    for (unsigned i = 0; i < call_count; ++i) {
        pjsua_call_info ci;
        status = pjsua_call_get_info(call_ids[i], &ci);

        for (unsigned med_idx = 0; med_idx < ci.media_cnt; ++med_idx) {
            const pjsua_call_media_info &mi = ci.media[med_idx];

            // 找到视频媒体且编码器端口有效
            if (mi.type == PJMEDIA_TYPE_VIDEO &&
                mi.stream.vid.enc_slot != PJSUA_INVALID_ID) {
                // ✅ 返回编码器端口（连接到摄像头的端口）
                return mi.stream.vid.enc_slot;
            }
        }
    }

    return PJSUA_INVALID_ID;  // 未找到视频通话
}
```

**关键点**:
- `enc_slot` 是编码器的视频会议桥端口ID（连接到 Capture Port）
- 返回此 ID 用于后续连接渲染器

#### Step 2: 创建渲染器 Port

## 🎯 FFmpeg 版本是否相关？

### 问题分析

用户问："是否还包含ffmpeg版本问题"

### 答案：**不相关！**

**原因分析**:

| 层级 | 组件 | 作用 | FFmpeg 版本影响 |
|------|------|------|----------------|
| **内核层** | V4L2 驱动 | 摄像头设备访问控制 | ❌ **不影响** |
| **PJSIP 层** | pjmedia_vid_capture | 调用 V4L2 打开摄像头 | ❌ **不影响** |
| **应用层** | FFmpeg (h264_rkmpp) | H.264 编码/解码 | ✅ **仅影响编解码** |

**V4L2 冲突发生位置**:
```c
// 内核层 - 驱动代码（与 FFmpeg 无关）
int v4l2_open(struct file *filp) {
    if (device_already_opened) {
        return -EBUSY;  // 设备繁忙（此处与 FFmpeg 版本无关）
    }
    device_already_opened = true;
    return 0;
}
```

**FFmpeg 工作位置**:
```
Camera → V4L2 → PJSIP Capture Port → 原始视频帧 (YUV/I420)
                                       ↓
                                  H.264 Encoder (FFmpeg)
                                       ↓
                                  RTP 网络包
```

**结论**: V4L2 冲突发生在**摄像头打开阶段**（内核驱动层），FFmpeg 在**编码阶段**（应用层），两者不相关。

## 🎯 技术总结

### 核心洞察

1. **V4L2 单进程限制是 Linux 内核驱动设计**：
   - 不是 Bug，是设计选择（避免竞争条件）
   - 无法通过应用层修改绕过

2. **PJSIP 视频会议桥是正确的解决方案**：
   - 设计目标：多路视频流分发
   - 零性能开销（内存拷贝，无编解码）
   - 架构清晰，易于维护

3. **FFmpeg 版本与 V4L2 冲突无关**：
   - V4L2 冲突发生在**设备打开阶段**（内核层）
   - FFmpeg 工作在**编解码阶段**（应用层）
   - 两者在调用链的不同位置

### 架构亮点

```
单一数据源，多路消费者模式 (Producer-Consumer):
- Producer: Camera (V4L2) - 只打开一次 ✅
- Splitter: Vid Conference Bridge (Tee) - 零拷贝分发 ✅
- Consumers: Encoder (RTP) + Renderer (本地预览) - 并行消费 ✅
```

### 适用场景

| 场景 | Fix 69 适用性 | 备注 |
|------|--------------|------|
| **Linux 视频通话 + 本地预览** | ✅ 完美适用 | 主要目标场景 |
| **Windows 视频通话** | ✅ 兼容但非必需 | Windows 支持多路访问 |
| **仅本地预览（无通话）** | ❌ 不适用 | Fallback 到独立预览 |
| **多路监控摄像头** | ✅ 可参考架构 | 参考 [39-RTSP视频监控接入方案](39-RTSP视频监控接入方案-FFmpeg-vs-GStreamer.md) |
