## 🎯 根本原因

### QTimer 定时器精度不足

**问题代码**（旧版实现）：
```cpp
// ❌ 使用周期性定时器
m_frameTimer->start(20);  // 期望每 20ms 触发一次

void onFrameTimerTimeout() {
    sendNextFrame();  // 但实际触发间隔不稳定
}
```

**为什么会失败**：

1. **平台限制**：
   - 在嵌入式 Linux 平台上，`QTimer` 精度受限于系统调度器
   - 即使使用 `Qt::PreciseTimer`，仍无法保证精确的 20ms 间隔

2. **误差累积**：
   ```
   第 1 帧：应该 20ms，实际 24ms → 延迟 4ms
   第 2 帧：应该 40ms，实际 48ms → 延迟 8ms
   第 3 帧：应该 60ms，实际 76ms → 延迟 16ms
   ...
   第 250 帧：应该 5000ms，实际 6800ms → 延迟 1800ms
   ```

3. **系统负载影响**：
   - 音频播放
   - UI 更新
   - 网络 I/O
   - 多任务调度

---

## 💡 解决方案

### 绝对时间戳控制算法

**核心思想**：不依赖定时器间隔精度，而是计算每帧的绝对发送时间

**算法公式**：
```cpp
// 第 i 帧应该发送的绝对时间
nextFrameAbsoluteTime = m_sendStartTime + i * 20

// 当前时间
currentTime = m_playbackTimer.elapsed()

// 需要延迟的时间（动态计算）
delay = nextFrameAbsoluteTime - currentTime
```

**自动补偿机制**：
```cpp
if (delay > 0) {
    // 正常情况：延迟发送
    QTimer::singleShot(delay, this, &AudioNetworkSender::sendNextFrame);
} else {
    // 已经延迟了：立即发送（补偿）
    QTimer::singleShot(0, this, &AudioNetworkSender::sendNextFrame);
}
```

**工作示例**：
```
发送开始时间 m_sendStartTime = 100ms

第 0 帧：应该 100ms，当前 120ms → 延迟 -20ms → 立即发送（补偿）
第 1 帧：应该 120ms，当前 120ms → 延迟 0ms   → 立即发送
第 2 帧：应该 140ms，当前 122ms → 延迟 18ms  → 等待 18ms
第 3 帧：应该 160ms，当前 140ms → 延迟 20ms  → 等待 20ms
第 4 帧：应该 180ms，当前 160ms → 延迟 20ms  → 等待 20ms（稳定）
```

**优势**：
- ✅ 不依赖定时器间隔精度
- ✅ 自动补偿累积延迟
- ✅ CPU 占用低（只在需要时唤醒）
- ✅ 实现简单，易于维护

### 修改 4：AudioNetworkSender.cpp - sendNextFrame() ⭐ 核心修改

**位置**：Line 757-822

**完全重构的函数逻辑**：

```cpp
void AudioNetworkSender::sendNextFrame()
{
    // ========== 1. 检查播放状态 ==========
    if (!m_isPlaying || m_currentFrameIndex >= m_currentFrames.size()) {
        qDebug() << "   ✅ 所有帧发送完成，总耗时:" << m_playbackTimer.elapsed() << "ms";
        stopPlayback();
        emit playbackFinished();
        return;
    }

    // ========== 2. 发送当前帧 ==========
    qint64 currentTime = m_playbackTimer.elapsed();
    const QByteArray& opusFrame = m_currentFrames[m_currentFrameIndex];

    qint64 bytesSent = m_udpSocket->writeDatagram(
        opusFrame.constData(),
        opusFrame.size(),
        m_multicastAddress,
        m_multicastPort
    );

    // 错误处理
    if (bytesSent < 0) {
        qWarning() << "❌ UDP 发送失败（帧" << m_currentFrameIndex << "）:"
                   << m_udpSocket->errorString();
        emit networkError(m_udpSocket->errorString());
    }

    // ========== 3. 计算下一帧的绝对时间 ==========
    m_currentFrameIndex++;  // 递增索引

    // 核心公式：下一帧应该发送的绝对时间戳
    qint64 nextFrameAbsoluteTime = m_sendStartTime + m_currentFrameIndex * 20;
    qint64 delay = nextFrameAbsoluteTime - currentTime;

    // ========== 4. 调试日志（每 50 帧）==========
    if ((m_currentFrameIndex - 1) % 50 == 0) {
        qDebug() << "   📡 已发送:" << (m_currentFrameIndex - 1) << "/" << m_totalFrames
                 << "帧（" << currentTime << "ms）";
        qDebug() << "      当前帧大小:" << opusFrame.size() << "字节";
        qDebug() << "      下一帧延迟:" << delay << "ms（绝对时间:" << nextFrameAbsoluteTime << "ms）";
    }

    // 触发进度信号
    emit playbackProgress(m_currentFrameIndex, m_totalFrames);

    // ========== 5. 调度下一帧发送 ==========
    if (delay > 0) {
        // 正常情况：延迟发送
        QTimer::singleShot(delay, this, &AudioNetworkSender::sendNextFrame);
    } else {
        // 已经延迟了：立即发送（自动补偿）
        if (delay < -10) {
            qWarning() << "⚠️ 严重延迟（帧" << m_currentFrameIndex << "）: 已延迟" << (-delay) << "ms";
        }
        QTimer::singleShot(0, this, &AudioNetworkSender::sendNextFrame);
    }
}
```

**关键改进**：
1. **绝对时间戳计算**：`nextFrameAbsoluteTime = m_sendStartTime + frameIndex * 20`
2. **动态延迟调整**：`delay = nextFrameAbsoluteTime - currentTime`
3. **自动补偿机制**：如果 `delay < 0`，立即发送下一帧
4. **递归调用**：使用 `QTimer::singleShot()` 替代周期性定时器
5. **延迟监控**：如果严重延迟（>10ms），输出警告日志


**推导过程**：
- 第 0 帧：`m_sendStartTime + 0 * 20 = m_sendStartTime`
- 第 1 帧：`m_sendStartTime + 1 * 20 = m_sendStartTime + 20ms`
- 第 2 帧：`m_sendStartTime + 2 * 20 = m_sendStartTime + 40ms`
- 第 i 帧：`m_sendStartTime + i * 20`

**延迟计算**：
```cpp
// 需要等待的时间 = 应该发送的时间 - 当前时间
delay = nextFrameAbsoluteTime - currentTime
```

**补偿机制**：
- 如果 `delay > 0`：正常，等待 `delay` 毫秒后发送
- 如果 `delay = 0`：刚好，立即发送
- 如果 `delay < 0`：已延迟，立即发送（补偿）

---

### QTimer::singleShot() 递归模式

**为什么使用递归**：
```cpp
void sendNextFrame() {
    // 发送当前帧
    sendUdpDatagram();

    // 计算下一帧延迟
    qint64 delay = calculateDelay();

    // 递归调用自己（通过 singleShot）
    QTimer::singleShot(delay, this, &AudioNetworkSender::sendNextFrame);
}
```

**优势**：
1. 每次调用都是独立的定时器（不会累积误差）
2. 可以根据实际情况动态调整延迟
3. CPU 占用低（只在需要时唤醒）
4. 代码逻辑清晰（一次发送 → 调度下一次）

**对比周期性定时器**：
```cpp
// ❌ 周期性：固定间隔，误差累积
m_timer->start(20);  // 每 20ms 触发一次（但实际可能 22ms、24ms...）

// ✅ singleShot：动态调整，自动补偿
QTimer::singleShot(delay, ...);  // delay 根据实际情况计算
```

- 系统资源分配

- 前 0.5 秒可能略有延迟
- 但不影响整体播放效果（用户未反馈异常）

**是否需要修复**：
- ❌ 不需要（启动延迟可接受）
- ✅ 如果需要，可以在播放前预热（提前初始化）

**现象**：Wireshark 仍显示帧间隔有抖动（15ms-33ms）

**原因**：
- 系统调度器（进程切换）
- 网络 I/O（网卡驱动、协议栈）
- UDP 组播（路由器、交换机）

**影响**：
- 小幅抖动不影响音频播放
- 音频解码器有缓冲区，可以平滑抖动

**是否需要修复**：
- ❌ 不需要（用户反馈"语音正常"）
- ✅ 如果需要更严格的实时性，可以：
  1. 提高进程优先级（实时调度）
  2. 使用专用网络接口（独立网卡）
  3. 减少系统负载（关闭无关服务）
