# FIX 100.290 - 修复 UDP 服务发现端口未监听问题

**修复时间**：2026-01-22 14:00（北京时间 UTC+8）
**修复版本**：VERSION 2026-01-22-14:00
**上次编译**：2026-01-22 13:39:40（需重新编译验证）
**问题严重性**：🔴 阻塞（TCP 音频传输完全无法工作）

---

## 一、问题总结

### 问题描述
设备（192.168.10.188）收到上位机（192.168.10.142）的 UDP 服务发现广播后，返回 **ICMP Port Unreachable** 错误，导致 TCP 音频传输协议无法启动。

### 根本原因
`AudioNetworkTcpSender` 对象创建后，**未调用 `startDiscovery()` 方法**，导致 UDP 端口 8600 没有绑定监听。

### 影响范围
- ❌ UDP 服务发现失败
- ❌ TCP 连接无法建立
- ❌ WebSocket 握手无法进行
- ❌ 音频数据无法传输
- ✅ **整个 TCP 音频传输功能完全不可用**

## 三、修复方案

### 修改文件：[src/control/CommonControl.cpp:135-136](src/control/CommonControl.cpp#L135-L136)

#### 修改前
```cpp
    qDebug() << "🔊 CommonControl: 音频播放器已初始化";
}  // 构造函数结束
```

#### 修改后
```cpp
    qDebug() << "🔊 CommonControl: 音频播放器已初始化";

    // ✅ 2026-01-22 20:05 [TCP音频传输] 自动启动 UDP 服务发现
    // 原因：上位机会在应用启动后立即发送 UDP 广播（端口 8600）
    // 如果不启动监听，设备会返回 ICMP Port Unreachable 错误
    m_audioNetworkTcpSender->startDiscovery();
    qDebug() << "✅ CommonControl: TCP 音频模块已启动 UDP 服务发现";
}
```

### 修复逻辑

1. **CommonControl 构造函数**（应用启动时）
   - 创建 `AudioNetworkTcpSender` 对象
   - **立即调用 `startDiscovery()`**

2. **AudioNetworkTcpSender::startDiscovery()**
   - 绑定 UDP 端口 8600
   - 等待上位机 UDP 广播
   - 接收 JSON → 解析服务器 IP:Port
   - 触发 TCP 连接流程

## 六、技术细节

### UDP 服务发现机制

#### 1. 上位机广播 JSON（端口 8600）
```json
{
  "voiceport": 7800,
  "voicev4": [-1062731588, -1062731589]
}
```

#### 2. 设备解析 JSON
```cpp
// voicev4 是 int32 形式的 IP 地址
// -1062731588 = 0xC0A80ABC = 192.168.10.188
QString serverIp = parseIpFromInt32(-1062731588);  // "192.168.10.188"
quint16 serverPort = 7800;
```

#### 3. 设备连接服务器
```cpp
m_wsClient->connectToServer(serverIp, serverPort);
// TCP 连接 192.168.10.142:7800
// WebSocket 握手
// 发送设备信息 JSON
```

### 为什么必须在启动时调用 startDiscovery()？

1. **上位机行为**：
   - 上位机软件启动后**立即发送 UDP 广播**
   - 不管设备是否在线，持续广播

2. **设备行为**：
   - 如果 UDP 端口未监听 → **ICMP Port Unreachable**
   - 如果 UDP 端口监听 → **接收 JSON → 自动连接**

3. **参考设备（192.168.10.98）行为**：
   - 应用启动时自动调用 `startDiscovery()`
   - 立即监听 UDP 8600
   - 无需手动配置
