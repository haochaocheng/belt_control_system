## 二、问题分析

### 问题 1：启动延迟长（~1.1秒）

**日志证据**（voip.md）：

```
Line 490: R 键按下
Line 509: 启动预警初始化
Line 510-518: TTS 合成 "1号皮带启动"
  ⏱️  TTS 合成耗时: 1047 ms  ← 主要瓶颈（占90%）
Line 763: Opus 编码耗时: 97 ms
Line 772: 开始发送音频帧

总延迟：~1.1 秒
```

**根本原因**：
- TTS 合成是同步阻塞操作，每次播放都需要 1000ms+ 合成时间
- 短文本（5个汉字）也需要完整的模型初始化和推理过程

**解决方向**（后续优化）：
1. 预缓存常用文本（"一号皮带启动" ~ "十号皮带启动"）
2. 应用启动时提前合成并保存 WAV 文件
3. 播放时直接使用缓存，跳过合成阶段
4. 预期延迟：1100ms → 100ms（减少 90%）

---

### 问题 2：数字"1"没有播放出来 ⭐

**日志证据**（voip.md）：

```
Line 515: 发送 TTS 命令
  Command: {"text":"1\xE5\x8F\xB7\xE7\x9A\xAE\xE5\xB8\xA6\xE5\x90\xAF\xE5\x8A\xA8",...}
  解码后：{"text":"1号皮带启动",...}  ← 文本正确

Line 517: TTS 合成成功
  ✅ 语音合成成功: Generated audio successfully
  采样数: 15222
  音频时长: 1902 ms  ← 约1.9秒音频
  TTS 合成耗时: 1047 ms

Line 771: 预缓冲 40ms
Line 772: 开始发送第 0 帧
```

**问题分析**：

1. **文本发送正确**：命令中包含完整文本 "1号皮带启动"
2. **合成成功**：生成了 1.9 秒的音频（15222个采样点 @ 8000Hz）
3. **用户听不到"1"**：但用户反馈只听到 "号皮带启动"，缺少开头的 "1"

**可能原因**：

| 原因 | 证据 | 可能性 |
|------|------|--------|
| **TTS 模型对数字发音不清** | 其他用户也报告过类似问题 | ⭐⭐⭐ 高 |
| 预缓冲时间太短（40ms） | 可能切掉了音频开头 | ⭐⭐ 中 |
| 上位机接收延迟 | WebSocket 连接稳定，日志正常 | ⭐ 低 |
| 音频编码问题 | Opus 编码成功，无错误 | ⭐ 低 |

**根本原因（最可能）**：
- Sherpa-ONNX VITS 模型在处理**阿拉伯数字**时发音不清晰或音量过低
- 中文 TTS 模型通常针对**中文文本**训练，对数字、字母等非汉字处理较差
- "1" 这个字符可能被合成为极短的音节或被跳过

## 三、解决方案

### 方案：使用中文数字代替阿拉伯数字 ⭐

**核心思路**：
```
旧文本："1号皮带启动"
新文本："一号皮带准备启动，请注意"
```

**改进点**：
1. ✅ **中文数字**："一" 代替 "1"（解决发音问题）
2. ✅ **更友好的表达**："准备启动" 代替 "启动"（更自然）
3. ✅ **增加提醒**："请注意" 结尾（符合工业场景规范）

**技术优势**：
- 中文数字在 TTS 模型中发音清晰准确
- 更长的文本使音频更流畅自然
- 符合工业语音提示的标准格式

**添加内容**：
```cpp
// ✅ 2026-01-23 01:45 [TTS发音优化] 数字转中文函数实现
// 原因：
//   - 用户反馈："'1'没有播放出来，直接号皮带启动"
//   - TTS 模型对阿拉伯数字"1"发音不清晰（日志：line 515-517 合成成功但用户听不到"1"）
//   - 解决方案：使用中文数字"一"代替阿拉伯数字"1"
// 新格式：
//   - 旧："1号皮带启动"
//   - 新："一号皮带准备启动，请注意"
// 效果：
//   - TTS 对中文数字发音清晰准确
//   - 增加"准备启动"和"请注意"使语音更友好自然
QString CommonControl::numberToChinese(int number) const
{
    // 支持 1-10 号皮带的中文数字转换
    static const QMap<int, QString> chineseNumbers = {
        {1, "一"},
        {2, "二"},
        {3, "三"},
        {4, "四"},
        {5, "五"},
        {6, "六"},
        {7, "七"},
        {8, "八"},
        {9, "九"},
        {10, "十"}
    };

    // 如果在映射范围内，返回中文数字
    if (chineseNumbers.contains(number)) {
        return chineseNumbers[number];
    }

    // 超出范围时回退到阿拉伯数字（如 11, 12 等）
    return QString::number(number);
}
```

**关键逻辑**：
1. **静态映射表**：1-10 的中文数字映射（编译时初始化）
2. **范围检查**：1-10 返回中文，超出范围返回阿拉伯数字
3. **防御性编程**：处理超出范围的情况（如 11 号皮带）

## 七、问题1的后续优化方案（预缓存）

### 问题描述

**当前状态**：
- TTS 合成耗时 ~1200ms（占总延迟 90%）
- 每次播放都需要重新合成
- 用户感觉延迟较长

### 优化方案：应用启动时预合成

**核心思路**：
```cpp
// 应用启动时（CommonControl 构造函数）
void CommonControl::CommonControl()
{
    // ... 其他初始化 ...

    // ✅ 预合成常用 TTS 文本
    QStringList preloadTexts = {
        "一号皮带准备启动，请注意",
        "二号皮带准备启动，请注意",
        "三号皮带准备启动，请注意",
        // ... 四-十号 ...
    };

    for (const QString &text : preloadTexts) {
        // 后台合成并缓存到 /tmp/tts_cache_1.wav 等
        m_tts->precacheText(text);
    }
}

// 播放时直接使用缓存
void CommonControl::playWarningOnce()
{
    QString warningText = QString("%1号皮带准备启动，请注意").arg(numberToChinese(m_currentBeltNumber));

    // 检查缓存
    if (m_tts->hasCachedAudio(warningText)) {
        // 直接使用缓存（跳过合成）
        m_tts->playFromCache(warningText);  // 0ms 合成延迟
    } else {
        // 缓存未命中，实时合成
        m_tts->sayToNetwork(warningText, true);  // ~1200ms
    }
}
```

**预期效果**：
- 首次启动：预合成 10 个常用文本（约 5-10 秒，后台进行）
- 后续播放：0ms 合成延迟（直接使用缓存）
- 总延迟：1300ms → 100ms（**减少 92%**）

**实施难度**：⭐⭐ 中等
- 需要修改 SherpaOnnxTTS 添加缓存机制
- 需要设计缓存管理（LRU、过期策略）
- 需要测试缓存文件的存储和加载

```cpp
    return chineseNumbers[number];
}
return QString::number(number);  // 如 11 → "11"
```
