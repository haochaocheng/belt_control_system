## 二、工作原理

### 2.1 修改类型识别

| 修改类型 | 是否需要编译 | 部署方式 | 耗时 |
|---------|------------|---------|------|
| **C++ 源码** | ✅ 需要 | 编译 → 复制二进制 → 重启容器 | 4-10 分钟 |
| **QML 界面** | ✅ 需要 | 编译 → 复制二进制 → 重启容器 | 4-10 分钟 |
| **Python 脚本** | ❌ 不需要 | 直接复制 → 重启容器 | 1-3 分钟 |

**注意**：QML 使用 `qt_add_qml_module(... STATIC ...)`，已编译进二进制，不能单独热更新。

### 2.2 容器常驻运行

设备上的 Docker 容器 `belt-control-app` 持续运行：

```
设备 192.168.10.185
└── Docker 容器: belt-control-app (常驻运行)
    ├── /app/belt_control_system         # 二进制文件（可热更新）
    ├── /app/tts_engines/                # Python TTS 脚本（可热更新）
    └── /app/lib/                        # 运行时库（不变）
```

### 2.3 快速部署流程

```
修改代码 → 自动检测类型 → 选择部署方案
                         ├─ C++/QML: 编译 → 复制二进制 → 重启容器
                         └─ Python: 直接复制 → 重启容器
```

### 2.4 正在运行的程序如何处理？

**关键机制**：使用 `docker restart` 重启容器，自动处理运行中的程序

**详细流程**：

1. **复制新文件到容器**：
   ```bash
   # 新二进制文件覆盖旧文件
   docker cp /tmp/belt_control_system.new belt-control-app:/app/belt_control_system
   ```

2. **重启容器**：
   ```bash
   # Docker 会优雅地停止容器内所有进程
   docker restart belt-control-app
   ```
   - Docker 发送 `SIGTERM` 信号给主进程
   - 等待 10 秒让程序优雅退出
   - 如果程序未退出，发送 `SIGKILL` 强制终止
   - 使用新的二进制文件重新启动容器

3. **验证新程序运行**：
   ```bash
   # 检查依赖库
   docker exec belt-control-app ldd /app/belt_control_system

   # 查看启动日志
   docker logs --tail 20 belt-control-app
   ```

**优点**：
- ✅ 无需手动停止进程
- ✅ 自动使用新的二进制文件
- ✅ 保持容器配置和挂载不变
- ✅ 重启时间约 5-10 秒

**注意事项**：
- ⚠️ 重启会中断正在进行的操作（如视频通话）
- ⚠️ 建议在测试环境或空闲时段部署
- ⚠️ 生产环境建议先备份当前版本

## 三、常见问题

### Q1: 为什么 QML 修改也需要编译？

**原因**: 项目使用 `qt_add_qml_module(... STATIC ...)`，QML 文件在编译时被编译进二进制文件，不是运行时加载。

**验证**: 查看 `src/qml/CMakeLists.txt` 第 4 行：
```cmake
qt_add_qml_module(qml_module
    URI BeltControlQml
    VERSION 1.0
    STATIC  # ← QML 编译进二进制
    ...
)
```

---

### Q3: 什么时候需要完整构建？

**需要完整构建的情况**:
- ✅ 首次部署到新设备
- ✅ 修改了 PJSIP 源码
- ✅ 修改了系统依赖（Dockerfile）
- ✅ 修改了 Python 依赖（requirements.txt）
- ✅ 容器被删除或损坏

**可以快速部署的情况**:
- ✅ 修改 C++ 业务逻辑
- ✅ 修改 QML 界面
- ✅ 修改 Python TTS 脚本
- ✅ 修改配置文件
