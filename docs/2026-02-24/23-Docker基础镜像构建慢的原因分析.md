## 二、慢的根本原因

### 2.1 主要原因：网络下载慢

**PaddleSpeech 依赖包大小**：
```
paddlepaddle: ~92 MB
numpy: ~14 MB
pandas: ~11 MB
scipy: ~31 MB
matplotlib: ~7 MB
librosa: ~260 KB
... 其他 100+ 个包

总计: ~200-300 MB
```

**下载速度问题**：
- 清华镜像：460 KB/s（实测）
- 下载 250 MB：**9-10 分钟**
- 但实际更慢，因为：
  - 需要逐个下载（串行）
  - 每个包都有依赖解析
  - 网络不稳定

### 2.2 次要原因：QEMU 模拟慢

**安装过程**：
```
1. 下载 wheel 包（网络 I/O）
2. 解压 wheel（磁盘 I/O）
3. 复制文件到 site-packages（磁盘 I/O）
4. 编译 .pyc 字节码（CPU 密集）
```

**QEMU 影响**：
- 网络 I/O：影响小
- 磁盘 I/O：影响中等（慢 2-3 倍）
- CPU 编译：影响大（慢 10-20 倍）

**预估时间分配**：
```
下载：60-80 分钟（网络慢）
解压和安装：40-60 分钟（QEMU 慢）
编译 .pyc：20-30 分钟（QEMU 很慢）

总计：120-170 分钟
```

### 2.3 为什么比预期慢？

**我之前说的 20-30 分钟是错误的**，原因：
1. ❌ 低估了 PaddleSpeech 的依赖数量（100+ 个包）
2. ❌ 低估了网络下载时间（清华镜像也不够快）
3. ❌ 低估了 QEMU 对安装过程的影响

**实际时间应该是**：
- 首次构建：**120-170 分钟**（2-3 小时）
- 后续构建：**2-5 分钟**（缓存命中）

### 方案 C：在 ARM64 设备上构建（最快）

**原理**：在原生 ARM64 环境构建，避免 QEMU 模拟

**步骤**：
```bash
# 1. SSH 到设备
ssh linaro@192.168.10.188

# 2. 上传 Dockerfile
# （在 Windows 上执行）
scp Dockerfile.ubuntu24-base linaro@192.168.10.188:/tmp/
scp -r docker/rk3588 linaro@192.168.10.188:/tmp/

# 3. 在设备上构建
cd /tmp
docker build -f Dockerfile.ubuntu24-base -t base-image .

# 4. 导出镜像
docker save base-image | gzip > base-image.tar.gz

# 5. 下载到 Windows
# （在 Windows 上执行）
scp linaro@192.168.10.188:/tmp/base-image.tar.gz .

# 6. 导入镜像
docker load < base-image.tar.gz
```

**效果**：
- 构建时间：**30-40 分钟**（vs 120-170 分钟）
- 节省时间：**80-130 分钟**

**适用场景**：
- 首次构建
- 网络很慢
- 设备性能好

## 五、为什么这次这么慢？

### 5.1 对比分析

| 场景 | 下载 | 安装 | 总时间 |
|------|------|------|--------|
| **本机 QEMU（当前）** | 60-80 分钟 | 60-90 分钟 | **120-170 分钟** |
| **设备上构建** | 15-20 分钟 | 15-20 分钟 | **30-40 分钟** |

| **离线包** | 0 分钟 | 5-10 分钟 | **5-10 分钟** |

### 5.2 根本原因

   - 实际：60-80 分钟（串行下载 + 依赖解析）

2. **QEMU 慢**：
   - 磁盘 I/O：慢 2-3 倍
   - CPU 编译：慢 10-20 倍
   - 总体：慢 3-5 倍

3. **依赖多**：
   - PaddleSpeech：100+ 个依赖
   - 每个包都要下载、解压、安装
   - 串行处理，无法并行
