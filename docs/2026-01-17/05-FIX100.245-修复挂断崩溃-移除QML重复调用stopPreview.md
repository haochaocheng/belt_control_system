- 错误码：Exit code 139 (SIGSEGV - 段错误)

## ⚠️ 根本原因

**QML自动停止逻辑与C++异步调用冲突，导致重复调用**

### 完整时序分析

```
1. 用户点击挂断按钮
   ↓
2. hangupCall() 调用 pjsua_call_hangup()
   ↓
3. PJSIP触发 PJSIP_INV_STATE_DISCONNECTED 回调（PJSIP线程）
   ↓
4. onCallStateChanged() 调用 notifyCallDisconnected()
   ↓
5. notifyCallDisconnected() 执行：
   - QMetaObject::invokeMethod(localVideoManager, "stopPreview", Qt::QueuedConnection)
   - stopPreview() 被放入Qt事件队列 ⏳
   ↓
6. isInCall 属性变为 false
   ↓
7. QML 监听到 isInCall 变化（Qt主线程，同步）
   - ❌ 直接调用 stopPreview() [第1次]
   - custom_slot: 4 → 移除成功
   - m_customSlot = INVALID
   ↓
8. Qt 事件循环执行队列中的任务（Qt主线程，异步）
   - ❌ 执行之前入队的 stopPreview() [第2次]
   - custom_slot: INVALID → 跳过清理
   - return 后访问已释放资源 → 崩溃！ 💥
```

### 为什么会崩溃？

虽然第二次调用检测到 `custom_slot == INVALID` 并提前返回，但：
1. **对象状态不一致**: 第一次调用已经修改了内部状态
2. **资源竞争**: PJSIP异步清理可能在两次调用之间完成
3. **内存访问**: 可能在 `return` 后访问了已释放的成员变量

## ✅ 修复方案

### 方案选择

**方案一**: 在C++中添加防重入标志 ❌
- 复杂，需要线程安全考虑
- 治标不治本

**方案二**: 修改析构函数避免重复清理 ❌
- 两次调用都不是析构触发

**方案三**: 移除QML自动停止逻辑 ✅ **采用**
- 简单直接
- 职责单一：视频资源由C++管理
- 避免UI层操作底层资源

## 💡 经验教训

### 1. 职责分离原则
- **UI层 (QML)**: 只负责显示和用户交互
- **业务层 (C++)**: 负责资源管理和清理
- 不应该让UI层直接操作底层资源

### 2. 异步调用的陷阱
- `QMetaObject::invokeMethod` 使用 `Qt::QueuedConnection` 是异步的
- 不要假设异步调用会立即执行
- 小心同步和异步调用的混用

### 3. 调试方法论
- ✅ 添加详细的调试日志（带唯一标记，如 `[HANGUP-DEBUG]`）
- ✅ 追踪完整的调用链路
- ✅ 统计调用次数（预期 vs 实际）
- ✅ 分析时序关系（同步 vs 异步）

### 4. 重复调用的防护
即使有双重清理保护（`m_customSlot == INVALID`检查），仍可能崩溃：
- 对象状态已改变
- 资源可能已释放
- 最好从源头避免重复调用
