# FIX 100.245 完整解决 - Use-After-Free 根因分析

**日期**: 2026-01-17 22:00
**问题**: 本机主动挂断通话崩溃，对方挂断不崩溃
**根本原因**: RemoteVideoManager 提前释放 pool 导致 Use-After-Free
**解决方案**: 采用静态映射延迟释放，pool 由 port_on_destroy 回调管理

---

## 📋 问题现象

### 崩溃场景
- ✅ **对方主动挂断**：程序正常运行，不崩溃
- ❌ **本机主动挂断**：程序崩溃，退出码 139 (SIGSEGV)

### 设备差异

- **设备 188**: 必定崩溃 ❌

**初步怀疑**：内存管理问题，可能是 Use-After-Free（使用已释放内存）

## 💡 根本原因

### 问题代码分析

**RemoteVideoManager::destroyCustomPort() - 错误实现：**
```cpp
void RemoteVideoManager::destroyCustomPort()
{
    if (m_customPort) {
        m_customPort = nullptr;  // 只清空指针
    }

    if (m_pool) {
        pj_pool_release(m_pool);  // ❌ 立即释放 pool
        m_pool = nullptr;
        // 💥 问题：port 结构存储在这个 pool 中，现在 pool 被释放了！
    }
}
```

**port_on_destroy() - 空实现：**
```cpp
pj_status_t RemoteVideoManager::port_on_destroy(pjmedia_port *port)
{
    qDebug() << "📹 Custom port on_destroy called";
    PJ_UNUSED_ARG(port);
    return PJ_SUCCESS;  // ❌ 什么都不做
}
```

### 时间序列分析

**本机主动挂断时的执行顺序：**

```
1. 用户点击挂断按钮
   ↓
2. notifyCallDisconnected() 被调用
   ↓
3. RemoteVideoManager::onCallDisconnected()
   ↓
4. destroyCustomPort()
   └─ pj_pool_release(m_pool) ← ❌ pool 被立即释放
   └─ port 结构所在内存被回收到内存池
   ↓
5. PJSIP 继续执行异步清理
   ↓
6. vid_conf 开始移除 port 0, 3, 2, 1 ✅
   ↓
7. vid_conf 尝试移除 port 5
   └─ pjmedia_port_dec_ref(port)
      └─ 访问 port->grp_lock ← 💥 内存已被释放
      └─ 访问 grp_lock 内部原子变量
         └─ 设备 188：内存已被覆盖 → SIGSEGV
         └─ 设备 151：内存侥幸保留 → 暂时不崩溃
```

**对方主动挂断时的执行顺序：**

```
1. 对方挂断通话
   ↓
2. PJSIP 收到 BYE 消息
   ↓
3. PJSIP 清理 call 相关资源
   ↓
4. vid_conf 移除所有 port (包括 port 5) ✅
   ↓
5. port 5 引用计数 → 0
   └─ 调用 port_on_destroy() ✅
   └─ 但什么都不做（空实现）
   ↓
6. notifyCallDisconnected() 被调用
   ↓
7. destroyCustomPort()
   └─ pj_pool_release(m_pool)
   └─ 此时 port 已经被 PJSIP 完全清理 ✅
   └─ 没有人再访问 port 结构 ✅
```

### Use-After-Free 原理

**Use-After-Free（UAF）是一种严重的内存安全问题：**

1. **内存被释放**：`pj_pool_release(m_pool)` 将 port 结构所在内存返回给内存池
2. **悬空指针**：PJSIP vid_conf 仍持有指向 port 的指针
3. **内存被重用**：内存池可能将这块内存分配给其他对象
4. **访问失效内存**：PJSIP 尝试访问 port->grp_lock 时：
   - **情况 1（设备 188）**：内存立即被覆盖 → grp_lock 变成垃圾数据 → 访问崩溃
   - **情况 2（设备 151）**：内存暂时保留原值 → grp_lock 仍有效 → 侥幸不崩溃

**这就是为什么同样的代码在不同设备上表现不同！**

## ✅ 解决方案

### 参考 LocalVideoManager 的正确实现

**LocalVideoManager 使用静态映射延迟释放：**

```cpp
// 1. 定义静态映射
static std::unordered_map<pjmedia_port*, pj_pool_t*> s_portPoolMap;

// 2. 创建 port 时保存映射
bool LocalVideoManager::createCustomPort(...)
{
    // ... 创建 port 和 pool ...

    s_portPoolMap[m_customPort] = m_customPool;  // ✅ 保存映射
    return true;
}

// 3. stopPreview() 不释放 pool
void LocalVideoManager::stopPreview()
{
    if (m_customSlot != PJSUA_INVALID_ID) {
        pjsua_vid_conf_remove_port(m_customSlot);  // ✅ 只移除 port
        m_customSlot = PJSUA_INVALID_ID;
    }

    // ❌ 不调用 pj_pool_release(m_customPool)
    // ✅ pool 将在 port_on_destroy 回调中释放
}

// 4. port_on_destroy 回调中释放 pool
pj_status_t LocalVideoManager::port_on_destroy(pjmedia_port *port)
{
    auto it = s_portPoolMap.find(port);
    if (it != s_portPoolMap.end()) {
        pj_pool_t *pool = it->second;
        pj_pool_release(pool);  // ✅ 此时释放安全
        s_portPoolMap.erase(it);
    }
    return PJ_SUCCESS;
}
```

```cpp

{
    // ✅ 2026-01-17 22:00 [FIX 100.245] 从静态映射中获取 pool 并释放
    auto it = s_remotePortPoolMap.find(port);
    if (it != s_remotePortPoolMap.end()) {
        pj_pool_t *pool = it->second;
        qDebug() << "📹 [FIX 100.245] RemoteVideoManager::port_on_destroy: Found pool in map, releasing...";

        pj_pool_release(pool);  // ✅ 此时释放安全

        s_remotePortPoolMap.erase(it);
        qDebug() << "✅ [FIX 100.245] Pool released in on_destroy callback";
    } else {
        qDebug() << "⚠️ [FIX 100.245] port_on_destroy: Port not found in map (already cleaned?)";
    }

    return PJ_SUCCESS;
}
```

### 时机正确

**修复后的执行顺序（本机挂断）：**

```
1. 用户点击挂断按钮
   ↓
2. notifyCallDisconnected() 被调用
   ↓
3. RemoteVideoManager::onCallDisconnected()
   ↓
4. destroyCustomPort()
   └─ m_customPort = nullptr ✅ 只清空指针
   └─ m_pool = nullptr ✅ 只清空指针
   └─ pool 仍在内存中 ✅
   ↓
5. PJSIP 继续执行异步清理
   ↓
6. vid_conf 移除 port 5
   └─ pjmedia_port_dec_ref(port)
      └─ 引用计数 → 0
      └─ 调用 port_on_destroy() ✅
         └─ 从 s_remotePortPoolMap 获取 pool
         └─ pj_pool_release(pool) ✅
         └─ 此时 PJSIP 所有清理已完成，释放安全 ✅
```

### 内存安全

1. **pool 延迟释放**：直到 PJSIP 完全清理完 port 才释放内存
2. **回调时机正确**：`port_on_destroy` 是 PJSIP 最后一步，此时释放绝对安全
3. **静态映射独立**：不依赖 `this` 指针，即使 RemoteVideoManager 已析构也能正确释放

### 两种场景都正确

**本机挂断：**
- RemoteVideoManager 先清理 → destroyCustomPort()
- PJSIP 后清理 → port_on_destroy() 释放 pool ✅

**对方挂断：**
- PJSIP 先清理 → port_on_destroy() 释放 pool ✅
- RemoteVideoManager 后清理 → destroyCustomPort() 发现 pool 已 NULL，跳过 ✅

## 📚 技术要点总结

### Use-After-Free 特征
1. **非确定性崩溃**：在不同设备/时机表现不同
2. **内存相关**：访问指针时 SIGSEGV
3. **时序敏感**：崩溃与操作顺序强相关

### PJSIP Port 生命周期管理
1. **引用计数**：`pjmedia_port_dec_ref()` 管理生命周期
2. **on_destroy 回调**：引用计数 → 0 时调用
3. **内存池管理**：port 结构存储在 pool 中，pool 不能提前释放

### 正确的清理顺序
1. **移除 port**：`pjsua_vid_conf_remove_port()` 只是启动清理
2. **等待回调**：PJSIP 异步完成清理后调用 `on_destroy`
3. **释放内存**：在 `on_destroy` 中释放 pool 才安全

### 静态映射的优势
1. **独立于对象生命周期**：RemoteVideoManager 析构后仍可访问
2. **线程安全**：可以在 PJSIP 线程和 Qt 线程间共享
3. **时机控制**：精确控制 pool 释放时机
