# FIX 100.200 测试结果 - 找到根本原因

**时间**: 2026-01-15 04:00（北京时间）
**结论**: ✅ **找到崩溃的根本原因！FFmpeg 内部切换了 AVCodecContext，但 PJSIP 仍使用旧实例**

---

## 1. 关键发现

### ✅ DIAG-A 和 DIAG-6 地址匹配（PJSIP 指针稳定）

**DIAG-A（PJSIP 编码器打开后，Line 1627-1628）**：
```
ff->enc_ctx: 0x7f14016e60
ff->enc_ctx->priv_data: 0x7f14017220
```

**DIAG-6（FFmpeg setup_frame，第一次编码时，Line 1838-1840）**：
```
AVCodecContext (ctx): 0x7f14016e60  ← ✅ 匹配 DIAG-A
ctx->priv_data: 0x7f14017220        ← ✅ 匹配 DIAG-A
X264Context (x4): 0x7f14017220
reordered_opaque: (nil)             ← ❌ 未初始化！
nb_reordered_opaque: 0
```

**结论**：
- ✅ PJSIP 的 `ff->enc_ctx` 指针在打开后到编码前保持稳定
- ✅ PJSIP 没有使用错误的缓存指针
- ❌ 但这个 X264Context (0x7f14017220) 没有被初始化

---

### ❌ DIAG-A 和 DIAG-5 地址完全不匹配（FFmpeg 切换了实例）

**DIAG-5（FFmpeg X264_init，第1个实例，Line 1290-1295）**：
```
X264Context address: 0x7f1462f360      ← ❌ 不匹配 DIAG-A (0x7f14017220)
reordered_opaque array: 0x7f16d32b10   ← ✅ 已分配
nb_reordered_opaque: 69                ← ✅ 已初始化
AVCodecContext (avctx): 0x7f1462eee0  ← ❌ 不匹配 DIAG-A (0x7f14016e60)
avctx->priv_data: 0x7f1462f360
```

**对比表**：

| 诊断点 | AVCodecContext | priv_data (X264Context) | 状态 |
|-------|----------------|------------------------|------|
| PJSIP avcodec_open2() 前（Line 1261） | ? | 0x7f14017220 | ⚠️ 已分配，未初始化 |
| DIAG-A（PJSIP 打开后） | 0x7f14016e60 | 0x7f14017220 | ✅ PJSIP 记录 |
| DIAG-5（FFmpeg 初始化） | 0x7f1462eee0 | 0x7f1462f360 | ✅ FFmpeg 初始化 |
| DIAG-6（FFmpeg 编码时） | 0x7f14016e60 | 0x7f14017220 | ❌ 使用未初始化实例 |

**结论**：
- ❌ FFmpeg `X264_init()` 初始化的是**不同的 AVCodecContext** (0x7f1462eee0)
- ❌ PJSIP 使用的 AVCodecContext (0x7f14016e60) **从未被初始化**
- ❌ 导致 `reordered_opaque = NULL` → 崩溃

---

### 🔴 真正的根本原因

**FFmpeg 在 `avcodec_open2()` 内部切换了 AVCodecContext！**

**时间线**：

```
01:43:59.273  [PJSIP] avcodec_alloc_context3()
              → enc_ctx = 0x7f14016e60
              → priv_data = 0x7f14017220 (FFmpeg 自动分配)

01:43:59.340  [PJSIP] avcodec_open2(enc_ctx, ...)
              → FFmpeg 内部调用 X264_init()
              → 但使用的是另一个 AVCodecContext (0x7f1462eee0)！
              → 初始化了 priv_data (0x7f1462f360) ✅
              → 原始的 priv_data (0x7f14017220) 未被初始化 ❌

01:43:59.340  [PJSIP] DIAG-A 记录地址
              → ff->enc_ctx = 0x7f14016e60 (原始实例)
              → ff->enc_ctx->priv_data = 0x7f14017220 (未初始化)

01:43:59.840  [PJSIP] avcodec_send_frame(enc_ctx, ...)
              → 使用原始 enc_ctx (0x7f14016e60)
              → 访问未初始化的 priv_data (0x7f14017220)
              → reordered_opaque = NULL
              → 崩溃 ❌
```

## 2. 为什么会有两个不同的 AVCodecContext？

### 可能的原因

#### 假设 1：FFmpeg 的编解码器能力协商机制

**证据**：
- 9 个 DIAG-5 实例被初始化（9 种不同的编码器配置）
- 可能是 FFmpeg 在测试不同的编码器参数组合
- 最终选择了一个配置，但 PJSIP 仍使用原始实例

**可能性**：60%

---

#### 假设 2：FFmpeg 的线程模型

**证据**：
- libx264 可能在内部创建了多个 AVCodecContext
- 主线程使用原始实例，工作线程使用新实例

**可能性**：20%

---

#### 假设 3：PJSIP 的编解码器注册机制

**证据**：
- PJSIP 注册了 9 个不同的编码器配置
- 每个配置都调用了 `avcodec_open2()`
- 但 PJSIP 使用了错误的实例

**可能性**：20%

## 3. 对比之前的分析

### FIX 100.199 的结论（部分正确）

- ✅ **正确**：使用了未初始化的 X264Context 实例
- ✅ **正确**：9 个实例被初始化，但使用的是第 10 个未初始化的
- ❌ **不完整**：没有发现 FFmpeg 内部切换了 AVCodecContext

### FIX 100.200 的新发现

- ✅ **PJSIP 指针管理是正确的**（DIAG-A == DIAG-6）
- ✅ **FFmpeg 内部切换了 AVCodecContext**（DIAG-A ≠ DIAG-5）
- ✅ **原始 AVCodecContext 从未被初始化**

## 4. 修复方案

### 方案 A：在 libx264.c 中添加防御性初始化（推荐）⭐

**原理**：
- 如果 `reordered_opaque == NULL`，说明 X264Context 未初始化
- 在第一次使用时自动初始化

**修改位置**：FFmpeg `libx264.c` Line 551（setup_frame 函数开头）

**代码**：
```c
static int setup_frame(AVCodecContext *ctx, const AVFrame *frame,
                       x264_picture_t **ppic)
{
    X264Context *x4 = ctx->priv_data;

    /* ✅ 2026-01-15 04:10 [FIX 100.201] 防御性初始化未初始化的 X264Context */
    if (!x4->reordered_opaque || x4->nb_reordered_opaque == 0) {
        av_log(ctx, AV_LOG_WARNING,
               "[FIX 100.201] X264Context not initialized! Initializing now...\n");
        av_log(ctx, AV_LOG_WARNING,
               "  X264Context address: %p\n", (void*)x4);
        av_log(ctx, AV_LOG_WARNING,
               "  This should NOT happen! Possible FFmpeg internal issue.\n");

        /* 检查编码器是否已打开 */
        if (!x4->enc) {
            av_log(ctx, AV_LOG_ERROR, "  ❌ ERROR: x264 encoder not opened!\n");
            return AVERROR(EINVAL);
        }

        /* 分配 reordered_opaque 数组 */
        int delayed_frames = x264_encoder_maximum_delayed_frames(x4->enc);
        x4->nb_reordered_opaque = FFMAX(delayed_frames + 17, 1);
        x4->reordered_opaque = av_calloc(x4->nb_reordered_opaque,
                                        sizeof(*x4->reordered_opaque));
        if (!x4->reordered_opaque) {
            x4->nb_reordered_opaque = 0;
            return AVERROR(ENOMEM);
        }
        x4->next_reordered_opaque = 0;

        av_log(ctx, AV_LOG_WARNING,
               "  ✅ Emergency initialization completed\n");
        av_log(ctx, AV_LOG_WARNING,
               "  Array pointer: %p, size: %d\n",
               (void*)x4->reordered_opaque, x4->nb_reordered_opaque);
    }

    X264Opaque *opaque = &x4->reordered_opaque[x4->next_reordered_opaque];
    // ... 继续原有逻辑
}
```

**优点**：
- ✅ 快速解决崩溃问题
- ✅ 防御性编程，避免未来类似问题
- ✅ 不影响正常初始化的实例
- ✅ 有详细的日志记录异常情况

**缺点**：
- ⚠️ 修改了 FFmpeg 官方源码（但仅添加防御性检查）
- ⚠️ 治标不治本（FFmpeg 内部问题未解决）

---

### 方案 B：在 PJSIP 中重新初始化编码器（复杂）

**原理**：
- 检测到 `priv_data` 未初始化时，重新调用 `avcodec_open2()`

**修改位置**：PJSIP `ffmpeg_vid_codecs.c`

**问题**：
- ❌ 不知道如何判断 `priv_data` 是否初始化（需要侵入 FFmpeg 内部）

- ❌ 可能引入新的问题

**可行性**：低

---

### 方案 C：禁用编解码器能力协商（测试用）

**原理**：
- 减少注册的编码器数量（从 9 个减少到 1 个）
- 避免 FFmpeg 内部切换实例

**修改位置**：PJSIP 编码器注册代码

**优点**：
- ✅ 快速验证假设 1
- ✅ 可能从根本上解决问题

**缺点**：
- ❌ 可能影响编解码器功能
- ❌ 不清楚如何修改注册代码

**可行性**：中等（需要进一步研究）

## 6. 结论

### ✅ FIX 100.200 诊断成功

1. **排除了错误假设**：
   - ❌ 不是 PJSIP 指针管理问题（DIAG-A == DIAG-6）
   - ❌ 不是 X264_close() 过早调用（未找到）

   - ✅ **导致 `reordered_opaque = NULL` → 崩溃**
