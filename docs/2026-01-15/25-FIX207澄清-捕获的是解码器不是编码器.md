## 🎯 核心问题：100% 确定

### 问题 1：为什么 libx264 的 priv_data 没有被初始化？

**答案**：libx264 使用多线程帧编码器（FF_THREAD_FRAME），FFmpeg 在多线程模式下：
- 创建了 9 个子线程上下文
- 每个子线程调用 X264_init()
- 但**主上下文**（PJSIP 的 AVCodecContext）**没有被初始化**
- PJSIP 使用主上下文编码，导致 x4->enc = NULL

### 问题 2：9 次 X264_init() 都初始化了什么？

**答案**：FFmpeg 为每个编码线程创建了独立的子上下文：

```
主上下文（PJSIP）: 0x7ed0016890
  ├─ priv_data: 0x7ed0016c50  ← ❌ 从未被 X264_init()
  └─ x4->enc: NULL  ← ❌ 未初始化

子上下文（线程 1-9）:
  ├─ 0x7ed062eaa0 → X264_init() ✅ → x4->enc: 0x7ed864fac0
  ├─ 0x7ed2d33200 → X264_init() ✅ → x4->enc: 0x7ec91d7960
  ├─ 0x7eb5451e10 → X264_init() ✅ → x4->enc: 0x7ec91d0960
  └─ ... (共 9 个)
```

### 问题 3：PJSIP 应该使用哪个上下文编码？

**理论**：FFmpeg 多线程编码的标准用法是：
- 主上下文调用 `avcodec_send_frame()`
- FFmpeg 内部自动分发到子线程
- 子线程使用各自的 x4->enc 编码
- FFmpeg 合并输出

**实际（PJSIP）**：
- PJSIP 直接访问主上下文的 priv_data
- x4->enc = NULL → 编码失败

**优势**：
- ✅ 符合 FFmpeg 设计

**优势**：
- ✅ 快速验证（2-3 分钟）
- ✅ 触发 FIX 100.207 诊断
- ✅ 主上下文会被 X264_init() 初始化
- ✅ x4->enc 不为 NULL

**风险**：

## 📝 总结

### ✅ 澄清的事实

1. **FIX 100.207 捕获了 h264_rkmpp 解码器**（不是编码器）
   - 解码器使用单线程初始化
   - FIX 100.207 正常工作
   - avctx 和 priv_data 都没有被替换

2. **libx264 编码器使用多线程初始化**
   - 绕过了 FIX 100.207 诊断代码
   - 创建了 9 个子线程上下文
   - 主上下文（PJSIP）没有被初始化

3. **编码失败的根本原因**
   - PJSIP 使用未初始化的主上下文编码
   - x4->enc = NULL
   - avcodec_send_frame() 返回 -22 (EINVAL)
