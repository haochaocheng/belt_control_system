## ❌ 致命缺陷 1：dlsym() 预期会失败（95% 概率）

### 问题

即使修改了 FFmpeg 源码（去掉 `static`，添加 `visibility("default")`），`X264_init` 符号仍然**不会被导出**。

### 证据

**已验证**（2026-01-16 01:00）：
```bash
# 增量编译 libx264.c 完成后
nm -D docker/rk3588/ffmpeg60-libs/opt/ffmpeg-rockchip/lib/libavcodec.so.60.31.102 | grep X264_init

# 结果：空（符号不存在）
```

**原因**：FFmpeg 使用符号版本控制系统

所有导出的符号都有 `@@LIBAVCODEC_60` 后缀：
```bash
nm -D libavcodec.so | grep ' T ' | head
# 输出：
# 00000000000fa3d0 T av_bsf_init@@LIBAVCODEC_60
# 00000000000fa640 T av_bsf_iterate@@LIBAVCODEC_60
# ...（只导出公开 API）
```

**X264_init 不是公开 API**，FFmpeg 从未打算导出它。

### 预期结果

```c
X264_init_func_t X264_init_ptr = (X264_init_func_t)dlsym(RTLD_DEFAULT, "X264_init");

// dlsym() 返回 NULL ❌
if (!X264_init_ptr) {
    PJ_LOG(1,(THIS_FILE, "  ⚠️ WARNING: X264_init symbol not found (dlsym failed)"));
    PJ_LOG(1,(THIS_FILE, "     dlerror: %s", dlerror()));
    // 输出：undefined symbol: X264_init
    status = PJMEDIA_CODEC_EFAILED;
    goto on_error;
}
```

**结果**：编码器初始化失败，视频通话仍然无法工作。

## ❌ 致命缺陷 3：破坏封装，不可维护

### 当前做法的问题

1. **调用 FFmpeg 内部函数**：
   - `X264_init()` 不是公开 API
   - FFmpeg 明确标记为 `static`（内部使用）
   - 破坏了模块封装

2. **FFmpeg 版本兼容性差**：
   - FFmpeg 7.0 可能改变 `X264_init()` 签名
   - 或者重命名、删除此函数
   - 编译时会报错

3. **维护成本高**：
   - 每次 FFmpeg 升级都要检查兼容性
   - 可能需要重新适配
   - 其他开发者看到这个代码会困惑

### 符合工程规范的做法

✅ **只使用 FFmpeg 公开 API**：
- `avcodec_alloc_context3()`
- `avcodec_open2()`
- `avcodec_send_frame()`
- `avcodec_receive_packet()`

❌ **不调用内部函数**：
- `X264_init()`（内部）
- `X264Context`（内部结构）
- `x4->enc`（内部字段）

## ❌ 致命缺陷 4：忽略了根本问题

### 真正的问题

**为什么 FFmpeg 会创建 9 个不同的 AVCodecContext？**

从 FIX 100.205 日志：
```
X264_init() 调用 9 次（每次启动）:
  1. AVCodecContext: 0x7efc6503e0 → priv_data: 0x7efc650860 ✅
  2. AVCodecContext: 0x7efed54ce0 → priv_data: 0x7efed55160 ✅
  3. AVCodecContext: 0x7ee9537a50 → priv_data: 0x7ee9537ed0 ✅
  ... (共 9 个)

PJSIP 使用的:
  AVCodecContext: 0x7efc038320 → priv_data: 0x7efc0386e0 ❌（未初始化）
```

**关键问题**：
1. PJSIP 只注册了 **8 个编解码器**
2. 只有 **H264 使用 libx264**
3. 那么 **其他 8 次 X264_init() 从哪来？**

### 可能的解释

**解释 1：FFmpeg 内部编解码器协商**
- FFmpeg 在 `avcodec_open2()` 中测试多个配置
- 创建多个实例用于兼容性测试
- 最终选择其中一个

**解释 2：PJSIP 配置错误**
- PJSIP 可能配置了多个 H264 编码器实例
- 每个实例有不同的参数（分辨率、码率）
- FFmpeg 为每个配置创建了新的 AVCodecContext

**解释 3：PJSIP 重复调用 avcodec_open2()**
- PJSIP 可能在内部多次调用 `avcodec_open2()`
- 每次调用都创建新的实例
- 但最终使用的是第一次（未初始化的）

### 我们应该调查的方向

1. **为什么 FFmpeg 不使用 PJSIP 传入的 AVCodecContext？**
2. **PJSIP 的调用顺序是否正确？**
3. **PJSIP 的参数配置是否有问题？**
4. **能否让 PJSIP 使用 FFmpeg 创建的 9 个实例之一？**
