## 5. 为什么第一次编码会崩溃？

### 预期行为

1. **第一次编码时**：
   - `opaque = &x4->reordered_opaque[0]`（索引=0）
   - `opaque->frame_opaque_ref == NULL`（刚初始化）
   - `opaque_uninit(opaque)` 调用 `av_buffer_unref(&NULL)`
   - **应该安全返回**（FFmpeg 允许 unref NULL）

2. **第二次编码时**：
   - `opaque = &x4->reordered_opaque[1]`（索引=1）
   - 依然是 `NULL`...

### 实际行为

**崩溃发生在第一次 `av_buffer_unref()` 调用！**

## 6. 可能的根因假设

### 假设1：av_calloc() 分配失败但返回了野指针

**证据**：
- `nb_reordered_opaque = 69`（测试日志确认）
- 内存分配 `69 * sizeof(X264Opaque)` ≈ 2-3KB
- 不太可能分配失败

**反驳**：
- `av_calloc()` 失败会返回 NULL，被 Line 1310-1313 检测到
- 不会返回野指针

### 假设2：PJSIP代码破坏了AVCodecContext内部状态

**证据**：
- 编码器成功打开
- 暂停/恢复操作正常
- 第一次编码前没有异常日志

**可疑操作**：
- PJSIP 在 `avcodec_open2()` 后没有直接操作 `AVCodecContext`
- 历史上 FIX 100.77 因手动释放 `hw_frames_ctx` 导致崩溃

**待检查**：
- PJSIP 是否在某个隐蔽的地方修改了 `enc_ctx`？
- 是否有多线程竞争？

### 假设3：frame_opaque_ref 指向了无效内存

**机制**：
```c
// Line 510: av_buffer_replace()
ret = av_buffer_replace(&opaque->frame_opaque_ref, frame->opaque_ref);
```

`av_buffer_replace()` 会先调用 `av_buffer_unref()` 释放旧的引用。

**问题**：
- 如果 `frame->opaque_ref` 是野指针？
- 如果 PJSIP 传递的 `AVFrame` 有问题？

**待检查**：
- PJSIP 传递给 `avcodec_send_frame()` 的 AVFrame 是否正确初始化？
- `frame->opaque_ref` 的值是什么？

### 假设4：编译器优化或内存对齐问题

**证据**：
- `X264Opaque` 结构体定义（Line 56-65）
- 可能有条件编译（`#if FF_API_REORDERED_OPAQUE`）

**待检查**：
- PJSIP 使用的 FFmpeg 头文件版本是否匹配？
- 结构体大小和对齐是否一致？
