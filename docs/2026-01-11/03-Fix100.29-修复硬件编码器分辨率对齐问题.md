# Fix 100.29：修复硬件编码器分辨率对齐问题

**日期**：2026-01-11 01:30
**问题**：h264_rkmpp 返回 -22 (EINVAL) 错误
**根本原因**：分辨率不符合 16 像素对齐要求

## 问题确认

### h264_rkmpp 的 16 像素对齐要求

根据 Rockchip MPP 官方文档：
> The encoder aligns both width and height to 16 pixels using `MPP_ALIGN(cfg->prep.height, 16) / 16` and `MPP_ALIGN(cfg->prep.width, 16) / 16`.

**原因**：
- H.264 编码器使用 16×16 宏块（macroblock）
- 硬件加速器要求内存访问按 16 像素对齐
- 不对齐的分辨率会导致色度数据读取错误

### 当前分辨率验证

```
640x360 (摄像头输出)：
- 宽度 640 = 16 × 40 ✅
- 高度 360 = 16 × 22.5 ❌ (不是 16 的倍数！)

768x432 (SDP 协商)：
- 宽度 768 = 16 × 48 ✅
- 高度 432 = 16 × 27 ✅

推荐分辨率（最接近 640x360）：
- 640x368 = 16 × 40 × 16 × 23 ✅
- 640x352 = 16 × 40 × 16 × 22 ✅
```

**结论**：h264_rkmpp 拒绝处理 360 高度的帧 → 返回 EINVAL (-22)

## 解决方案

### 方案 1：修改摄像头分辨率为 640x368（推荐）⭐

#### 优点
- 符合 16 像素对齐要求
- 启用硬件编码器（低功耗）
- 最接近原始 640x360 分辨率
- 视觉差异极小（8 像素高度差）

#### 实施方法

修改摄像头配置（可能在 `LocalVideoManager.cpp` 或应用启动参数）：

**选项 A：修改应用配置**
```cpp

```

**选项 B：修改 V4L2 设备设置**
```bash

# 如果支持 640x368，修改应用配置使用该分辨率
```

### 方案 2：使用 768x432 分辨率

#### 优点
- 符合 SDP 协商结果
- 符合 16 像素对齐要求
- 无需修改 SDP 配置

#### 缺点
- 分辨率比摄像头原始输出高
- 需要视频缩放器（增加 CPU 开销）

#### 实施方法

**选项 A：添加软件缩放器（libswscale）**
```c

    640, 360, AV_PIX_FMT_YUV420P,  // 输入
    768, 432, AV_PIX_FMT_YUV420P,  // 输出
    SWS_BILINEAR, NULL, NULL, NULL
);
sws_scale(sws_ctx, input_data, input_linesize, 0, 360,
          output_data, output_linesize);
```

**选项 B：使用 RGA 硬件缩放器**（需要 RGA 配置）
```c

```

## 技术细节

### 为什么是 16 像素对齐？

**H.264 宏块结构**：
- H.264 使用 16×16 像素的宏块作为基本编码单元
- 硬件编码器按宏块处理，无法处理非对齐分辨率
- 色度数据（UV）是亮度数据（Y）的 1/2 分辨率（4:2:0）
- 非对齐会导致色度数据访问越界

**示例**：
```
1080p 视频的实际内存布局：
- 配置分辨率：1920×1080
- 水平 stride：1920 (对齐)
- 垂直 stride：1088 (1080 向上对齐到 16 的倍数)
- 实际内存大小：1920×1088×3/2
```

### 360 vs 368 的视觉差异

```
360: 16 × 22 +  8 (不完整的宏块)
368: 16 × 23     (完整的 23 个宏块)

差异：8 像素 / 360 = 2.2%
人眼几乎察觉不到
```
