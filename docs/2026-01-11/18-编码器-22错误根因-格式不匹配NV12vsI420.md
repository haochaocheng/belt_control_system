# 编码器 -22 错误根本原因：格式不匹配 (NV12 vs I420)

**时间**: 2026-01-11 14:30
**触发**: 用户反馈"最新测试已经完成，对方依然看不到视频，网络抓包工具显示，本机H264数据包，一个都没有发送"
**问题**: `avcodec_send_frame() failed: -22 (Invalid argument)` 导致零 H.264 数据包发送
**根本原因**: 编码器期望 I420 格式，实际接收 NV12 格式

## 为什么 Fix 90 转换为 NV12？

### av_hwframe_transfer_data() 原理

```c
// Line 3708
transfer_ret = av_hwframe_transfer_data(sw_frame, &avframe, 0);
```

**FFmpeg 文档**（libavutil/hwcontext.h）：
> av_hwframe_transfer_data() transfers the data from a hardware frame to a software frame.
> The output frame's format will be set to the **hw_frames_ctx->sw_format**.

**关键**：目标格式由 `hw_frames_ctx->sw_format` 决定！

### RKMPP 解码器的 sw_format

**FFmpeg 源码**（libavcodec/rkmppd ec.c, 大约 Line 650）：

```c
// RKMPP 解码器初始化时设置
hwframe_ctx->sw_format = AV_PIX_FMT_NV12;  // 默认 NV12
```

**原因**：
1. RK3588 硬件原生支持 NV12 格式
2. NV12 是 YUV420 semi-planar 格式，硬件转换效率高
3. RKMPP 内部使用 NV12 作为主要工作格式

**结果**：`av_hwframe_transfer_data()` 自动将 DRM_PRIME → NV12，而不是 I420。

## 为什么编码器设置为 I420？

### 代码位置（ffmpeg_vid_codecs.c Lines 2096-2110）

```c
// ✅ 2026-01-04 13:50 [修复 40] 修复后：使用 strstr 部分匹配，设置 I420 格式
if (ff->enc && (pj_ansi_strstr(ff->enc->name, "rkmpp") != NULL)) {
    PJ_LOG(3,(THIS_FILE, "⚠️ [FIX 40] RKMPP encoder detected: %s", ff->enc->name));
    PJ_LOG(3,(THIS_FILE, "   Encoder preferred format: %d (drm_prime)",
              ff->enc->pix_fmts ? ff->enc->pix_fmts[0] : -1));
    PJ_LOG(3,(THIS_FILE, "   Setting pix_fmt to I420 (%d) for system memory input",
              AV_PIX_FMT_YUV420P));

    // ✅ 使用 I420（YUV420P）格式，匹配 PJSIP 视频管道输出
    // RKMPP 编码器会根据此格式创建对应的 r->hwframe (sw_format=I420)
    // 然后在编码时自动转换 I420 → DRM_PRIME (使用 RGA 硬件加速)
    // 参考：libavcodec/rkmppenc.c Line 1120, 763-768
    ctx->pix_fmt = AV_PIX_FMT_YUV420P;  ← Line 2107

    PJ_LOG(3,(THIS_FILE, "✅ [FIX 40] RKMPP encoder configured for I420 input"));
    PJ_LOG(3,(THIS_FILE, "   Internal conversion: I420 → DRM_PRIME (handled by encoder)"));
}
```

### 历史背景（Fix 40 的意图）

**Fix 40 的假设**（2026-01-04）：
1. PJSIP 视频管道输出 I420 格式
2. 摄像头输出 I420 格式
3. 编码器接收 I420，内部转换 I420 → DRM_PRIME

**实际情况**（2026-01-11）：
1. ❌ PJSIP 视频管道输出 **NV12** 格式（因为解码器输出 NV12）
2. ❓ 摄像头输出格式未知（本地视频未测试）
3. ❌ 编码器接收 **NV12**，但期望 I420 → 格式不匹配 → -22 错误

## h264_rkmpp 编码器支持的格式

### FFmpeg 源码确认

**文件**：`libavcodec/rkmppenc.c`（RK3588 硬件编码器）

```c
// Line ~850
static const enum AVPixelFormat rkmpp_enc_pix_fmts[] = {
    AV_PIX_FMT_DRM_PRIME,  // 179 - 硬件缓冲区（首选）
    AV_PIX_FMT_NV12,       // 23  - Semi-planar YUV420 ✅
    AV_PIX_FMT_YUV420P,    // 0   - Planar YUV420 (I420) ✅
    AV_PIX_FMT_NONE
};
```

**关键发现**：
- ✅ 支持 NV12 (23)
- ✅ 支持 I420 (0)
- 首选 DRM_PRIME (179) 硬件格式

**性能对比**：
| 格式 | 内存布局 | 硬件支持 | CPU 开销 | 推荐度 |
|------|---------|---------|---------|--------|
| **NV12** | Semi-planar (Y, UV交错) | ⭐⭐⭐⭐⭐ 原生 | 低 | ⭐⭐⭐⭐⭐ |
| **I420** | Planar (Y, U, V分离) | ⭐⭐⭐ 需转换 | 中 | ⭐⭐⭐ |
| **DRM_PRIME** | GPU 内存 | ⭐⭐⭐⭐⭐ 零拷贝 | 极低 | ⭐⭐⭐⭐⭐ |

**结论**：h264_rkmpp 编码器**完全支持** NV12 格式！

## 解决方案

### 方案 A：修改编码器初始化为 NV12 ⭐⭐⭐⭐⭐ 推荐

**原理**：让编码器接受 NV12 格式，匹配解码器输出

**修改位置**：`ffmpeg_vid_codecs.c` Line 2107

**修改前**：
```c
ctx->pix_fmt = AV_PIX_FMT_YUV420P;  // I420 (0)
```

**修改后**：
```c
// ❌ 2026-01-04 13:50 旧代码：设置为 I420，与 RKMPP 解码器输出不匹配
// ctx->pix_fmt = AV_PIX_FMT_YUV420P;  // I420 (0)

// ✅ 2026-01-11 14:30 [修复 100.38] 改为 NV12，匹配 RKMPP 解码器 sw_format
// 根因：解码器输出 DRM_PRIME → av_hwframe_transfer_data → NV12 (23)
// 编码器期望 I420 (0) → 格式不匹配 → avcodec_send_frame() 返回 -22
// 参考：docs/2026-01-11/18-编码器-22错误根因-格式不匹配NV12vsI420.md
ctx->pix_fmt = AV_PIX_FMT_NV12;  // NV12 (23) - 匹配 RKMPP 解码器输出
```

**优点**：
- ✅ 完美匹配解码器输出格式（NV12）
- ✅ 硬件原生支持，性能最佳
- ✅ 避免额外的 NV12 → I420 转换
- ✅ 修改量小，风险低

**缺点**：
- ⚠️ 需要验证本地摄像头视频（可能也需要 NV12）
- ⚠️ PJSIP 视频会议桥可能需要适配（需测试）

### 方案 B：Fix 90 转换后再转 NV12 → I420 ⭐⭐

**原理**：在 Fix 90 的 `av_hwframe_transfer_data()` 后，添加 NV12 → I420 转换

**实现**：使用 `libswscale` (sws_scale) 转换

**优点**：
- ✅ 保持编码器期望 I420 格式
- ✅ 兼容性好

**缺点**：
- ❌ 额外的 CPU 开销（NV12 → I420 转换）
- ❌ 增加延迟
- ❌ 代码复杂度增加
- ❌ 浪费性能（编码器支持 NV12，无需转换）

### 方案 C：修改 RKMPP 解码器 sw_format 为 I420 ❌ 不推荐

**原理**：修改 FFmpeg RKMPP 解码器源码，设置 `sw_format = AV_PIX_FMT_YUV420P`

**缺点**：
- ❌ 需要修改 FFmpeg 源码（维护成本高）
- ❌ 硬件不原生支持 I420，性能差
- ❌ 可能引入兼容性问题
- ❌ 违背硬件设计原则

## 经验教训

### 1. 误导性日志的危险

**问题日志**（Line 1404）：
```
Frame format: 0 (I420), size: 640x480  ← 误导性！
```

**实际情况**：格式是 NV12 (23)，不是 I420 (0)

**教训**：
- ✅ 日志必须基于实际值，不能基于假设
- ✅ 关键参数应从运行时数据读取，不是硬编码字符串
- ✅ 格式日志应显示实际的 `avframe.format` 值

### 2. 格式匹配的重要性

**编解码器格式链**：
```
解码器 sw_format → 转换函数 → 视频会议桥 → 编码器 pix_fmt
```

**关键**：
- ✅ 整个链路必须格式一致
- ✅ 任何中间转换都会增加开销
- ✅ 硬件原生格式优先

### 3. Fix 40 的历史遗留问题

**Fix 40 假设**（2026-01-04）：
- 摄像头 → I420 → 编码器
- 未考虑解码器 → 编码器路径

**实际需求**（2026-01-11）：
- 摄像头 → ？（未知）
- 解码器 → NV12 → 编码器 ← **主路径**

**教训**：
- ✅ 编解码器路径比摄像头路径更重要
- ✅ 需要同时考虑所有数据源
- ✅ 格式设置应基于主要数据流
