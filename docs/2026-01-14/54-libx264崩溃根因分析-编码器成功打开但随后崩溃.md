## 🤔 问题假设

### 假设 1：ABI 不兼容（最可能）⭐
**问题**：libx264.so.165 和 FFmpeg 6.0 之间存在 ABI 不兼容

**证据**：
1. libx264.so.165 来自 `docker/rk3588/rk3588-libs/lib/`
2. FFmpeg 6.0 来自 `docker/rk3588/ffmpeg60-libs/`
3. 两者可能**不是一起编译的**
4. 编码器打开成功，但内部数据结构不匹配 → 访问非法内存 → 延迟崩溃

**libx264 ABI 变化历史**：
- libx264.so.164 (2023): API 164
- libx264.so.165 (2024): API 165，ABI 可能有重大变化
- FFmpeg 6.0 (2023): 编译时链接的 libx264 版本未知

**可能的 ABI 不匹配**：
- `x264_encoder_parameters` 结构体布局变化
- `x264_picture_t` 成员偏移变化
- 函数调用约定变化

### 假设 2：FFmpeg 6.0 + libx264 内部 Bug
**问题**：FFmpeg 6.0 的 libx264 wrapper (libavcodec/libx264.c) 存在 bug

**证据**：
1. 崩溃在 `av_buffer_unref()`，这是 FFmpeg 的内存管理
2. 编码器打开成功，说明 FFmpeg 内部初始化没有检查到错误
3. 延迟崩溃，说明某个内部字段/缓冲区访问了无效内存

**可能的 Bug 场景**：
- FFmpeg 分配了某个缓冲区，但 libx264 没有正确初始化
- libx264 返回了错误的指针，FFmpeg 稍后访问导致崩溃
- 线程同步问题（虽然我们强制了单线程）

### 假设 3：内存分配器冲突
**问题**：libx264 和 FFmpeg 使用不同的内存分配器

**证据**：
1. `av_buffer_unref()` 是 FFmpeg 的缓冲区管理
2. libx264 可能有自己的内存池
3. 交叉释放导致 double-free
