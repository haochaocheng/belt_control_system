## 执行摘要

### 核心发现

经过对 **4805 行 FFmpeg 编解码器源码**的完整分析，识别出 **编码器崩溃的根本原因**：

**不对称的清理流程** + **共享硬件设备的引用计数问题**

| 对比项 | 编码器清理（Line 3073-3140） | 解码器清理（Line 3141-3144） |
|--------|----------------------------|----------------------------|
| **Flush 缓冲区** | ✅ **有**（avcodec_send_frame(NULL) + 循环 receive）| ❌ **无** ⚠️ |
| **释放 hw_frames_ctx** | ✅ **有**（av_buffer_unref + 设置 NULL）| ❌ **无** ⚠️⚠️⚠️ |
| **手动释放 hw_device_ctx** | ❌ 无（Fix 100.50 正确移除）| ❌ 无 |
| **清理完整性** | ✅ **完整** | ❌ **不完整** ⚠️⚠️⚠️ |

**关键问题**：
- 解码器的 `hw_frames_ctx` **从未被释放**
- 解码器的 `hw_frames_ctx` 内部可能持有对共享 `g_rkmpp_hwdevice` 的引用
- 编码器的 `avcodec_close()` 尝试释放 `hw_device_ctx`
- 但解码器的 `hw_frames_ctx` 仍持有引用 → **引用计数混乱** → `free()` 崩溃

### 3.3 清理时的引用计数变化

#### 当前代码的清理流程：

```c
/* 编码器清理 */
if (ff->enc_ctx->hw_frames_ctx) {
    av_buffer_unref(&ff->enc_ctx->hw_frames_ctx);  // 引用计数 -1（如果有）
}

// ↑ 引用计数 -1 (3 → 2)

/* 解码器清理 ❌ 问题！*/

// ↑ 引用计数 -1 (2 → 1)
// ⚠️ 但如果 dec_ctx->hw_frames_ctx 存在且未释放，它仍持有 device_ref!

```

**问题场景**：

如果解码器的 `hw_frames_ctx` **从未被释放**：

```
编码器 avcodec_close():
  av_buffer_unref(&enc_ctx->hw_device_ctx)  // 4 → 3

解码器 avcodec_close():
  av_buffer_unref(&dec_ctx->hw_device_ctx)  // 3 → 2

  但！dec_ctx->hw_frames_ctx 仍然存在:
    dec_ctx->hw_frames_ctx->device_ref 仍持有引用 (引用计数 = 1)

  FFmpeg 内部尝试释放 hw_frames_ctx:
    av_buffer_unref(&hw_frames_ctx->device_ref)  // 2 → 1

  但可能此时 hw_device_ctx 已经部分释放或处于异常状态
  → free() 访问无效内存 → SIGSEGV
```

## 四、根本原因总结

### 4.1 核心问题

**解码器的 hw_frames_ctx 从未被手动释放**

**代码证据**：
- 编码器清理（Line 3109-3116）：✅ **显式释放 hw_frames_ctx**
- 解码器清理（Line 3141-3144）：❌ **完全没有释放 hw_frames_ctx**

**后果**：
1. 解码器的 `hw_frames_ctx` 内部持有对 `hw_device_ctx` 的引用
2. 编码器的 `avcodec_close()` 先执行，减少引用计数
3. 解码器的 `avcodec_close()` 后执行，尝试释放 `hw_device_ctx`
4. 但 `hw_frames_ctx` 仍持有引用 → 引用计数混乱
5. FFmpeg 内部尝试释放时，访问已部分释放的内存 → `free()` 崩溃

---

### 4.2 为什么编码器崩溃，而不是解码器？

**时序分析**：

```c
/* 编码器先清理 */
avcodec_close(ff->enc_ctx);  // ← Line 3134
  ↓
  FFmpeg 内部尝试释放 hw_device_ctx
  ↓
  检测到引用计数异常（解码器的 hw_frames_ctx 仍持有引用）
  ↓
  尝试访问 hw_device_ctx 的内存
  ↓
  ⚠️ 此时内存状态不一致（部分释放）
  ↓
  free() 访问无效指针 → SIGSEGV
```

**为什么不是在解码器 avcodec_close 崩溃？**
- 因为崩溃发生在 **编码器的 avcodec_close()** 内部
- 编码器尝试释放共享的 hw_device_ctx
- 但解码器的 hw_frames_ctx 仍持有引用
- 引用计数机制检测到不一致，尝试修复时访问无效内存

---

### 4.3 打开/关闭顺序的不对称

| 操作 | 解码器 | 编码器 | 状态 |
|------|--------|--------|------|
| **打开顺序** | 第 1 步（先）| 第 2 步（后）| ✅ Fix 81 |
| **关闭顺序** | 第 2 步（后）| 第 1 步（先）| ⚠️ **问题** |

**理想的关闭顺序应该是**：
- **先关闭编码器**（与打开顺序相反）
- **后关闭解码器**（最后打开的最后关闭）

**但更重要的是**：
- **每个 codec 都应该完整清理自己的资源**
- 解码器**必须**释放自己的 `hw_frames_ctx`

---

## 五、解决方案设计

### 方案 A：对称清理解码器（推荐）⭐⭐⭐

**核心思路**：让解码器的清理与编码器**完全对称**

**实施位置**: `ffmpeg_vid_codecs.c` Line 3141-3144

**修改前**（当前代码）:
```c
if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
    avcodec_close(ff->dec_ctx);  // ← 只有这一行
    av_free(ff->dec_ctx);
}
```

**修改后**:
```c
if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
    /* ✅ Step 1: Flush 解码器缓冲区 */
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 1/3] Flushing decoder buffers"));
    avcodec_send_packet(ff->dec_ctx, NULL);  // 发送 flush 信号

    AVFrame frame;
    av_frame_unref(&frame);
    int flush_count = 0;
    while (avcodec_receive_frame(ff->dec_ctx, &frame) == 0) {
        flush_count++;
        av_frame_unref(&frame);
    }
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 1/3] Decoder buffers flushed (%d frames)", flush_count));

    /* ✅ Step 2: 释放 hw_frames_ctx（关键！） */
    if (ff->dec_ctx->hw_frames_ctx) {
        PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 2/3] Releasing decoder hw_frames_ctx"));
        av_buffer_unref(&ff->dec_ctx->hw_frames_ctx);
        ff->dec_ctx->hw_frames_ctx = NULL;
        PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 2/3] hw_frames_ctx set to NULL"));
    } else {
        PJ_LOG(3,(THIS_FILE, "  [FIX 100.65 Step 2/3] hw_frames_ctx is NULL (already released or not set)"));
    }

    /* ❌ Step 3: 不手动释放 hw_device_ctx */
    if (ff->dec_ctx->hw_device_ctx) {
        PJ_LOG(3,(THIS_FILE, "  [FIX 100.65] hw_device_ctx will be released by avcodec_close() (shared, ref-counted)"));
    }

    /* ✅ Step 4: 关闭解码器 */
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 3/3] Closing decoder (avcodec_close handles hw_device_ctx)"));
    avcodec_close(ff->dec_ctx);
    av_free(ff->dec_ctx);
}
```

**技术原理**：
1. ✅ **Flush 解码器缓冲区**：确保所有待处理的帧都被释放
2. ✅ **释放 hw_frames_ctx**：**关键步骤**，解除对 hw_device_ctx 的引用
3. ❌ **不手动释放 hw_device_ctx**：让 avcodec_close() 自动处理（引用计数机制）
4. ✅ **调用 avcodec_close()**：触发 FFmpeg 内部清理

**优势**：
- 完全对称的清理流程（编码器和解码器一致）
- 彻底解决引用计数混乱问题
- 遵循 Fix 100.50 的设计原则（不手动 unref hw_device_ctx）
- 最小化修改，风险最低

### 方案 B：调整清理顺序（备选）

**核心思路**：先关闭解码器，后关闭编码器（与打开顺序保持一致）

**修改位置**: `ffmpeg_vid_codecs.c` Line 3072-3147

**修改前**:
```c

/* 先清理编码器 */
if (ff->enc_ctx) {
    // ...编码器清理...
    avcodec_close(ff->enc_ctx);
}

/* 后清理解码器 */
if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
    avcodec_close(ff->dec_ctx);
}
```

**修改后**:
```c
pj_mutex_lock(ff_mutex);

/* ✅ 先清理解码器（与打开顺序相反：LIFO） */
if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
    // ...对称的解码器清理（方案 A 的代码）...
    avcodec_close(ff->dec_ctx);
    av_free(ff->dec_ctx);
}

/* ✅ 后清理编码器 */
if (ff->enc_ctx) {
    // ...编码器清理（保持不变）...
    avcodec_close(ff->enc_ctx);
    av_free(ff->enc_ctx);
}
```

**优势**：
- 打开和关闭顺序对称（LIFO：Last In, First Out）
- 符合资源管理的最佳实践

**劣势**：
- 需要调整更多代码
- 如果不结合方案 A，仍可能有引用计数问题

### 方案 C：方案 A + 方案 B（最佳）⭐⭐⭐⭐⭐

**结合两个方案的优势**：

2. ✅ **调整清理顺序**（方案 B）

```c
        ff->enc_ctx->hw_frames_ctx = NULL;
    }

    /* ✅ 关闭编码器 */
    avcodec_close(ff->enc_ctx);
    av_free(ff->enc_ctx);
}

ff->enc_ctx = NULL;
ff->dec_ctx = NULL;
pj_mutex_unlock(ff_mutex);
```

## 九、总结

### 核心发现

1. **不对称的清理流程**：
   - 编码器：完整清理（Flush + 释放 hw_frames_ctx）
   - 解码器：不完整清理（只有 avcodec_close）

2. **解码器 hw_frames_ctx 从未被释放**：
   - 内部持有对 hw_device_ctx 的引用
   - 导致引用计数混乱
   - 编码器 avcodec_close 时访问无效内存 → SIGSEGV

3. **打开/关闭顺序不对称**：
   - 打开：先解码器，后编码器（Fix 81）
   - 关闭：先编码器，后解码器（不对称）

### 推荐方案

**Fix 100.65 = 方案 C（对称清理 + 调整顺序）**

**实施步骤**：
1. ✅ 在解码器清理前，Flush 解码器缓冲区
2. ✅ **显式释放解码器的 hw_frames_ctx**（关键）
3. ✅ 调整清理顺序：先解码器，后编码器（LIFO）
4. ✅ 保持 Fix 100.50 的设计：不手动 unref hw_device_ctx
