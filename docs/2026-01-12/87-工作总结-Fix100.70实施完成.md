### 修改 4: 添加 force_cleanup 路径（Line 3270-3344）

**完整的强制清理代码**：

```c
force_cleanup:
    /* ⚠️ 2026-01-12 20:10 [FIX 100.70] 强制清理路径（不持有 mutex 锁）
     * 触发条件：
     *   - pj_mutex_trylock(ff_mutex) 失败（锁被持有或死锁）
     * 策略：
     *   - 不等待锁，直接清理（竞态风险 < 死锁风险）
     *   - 解码器：跳过 flush，只释放 hw_frames_ctx + 关闭
     *   - 编码器：执行 flush，释放 hw_frames_ctx + 关闭
     *   - 确保资源被释放，第二次通话可以正常工作
     * 风险：
     *   - 不持有锁的清理可能有竞态条件（例如并发访问 ff->dec_ctx/enc_ctx）
     *   - 但死锁导致资源永不释放的风险更大
     * 缓解：
     *   - PJSIP 设计上不应该并发调用 codec_close（每个 call 的 codec 独立）
     *   - 即使有竞态，最多崩溃一次，总比死锁好
     */
    PJ_LOG(1, "⚠️ [FIX 100.70 FORCE CLEANUP] Starting cleanup WITHOUT mutex protection");

    /* ✅ STEP 1: 强制清理解码器 */
    if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
        PJ_LOG(1, "⚠️ [FIX 100.70 FORCE CLEANUP] Decoder cleanup");

        /* 跳过 flush（避免卡住） */

        /* 释放 hw_frames_ctx */
        if (ff->dec_ctx->hw_frames_ctx) {
            PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Releasing decoder hw_frames_ctx");
            av_buffer_unref(&ff->dec_ctx->hw_frames_ctx);
            ff->dec_ctx->hw_frames_ctx = NULL;
        }

        /* 关闭解码器 */
        PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Closing decoder");
        avcodec_close(ff->dec_ctx);
        av_free(ff->dec_ctx);
    }

    /* ✅ STEP 2: 强制清理编码器 */
    if (ff->enc_ctx) {
        PJ_LOG(1, "⚠️ [FIX 100.70 FORCE CLEANUP] Encoder cleanup");

        /* Flush 编码器缓冲区 */
        PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Flushing encoder buffers");
        avcodec_send_frame(ff->enc_ctx, NULL);

        AVPacket pkt;
        av_init_packet(&pkt);
        pkt.data = NULL;
        pkt.size = 0;

        int flush_count = 0;
        while (avcodec_receive_packet(ff->enc_ctx, &pkt) == 0) {
            flush_count++;
            av_packet_unref(&pkt);
        }
        PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Encoder buffers flushed (%d packets)", flush_count);

        /* 释放 hw_frames_ctx */
        if (ff->enc_ctx->hw_frames_ctx) {
            PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Releasing encoder hw_frames_ctx");
            av_buffer_unref(&ff->enc_ctx->hw_frames_ctx);
            ff->enc_ctx->hw_frames_ctx = NULL;
        }

        /* 关闭编码器 */
        PJ_LOG(1, "  [FIX 100.70 FORCE CLEANUP] Closing encoder");
        avcodec_close(ff->enc_ctx);
        av_free(ff->enc_ctx);
    }

    ff->enc_ctx = NULL;
    ff->dec_ctx = NULL;

    PJ_LOG(1, "✅ [FIX 100.70 FORCE CLEANUP] Forced cleanup completed (WITHOUT lock)");
    return PJ_SUCCESS;
```

## 七、风险评估

### 风险 1：竞态条件（可接受）

**问题**：
- 不持有锁的清理可能有并发访问 `ff->dec_ctx` / `ff->enc_ctx`

**缓解**：
- PJSIP 设计上每个 call 的 codec 是独立的
- 不应该并发调用 `codec_close()`
- 即使有竞态，最多崩溃一次（Exit code 139）
- 总比死锁好（资源永不释放）

### 风险 2：flush 可能卡住（已处理）

**问题**：
- force_cleanup 中编码器 flush 可能卡住

**缓解**：
- 编码器 flush 通常可靠（不像解码器）
- 如果卡住，只影响极端情况（trylock 失败 + flush 卡住）
- 可以在未来版本中添加超时机制


**价值**：
- 每一步基于证据
- 不猜测，不盲目修改
- 问题定位精确到代码行

### 洞察 2：trylock 是死锁的最佳解决方案

**为什么 trylock 有效**：
- 不会被阻塞（立即返回）
- 保留正常清理路径（大部分情况）
- 提供强制清理后路（极端情况）
- 适用于 C 语言（无 RAII）

### 洞察 3：竞态风险 < 死锁风险

**决策理由**：
- 死锁：资源永不释放，程序功能完全失效，无法恢复
- 竞态：最多崩溃一次，可以重启恢复
- **死锁的危害远大于竞态**
