## 二、根本原因分析

### 🔍 为什么正常路径也会出现 pthread_mutex_lock 失败？

**Fix 100.61 的假设**：
- 认为只有析构时 mutex 会失效
- 正常路径应该安全

**新证据**：
- Fix 100.62 测试显示，正常路径也会崩溃
- 崩溃发生在 `QMutexLocker` 加锁时
- 错误码相同：ESRCH（"No Such Process"）

**可能原因**：

#### 原因 1：对象所属线程正在终止
```
时序推测：
t0  onCallEnded() 触发（主线程或 PJSIP 线程）
↓   SipPhoneManager 收到信号
↓   可能触发对象删除（deleteLater）
↓
t1  LocalVideoManager::stopPreview() 被调用
↓   此时对象可能已经标记为待删除
↓   QMutex 底层的 pthread_mutex 关联的线程可能正在终止
↓
t2  QMutexLocker 尝试加锁
↓   pthread_mutex_lock() 检测到线程状态异常
↓   返回 ESRCH → assert 失败 → Exit code 133
```

#### 原因 2：mutex 本身在某些情况下失效
- Qt 对象的 QMutex 成员变量在某些边界情况下可能失效
- 与对象的生命周期管理相关
- 尤其在 `deleteLater()` 或信号槽机制中

---

### 🔑 关键洞察：Fix 100.62 不需要 mutex

**Fix 100.62 的操作**（Line 388-451）：
```cpp

// 1. 停止重试定时器（Qt 线程安全）
if (m_capSlotRetryTimer && m_capSlotRetryTimer->isActive()) {
    m_capSlotRetryTimer->stop();
}

// 2. 双重清理保护（原子操作）

    return;
}

// 3. 标记为已清理（赋值操作，简单）

m_reusedCapSlot = PJSUA_INVALID_ID;

// 4. 标记 port 为 null（赋值操作）
m_customPort = nullptr;

// 5. 停止延迟清理定时器（Qt 线程安全）

    m_delayedCleanupTimer->stop();
}

// 6. 更新状态

```

**分析**：
- **所有操作都是简单的赋值或 Qt 内置线程安全操作**
- **没有任何复杂的资源分配/释放**
- **没有调用 PJSIP API**（不会与 PJSIP 线程竞争）
- **双重清理保护通过 `m_customSlot == PJSUA_INVALID_ID` 检查实现**（原子操作）

**结论**：
- **Fix 100.62 的操作不需要 mutex 保护**
- `m_customSlot` 的检查和赋值是原子操作（在大多数架构上）
- Qt 的 QTimer 操作本身就是线程安全的
- **mutex 反而成为了崩溃源**

## 三、Fix 100.63 解决方案

### 🎯 核心思路

**完全移除 mutex**：
- 正常路径：不使用 `QMutexLocker`（Fix 100.63）
- 析构路径：已在 Fix 100.61 中跳过 mutex

**双重清理保护**：
- 通过 `m_customSlot == PJSUA_INVALID_ID` 检查实现
- 这是原子操作，不需要 mutex

**为什么安全**：
1. **操作简单**：只有赋值和状态检查
2. **Qt 线程安全**：QTimer 操作本身线程安全
3. **原子检查**：`m_customSlot` 的读写在大多数架构上是原子的
4. **无竞态条件**：不涉及复杂的资源分配/释放

## 五、技术原理

### 为什么不需要 mutex？

#### 1. 操作类型分析

| 操作 | 类型 | 是否需要 mutex？ |
|------|------|-----------------|
| 停止 QTimer | Qt 线程安全 | ❌ 否 |
| `m_retryCount = 0` | 简单赋值 | ❌ 否（单线程访问）|
| `m_customSlot == PJSUA_INVALID_ID` | 原子读取 | ❌ 否 |
| `m_customSlot = PJSUA_INVALID_ID` | 原子写入 | ❌ 否 |
| `m_customPort = nullptr` | 简单赋值 | ❌ 否 |
| `m_hasLocalVideo = false` | 简单赋值 | ❌ 否 |
| `emit hasLocalVideoChanged()` | Qt 信号 | ❌ 否（Qt 线程安全）|

**结论**：所有操作都不需要 mutex 保护。

---

#### 2. 双重清理保护的安全性

**检查代码**：
```cpp
if (m_customSlot == PJSUA_INVALID_ID) {
    return;
}
```

**为什么安全**：
- `m_customSlot` 是 `pjsua_conf_port_id` 类型（typedef int）
- 在 x86、ARM、RISC-V 等主流架构上，int 的读写是原子的
- 即使多线程同时读写，最坏情况是读到旧值或新值，不会读到中间状态
- 旧值检查 → 跳过清理 ✅
- 新值检查 → 执行清理 ✅
- **不会出现部分执行的情况**

**赋值代码**：
```cpp
m_customSlot = PJSUA_INVALID_ID;
```

**为什么安全**：
- 原子写入（单条汇编指令）
- 即使多线程同时写入，最终结果都是 `PJSUA_INVALID_ID`
- **不会出现数据损坏**

---

#### 3. Qt 线程安全

**QTimer 操作**：
- `QTimer::stop()` 是线程安全的（Qt 文档保证）
- 内部使用事件系统，自动处理跨线程调用
- 不需要额外的 mutex 保护

**信号发射**：
- `emit hasLocalVideoChanged()` 是线程安全的
- Qt 的信号槽机制自动处理线程切换
- 不需要额外的 mutex 保护

---

### 为什么 mutex 反而成为问题？

**Fix 100.61 的教训**：
- 析构时 mutex 可能失效（pthread_mutex 关联的线程终止）
- 导致 ESRCH 错误

**Fix 100.62 的新发现**：
- 正常路径也会出现 mutex 失效
- 说明 mutex 在某些边界情况下不可靠

**根本原因**：
- Qt 对象的生命周期管理复杂（deleteLater、信号槽、事件循环）
- QMutex 依赖底层 pthread_mutex，在对象即将销毁时可能失效
- **简单的操作不需要 mutex，反而引入了新的失败点**
