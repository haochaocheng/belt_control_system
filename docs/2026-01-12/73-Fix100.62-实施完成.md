### 修改 3：port_on_destroy() 从映射释放 pool（Line 996-1017）

**文件**：`src/sip_phone/LocalVideoManager.cpp`

```cpp
pj_status_t LocalVideoManager::port_on_destroy(pjmedia_port *port)
{
    // ✅ 2026-01-12 02:15 [修复 100.62] 从静态映射中获取 pool 并释放
    // 原因：不能访问 this 指针（可能已析构），但需要释放 pool
    // 解决：从静态映射中查找 port → pool，释放后从映射中移除
    // 时机：vid_conf 真正销毁 port 时调用，此时 PJSIP 所有清理已完成
    // 详细：docs/2026-01-12/72-完整根因分析-崩溃的真正原因.md

    auto it = s_portPoolMap.find(port);
    if (it != s_portPoolMap.end()) {
        pj_pool_t *pool = it->second;
        qDebug() << "📹 [FIX 100.62] port_on_destroy: Found pool in map, releasing...";
        pj_pool_release(pool);
        s_portPoolMap.erase(it);
        qDebug() << "✅ [FIX 100.62] Pool released in on_destroy callback";
    } else {
        qDebug() << "⚠️ [FIX 100.62] port_on_destroy: Port not found in map (already cleaned?)";
    }

    PJ_UNUSED_ARG(port);
    return PJ_SUCCESS;
}
```

## 三、技术优势

### ✅ 为什么 Fix 100.62 能彻底解决？

| 特性 | Fix 100.59 ❌ | Fix 100.62 ✅ |
|-----|--------------|--------------|
| **手动 disconnect** | ✅ 是（总是失败 PJ_EINVAL）| ❌ **否**（PJSIP 自动处理）|
| **手动 remove** | ✅ 是（异步竞态）| ❌ **否**（PJSIP 自动处理）|
| **Pool 释放时机** | 200ms 延迟定时器（猜测）| ⭐ **port_on_destroy 回调**（完全正确）|
| **访问 this 指针** | ❌ 否 | ❌ **否**（从静态映射取 pool）|
| **时序竞争** | ✅ 存在（与 PJSIP 竞争）| ❌ **无**（完全依赖 PJSIP）|

### 🔑 核心洞察

1. **PJSIP 自动断开所有连接**
   - 手动 disconnect 是多余的（总是晚于 PJSIP）
   - 证据：日志 Line 3107 显示 PJSIP 已自动断开 3→4

2. **手动 remove 导致时序竞争**
   - 异步操作无法控制时序
   - 崩溃发生在 remove 完成之前

3. **Pool 释放时机的选择**
   - 太早（立即）：异步竞态崩溃（Fix 100.56）
   - 延迟（200/500/1000ms）：无法准确判断（Fix 100.58/100.59）
   - **正确时机**：port_on_destroy 回调（PJSIP 完成所有清理后）

4. **静态映射解决 this 指针问题**
   - port_put_frame 仍能访问 this（处理帧）
   - port_on_destroy 从映射取 pool（不依赖 this）
   - 即使 this 已析构，on_destroy 也能安全释放 pool
