**关键发现**：

## 二、根本原因分析

### 通过代码分析（grep ff_mutex 使用）发现

**发现 1：open_ffmpeg_codec() 中 mutex 已被移除**
- **代码位置**：Line 2590-2600
- **移除时间**：2025-12-31 10:10（Fix 100.17.4）
- **移除原因**：避免递归死锁（非递归锁）
- **结论**：编码器初始化不持有锁，不会导致 trylock 失败

**发现 2：ffmpeg_factory.mutex 被所有 codec 共享**
- **定义位置**：Line 196
- **设计问题**：所有 codec（音频 + 视频）共享一个 `ffmpeg_factory.mutex`
- **后果**：音频 codec 关闭时持有锁 → 视频 codec trylock 失败（EBUSY）

**发现 3：VERSION 131 的"死锁"不是真正的死锁**
- **真相**：trylock 失败 = 锁正在被使用（正常并发竞争）
- **不是**：锁永远被持有（真正的死锁）
- **场景**：音频和视频 codec 并发关闭，竞争同一个锁

**发现 4：VERSION 132 的 force_cleanup 崩溃原因**
- force_cleanup 不持有锁
- 与持有锁的线程（音频 codec）并发访问 avcodec_close()
- 并发访问共享资源 → 竞态条件 → 崩溃

---

## 三、Fix 100.71 实施内容

### 目标

**完全移除 ffmpeg_codec_close() 中的 ff_mutex 使用**

### 核心方案

**参考 Fix 100.17.4（已在 open_ffmpeg_codec() 中成功移除 mutex）**
- 假设：PJSIP 保证每个 codec 实例的生命周期是单线程的
- 不同 codec 实例（音频/视频）各自独立，不需要互斥
- 直接执行清理代码，不持有任何锁

## 七、技术洞察

### 洞察 1：trylock 失败 ≠ 死锁

**教训**：
- trylock 失败（EBUSY）= 锁正在被使用（正常并发竞争）
- 不能假设 trylock 失败 = 死锁（锁永远被持有）
- 不能假设可以安全地绕过锁（force_cleanup 必然崩溃）

### 洞察 2：共享 mutex 的设计缺陷

**问题**：
- 所有 codec（音频 + 视频）共享 `ffmpeg_factory.mutex`
- 一个 codec 的清理 → 阻塞其他所有 codec 的清理
- 导致并发竞争和 trylock 失败

**解决**：
- 完全移除 mutex（假设 PJSIP 保证单线程）
- 或者为每个 codec 实例创建独立的 mutex

### 洞察 3：诊断式开发的价值

**完整流程**：
```
Fix 100.66: 诊断 dec_ctx/enc_ctx → 发现都存在
    ↓
Fix 100.69: 诊断 ff_mutex → 发现"死锁"
    ↓
Fix 100.70: trylock + force_cleanup → 崩溃
    ↓
分析根本原因 → 发现共享 mutex 设计问题
    ↓
Fix 100.71: 移除 mutex → 从根本解决
```

**价值**：
- 每一步基于证据
- 不断深入挖掘根本原因

## 十、关键教训

### 教训 1：不要假设 trylock 失败 = 死锁

**错误假设**：
- trylock 失败 → 锁永远被持有 → 可以安全地绕过锁

**正确理解**：
- trylock 失败 → 锁**正在被使用** → **不能**绕过锁
- 绕过锁 = 不持有锁的并发访问 = 竞态条件 = 崩溃

### 教训 2：force_cleanup 不是解决方案

**为什么 force_cleanup 失败**：
- 不持有锁 → 与持有锁的线程并发
- 并发访问 avcodec_close() → 竞态条件
- free() 崩溃（double-free 或访问被释放的内存）

### 教训 3：深入分析根本原因

**过程**：
1. VERSION 131: 发现"死锁"
2. VERSION 132: 尝试绕过死锁 → 崩溃
3. 分析根本原因 → 发现共享 mutex 设计问题
4. VERSION 133: 从根本解决（移除 mutex）

**价值**：
- 不要满足于表面现象
- 深入挖掘根本原因
- 找到正确的解决方案
