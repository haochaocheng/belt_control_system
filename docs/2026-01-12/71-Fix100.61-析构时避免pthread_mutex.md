## 二、根本原因分析

### 🔍 pthread_mutex_lock 失败分析

**glibc 源码** (`pthread_mutex_lock.c:450`):
```c
int __pthread_mutex_lock_full (pthread_mutex_t *mutex)
{
    int oldval;
    pid_t id = THREAD_GETMEM (THREAD_SELF, tid);

    // ... 省略 ...

    if (e == ESRCH) {
        /* No such process/thread */
        assert (e != ESRCH || !robust);  // ← Line 450 失败
    }
}
```

**ESRCH 错误含义**：
- 操作系统内核返回 ESRCH（"No Such Process"）
- mutex 关联的线程已不存在
- 通常发生在对象析构过程中

---

### 🕒 时序分析：为什么 mutex 失效？

**崩溃时序推测**：

```
时间轴：t0  通话结束 → 触发 onCallEnded()
        ↓ SipPhoneManager 收到信号

        t1  SipPhoneManager 开始清理
        ↓ 可能触发 LocalVideoManager 析构

        t2  LocalVideoManager::~LocalVideoManager() 开始
        ↓ qDebug() << "LocalVideoManager: Shutting down...";  ← ⚠️ 日志未打印
        ↓ 调用 stopPreview()

        t3  stopPreview() 执行
        ↓ QMutexLocker locker(&m_cleanupMutex);  ← 尝试加锁
        ↓ pthread_mutex_lock(&m_cleanupMutex.__internal_mutex)

        t4  ❌ pthread_mutex_lock 返回 ESRCH
        ↓ assert 失败 → glibc 报错 → 程序终止（exit code 133）
```

**为什么 mutex 失效？**

**可能原因 1：对象析构顺序**
- Qt 对象析构时，基类可能先析构
- QMutex 是否在 stopPreview() 执行前已析构？
- 但 QMutex 是成员变量，应该在所有成员函数执行后才析构

**可能原因 2：线程状态失效**
- QMutex 内部使用 pthread_mutex_t
- 如果 LocalVideoManager 所属的线程正在终止
- pthread_mutex_t 关联的线程 ID 可能已失效
- 导致 pthread_mutex_lock 返回 ESRCH

**可能原因 3：对象状态不一致**
- 析构函数开始时，对象处于半析构状态
- QMutex 虽然存在，但底层 pthread_mutex 可能已无效
- Qt 的 RAII 机制在某些情况下可能出现边界问题

## 三、解决方案：Fix 100.61

### 🎯 核心思路

**在析构时跳过 QMutexLocker**：

**原因**：
1. **析构时无并发风险** - 对象正在被销毁，不可能有其他线程访问
2. **mutex 可能失效** - 对象析构状态下，QMutex 不保证有效
3. **重复清理已防止** - 第一次 stopPreview() 已执行清理

**方案**：
1. 添加 `m_isDestroying` 标志
2. 析构函数设置标志
3. stopPreview() 检查标志，析构时跳过 QMutexLocker

## 五、技术原理

### 为什么析构时不需要 mutex？

**Qt 对象析构保证**：
1. 析构函数执行时，对象的引用计数为 0
2. 不可能有其他线程持有该对象的引用
3. **因此不可能有并发访问**

**mutex 的作用**：
- 正常运行时：防止多个线程同时调用 stopPreview()
- 析构时：对象唯一引用正在被销毁 → **无需互斥保护**

### 为什么析构时立即释放 pool？

**正常路径（200ms 延迟）**：
- 等待 PJSIP vid_conf 异步操作完成
- 避免访问正在被清理的资源

**析构路径（立即释放）**：
- 对象即将销毁，无需等待
- 延迟定时器本身也会被销毁
- 立即释放，确保资源在对象销毁前清理

### pthread_mutex_lock 失败的底层原因

**POSIX 线程规范**：
- `pthread_mutex_lock()` 要求 mutex 有效且线程存在
- 如果 mutex 关联的线程已终止 → 返回 ESRCH
- glibc 的 robust mutex 检查失败 → assert 触发

**为什么 QMutex 可能失效？**
- QMutex 内部封装 pthread_mutex_t
- 对象析构时，C++ 成员变量析构顺序不确定
- QMutex 可能在 stopPreview() 执行前部分失效
- 或者：线程状态改变导致 pthread 层检测失败
