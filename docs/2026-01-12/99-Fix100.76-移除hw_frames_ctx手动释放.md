## 二、问题根本原因

### FFmpeg 官方文档

**avcodec_close() 的官方说明**：
> **"avcodec_close() will flush and free all resources"**

**含义**：
- `avcodec_close()` 会自动清理 **所有** 资源
- 包括：
  - `hw_frames_ctx`（硬件帧上下文）
  - `hw_device_ctx`（硬件设备上下文）
  - 编解码器内部缓冲区
  - 所有其他内部状态

### 手动释放的问题

**当前代码的问题**（VERSION 137）：

```c
// 【解码器清理】
// STEP 1: 手动释放 hw_frames_ctx
if (ff->dec_ctx->hw_frames_ctx) {
    av_buffer_unref(&ff->dec_ctx->hw_frames_ctx);  // ← 手动 unref
    ff->dec_ctx->hw_frames_ctx = NULL;
}

// STEP 2: 调用 avcodec_close
avcodec_close(ff->dec_ctx);  // ← FFmpeg 内部再次尝试 unref → 解码器侥幸成功


// 【编码器清理】
// STEP 1: 手动释放 hw_frames_ctx
if (ff->enc_ctx->hw_frames_ctx) {
    av_buffer_unref(&ff->enc_ctx->hw_frames_ctx);  // ← 手动 unref
    ff->enc_ctx->hw_frames_ctx = NULL;
}

// STEP 2: 调用 avcodec_close
avcodec_close(ff->enc_ctx);  // ← FFmpeg 内部再次尝试 unref → 编码器崩溃在 free()
```

**问题机制**：

1. **引用计数混乱**：
   - 手动 `av_buffer_unref` 将引用计数 -1
   - `avcodec_close()` 内部再次尝试 unref（不知道已经手动释放）
   - 可能导致引用计数降到负数或访问已释放的内存

2. **Double-free**：
   - 手动 unref 后，内存可能已经被释放
   - `avcodec_close()` 内部再次 unref 时尝试 free 已释放的内存
   - 导致 `__GI___libc_free` 崩溃

3. **为什么解码器侥幸成功但编码器崩溃？**
   - 可能的原因：
     - 编码器有 flush 操作（Line 3333-3348），留下额外的引用
     - 编码器和解码器共享 `g_rkmpp_hwdevice`，引用计数交互复杂
     - 时序问题：解码器先清理，编码器后清理，状态不一致

### 正确的做法

**FFmpeg 官方建议**：

```c
// ❌ 错误：手动管理 hw_frames_ctx
if (enc_ctx->hw_frames_ctx) {
    av_buffer_unref(&enc_ctx->hw_frames_ctx);
    enc_ctx->hw_frames_ctx = NULL;
}
avcodec_close(enc_ctx);

// ✅ 正确：让 avcodec_close() 自动清理
avcodec_close(enc_ctx);  // 自动清理 hw_frames_ctx 和所有其他资源
```

**原因**：
- `avcodec_close()` 内部知道如何正确清理所有资源
- 手动管理可能与内部清理冲突
- 引用计数管理非常复杂，容易出错

## 三、Fix 100.76 解决方案

### 核心思路

**移除所有手动 `av_buffer_unref(&hw_frames_ctx)` 调用**

**原则**：
1. **信任 FFmpeg**：让 `avcodec_close()` 自动清理所有资源
2. **保持一致性**：编码器和解码器采用相同的清理方式
3. **简化代码**：减少手动资源管理的复杂性

## 五、技术要点

### 为什么不手动释放 hw_frames_ctx

1. **FFmpeg 官方建议**：
   - 文档明确：`avcodec_close()` 清理所有资源
   - 包括 `hw_frames_ctx` 和 `hw_device_ctx`

2. **引用计数复杂性**：
   - `hw_frames_ctx` 使用 `AVBufferRef` 引用计数机制
   - 手动 unref 可能与内部清理冲突
   - 导致 double-free 或 use-after-free

3. **一致性**：
   - Fix 100.50 已经移除了 `hw_device_ctx` 的手动释放（同样原因）
   - 现在 `hw_frames_ctx` 也采用相同方式

### 与 Fix 100.50 的关系

**Fix 100.50**（成功修复）：
- **目标**：移除手动释放 `hw_device_ctx`
- **原因**：`avcodec_close()` 会自动处理
- **结果**：挂断不再崩溃（部分成功）

**Fix 100.76**（本次修复）：
- **目标**：移除手动释放 `hw_frames_ctx`
- **原因**：与 Fix 100.50 相同 - `avcodec_close()` 自动处理
- **结果**：预期完全解决编码器崩溃

**共同原则**：
- **信任 FFmpeg**：让库函数自动管理资源
- **简化代码**：减少手动管理复杂性
- **遵循官方**：按照 FFmpeg 文档使用 API

## 八、关键洞察

### 洞察 1：信任库函数的重要性

**教训**：
- FFmpeg 是成熟的库，文档明确说明 API 行为
- 过度手动管理可能破坏内部状态
- 应该遵循官方建议，而不是"聪明"地手动管理

**对比**：
- ❌ Fix 100.50 之前：手动释放 `hw_device_ctx` → 崩溃
- ✅ Fix 100.50：移除手动释放 → 部分成功
- ❌ Fix 100.50-100.75：保留手动释放 `hw_frames_ctx` → 仍然崩溃
- ✅ Fix 100.76：移除手动释放 `hw_frames_ctx` → 预期成功

### 洞察 2：细粒度诊断的价值

**没有 VERSION 137 的 10 个诊断点**：
- 无法确定是解码器还是编码器问题
- 无法确定崩溃在 `avcodec_close()` 内部还是外部
- 可能误判为其他问题（如访问野指针）

**有了 10 个诊断点**：
- 精确定位到编码器 `avcodec_close()` 内部 `free()`
- 排除了所有其他可能性
- 直接指向手动 unref 与内部清理冲突

### 洞察 3：保持代码一致性

**原因**：
- 解码器和编码器本质上是相同的清理流程
- 一个成功、一个失败，说明运气成分（timing, 引用计数状态）
- 应该采用相同的清理方式，而不是"成功的就不改"

**决策**：
- 即使解码器侥幸成功，也移除手动 unref
- 保持编码器和解码器清理逻辑一致
- 降低维护复杂性
