## 二、根本原因分析

### 🔍 关键时序问题

**PJSIP 通话结束清理顺序**（日志 Line 5378-5388）：
```
11:38:40.717  vid_conf.c  ..........Disconnect video ports 3->2 queued  ← cap_slot → enc_slot
11:38:40.717  vid_conf.c  ..........Remove video port 3 queued         ← 移除 cap_slot (摄像头)
11:38:40.717  vid_conf.c  ..........Remove video port 2 queued         ← 移除 enc_slot (编码器)
```

**LocalVideoManager 清理**（Line 5436-5441）：
```
[DEBUG] ✅ Call ended - auto-stopping PJSIP local video preview
[DEBUG] 🔧 [FIX 100.58] Initiating delayed cleanup (cap_slot: 3 → custom_slot: 4)
11:38:40.727  vid_conf.c  .Remove video port 4 queued                  ← 移除 custom_slot
```

**时间差**：`11:38:40.717` → `11:38:40.727` = **只有 10ms！**

### ⚠️ 致命时序冲突

```
时间轴：
t0 (717ms)  PJSIP 通话结束，开始清理
            ↓ 放入队列：Disconnect 3→2
            ↓ 放入队列：Remove port 3 (cap_slot)
            ↓ 放入队列：Remove port 2 (enc_slot)

t1 (727ms)  LocalVideoManager::stopPreview() 被调用  ← 晚了 10ms！
            ↓ 放入队列：Remove port 4 (custom_slot)
            ↓ 启动 1000ms 延迟定时器

t2 (<1000ms) vid_conf 工作线程开始处理队列
            ↓ 处理 "Disconnect 3→2"
            ↓ 处理 "Remove port 3" (cap_slot)
            ↓ 处理 "Remove port 2" (enc_slot)  ← ⚠️ 关键：清理编码器
               ↓ 调用编解码器的 on_destroy()
               ↓ ffmpeg_codec_close()
               ↓ avcodec_close()
               ↓ free() → ❌ SIGSEGV 崩溃！

t3 (未执行) 处理 "Remove port 4" (custom_slot)
t4 (未执行) 1000ms 延迟定时器触发
```

### 🔑 核心问题：Fix 100.58 缺少手动断开连接

**Fix 100.58 的代码**（错误）：
```cpp
// 只调用 remove，不手动 disconnect
pjsua_vid_conf_remove_port(temp_customSlot);
```

**问题分析**：

1. **custom_slot=4 连接到 cap_slot=3**
   - 连接状态仍然存在

2. **PJSIP 清理 enc_slot=2（编码器）**
   - 编解码器的 `on_destroy()` 被调用
   - 访问连接状态或共享资源

3. **custom_slot 的连接未断开**
   - 资源冲突：编解码器尝试释放共享或已释放的资源
   - Double-free → SIGSEGV

### 🆚 为什么 Fix 100.57 去掉了手动 disconnect？

**Fix 100.57 的错误判断**：
```cpp
// ✅ 2026-01-11 23:50 [修复 100.57] 只移除端口，不手动断开连接
// 问题：通话结束时 cap_slot 可能已被 PJSIP 释放，手动 disconnect 会访问已释放内存
// 证据：崩溃类型变化 SIGSEGV → SIGTRAP(abort)，glibc 检测到 heap corruption
// 原因：pjsua_vid_conf_remove_port() 是异步的（queued），但我们立即释放 pool
//       vid_conf 线程访问已释放的 port → heap corruption → abort()
// 解决：
//   1. 不手动 disconnect（vid_conf remove 会自动处理）← ❌ 这是错误的！
```

**错误原因**：
- ❌ 认为 `vid_conf remove` 会自动断开连接
- ✅ 确实会自动断开，**但是异步的**
- ❌ PJSIP 可能在断开之前就清理了 enc_slot
- ❌ 导致编解码器清理时访问未断开的连接 → 崩溃

## 三、解决方案：Fix 100.59

### 核心思路

**恢复手动 disconnect + 缩短延迟时间**：

1. **✅ 立即手动断开连接**：`pjsua_vid_conf_disconnect(cap_slot, custom_slot)`
   - 即使晚了 10ms，也要立即断开
   - 减少编解码器清理时的资源冲突

2. **✅ 立即移除 custom_slot**：`pjsua_vid_conf_remove_port(custom_slot)`
   - 异步操作，放入队列

3. **✅ 缩短延迟到 200ms**：
   - 1000ms 太长，vid_conf 异步操作通常在 100-500ms 内完成
   - 200ms 足够，加快 pool 释放
   - 减少程序等待时间

4. **✅ 保留互斥锁保护**：防止并发调用（虽然目前未发生，但保留保险）

### 为什么手动 disconnect 能解决？

**关键时序改进**：
```cpp
// Fix 100.59：
pjsua_vid_conf_disconnect(cap_slot, custom_slot);  // ← 立即断开连接
pjsua_vid_conf_remove_port(custom_slot);           // ← 然后移除端口
```

**优势**：
1. **disconnect 先执行**：
   - 即使异步，也会在 remove 之前处理
   - 断开 custom_slot 与 cap_slot 的连接

2. **减少资源冲突**：
   - PJSIP 清理 enc_slot 时，custom_slot 的连接已断开（或正在断开）
   - 编解码器 `on_destroy()` 不会访问 custom_slot 的连接状态

3. **早于 PJSIP 清理**（如果快的话）：
   - 虽然晚了 10ms，但 disconnect 操作可能在 PJSIP 清理 enc_slot 之前完成

## 五、技术原理

### 为什么手动 disconnect 重要？

**PJSIP 的连接状态管理**：
```
cap_slot=3 (摄像头) → enc_slot=2 (编码器)
                    ↘ custom_slot=4 (本地预览)
```

**清理时的资源依赖**：
1. **enc_slot 的 on_destroy**：
   - 需要清理编解码器
   - 可能检查连接状态
   - 访问共享资源（内存、硬件设备）

2. **custom_slot 仍连接着 cap_slot**：
   - 连接状态未断开
   - vid_conf 的内部数据结构仍记录着连接
   - 可能被 enc_slot 的清理访问

3. **资源冲突**：
   - enc_slot 清理时访问 cap_slot 的状态
   - custom_slot 的连接导致数据结构不一致
   - Double-free 或访问已释放内存

**手动 disconnect 的作用**：
```cpp
pjsua_vid_conf_disconnect(cap_slot, custom_slot);  // ← 立即断开
```
- 清除 vid_conf 中的连接记录
- enc_slot 清理时不会访问 custom_slot 的连接
- 避免资源冲突

---

### 200ms 延迟的选择

**为什么不是更短（50ms）？**
- vid_conf 异步操作可能需要 100-200ms
- 太短可能导致 pool 释放时 vid_conf 还在清理

**为什么不是更长（1000ms）？**
- vid_conf 操作通常很快（< 500ms）
- 1000ms 延迟太长，影响第二次通话的启动
- 用户可能在 1000ms 内重新发起通话

**200ms 的平衡**：
- ✅ 足够 vid_conf 完成异步操作
- ✅ 不会过度延迟第二次通话
- ✅ 如果崩溃，至少能看到更快的日志反馈
