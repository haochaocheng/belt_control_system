
**为什么 `ff = NULL`？**

- 第二次调用时，`codec->codec_data = NULL` → `ff = NULL`
- 访问 `ff->enc_ctx` → 空指针解引用崩溃

## 三、为什么 Fix 100.72 失败？

### Fix 100.72 的逻辑

```c
if (ff->enc_ctx || ff->dec_ctx) {
    // 调用 ffmpeg_codec_close()
}
```

**问题**：
- 第一次调用 `pjmedia_vid_codec_close()` 已经清理了 `enc_ctx` 和 `dec_ctx`
- 到达 `ffmpeg_dealloc_codec()` 时，条件判断为 **FALSE**
- Fix 100.72 **不执行**
- 设置 `codec->codec_data = NULL`
- 第二次调用 `ffmpeg_codec_close()` → 空指针解引用

**结论**：Fix 100.72 的假设是错误的，它假设 `ffmpeg_codec_close()` 未被调用，但实际上已经被调用了。

## 五、Fix 100.73 解决方案

### 核心修改

**在 `ffmpeg_codec_close()` 中添加 NULL 检查**（Line 3116-3120）：

```c
ff = (ffmpeg_private*)codec->codec_data;
if (!ff) {
    PJ_LOG(1,(THIS_FILE, "✅ [FIX 100.73] codec_data is NULL, codec already closed (double-close prevented)"));
    return PJ_SUCCESS;
}
```

### 为什么这是正确的修复

1. **防止 double-close**：
   - 第一次调用正常执行清理
   - 第二次调用检测到 `codec_data = NULL` → 直接返回成功

2. **不破坏正常流程**：
   - 第一次调用时 `codec_data != NULL` → 正常执行
   - 不影响任何现有逻辑

3. **符合 PJSIP 设计模式**：
   - PJSIP 的其他 codec 实现也有类似的 NULL 检查
   - 这是防御性编程的最佳实践

### 为什么会有第二次调用

**推测**：
- `pj_pool_release(pool)` 可能有自己的清理回调
- Pool 中可能有注册的资源清理函数
- 这些清理函数可能会尝试调用 `ffmpeg_codec_close()`

**关键**：
- 我们无需找到确切的第二次调用位置
- 只需要在 `ffmpeg_codec_close()` 中防御性地检查 NULL

## 八、关键洞察

### 洞察 1：防御性编程的重要性

**教训**：
- 永远不要假设函数只会被调用一次
- 即使设计上应该只调用一次，也要防御多次调用
- NULL 检查是最简单但最有效的防御措施

### 洞察 2：复杂调用链的隐藏行为

**发现**：
- PJSIP 的 Group Lock 机制有多层回调
- Pool 释放可能触发额外的清理回调
- 这些回调可能不在明显的调用路径中

### 洞察 3：Fix 的假设必须验证

**Fix 100.72 的假设**：
- 假设 `ffmpeg_codec_close()` 未被调用
- 实际上它已经被调用了

**Fix 100.73 的假设**：
- 假设 `ffmpeg_codec_close()` 可能被多次调用
- 通过实际崩溃验证了这个假设 ✅

### 洞察 4：调用栈是最可靠的线索

**Core Dump 调用栈**：
```
#3 on_destroy() ← 这说明是回调触发
#2 ffmpeg_codec_close() ← 这是崩溃函数
```

**推理**：
- 如果是正常调用，调用栈应该是 `on_stream_destroy() → ffmpeg_codec_close()`
- 但调用栈显示是 `on_destroy() → ... → ffmpeg_codec_close()`
- 说明有额外的中间层或回调机制
