## 三、核心发现：PJSIP 已经自动断开了连接

### 🔑 关键证据（Line 3107）

```
13:23:21.989 vid_conf.c  .Port 3 (USB camera: USB camera) stop transmitting to port 4 (qt_local_video_sink)
```

**这说明什么？**

1. **PJSIP 在通话结束时会自动断开所有连接**
2. **cap_slot (3) → custom_slot (4) 的连接在 989ms 就被 PJSIP 自动断开了**
3. **LocalVideoManager 的手动 disconnect 在 990ms 才执行（晚了 1ms）**
4. **因此手动 disconnect 返回 PJ_EINVAL（port 3 已不存在）**

### ❌ Fix 100.59 的错误假设

**Fix 100.59 的假设**：
- 认为缺少手动 disconnect 导致崩溃
- 认为需要主动断开 3→4 连接

**实际情况**：
- PJSIP 已经自动断开了 3→4 连接（Line 3107）
- 手动 disconnect 是多余的，而且会失败（PJ_EINVAL）
- **崩溃的真正原因不是连接未断开**

## 五、根本原因结论

### 🎯 真正的根本原因

**不是缺少 disconnect**（PJSIP 已经自动处理）

**而是**：

1. **Port 4 的异步 remove 太慢**
   - `pjsua_vid_conf_remove_port(4)` 放入队列（Line 3153）
   - 但在编码器清理完成前未真正执行
   - 编码器清理时 port 4 仍在 vid_conf 中

2. **Pool 释放时机不对**
   - 200ms 延迟太长，崩溃发生在延迟之前
   - 但立即释放又会导致异步竞态（Fix 100.56 的问题）

3. **编码器与 custom_slot 的资源冲突**
   - 编码器清理时可能遍历 vid_conf 的端口列表
   - 访问到 port 4 的结构
   - port 4 的某些字段或回调指针已失效 → 崩溃

### 🔑 关键洞察

**Fix 100.57 去掉 disconnect 是对的**（虽然当时原因分析不准确）

**Fix 100.58 和 100.59 恢复 disconnect 是错的**：
- 手动 disconnect 总是晚于 PJSIP 自动断开
- 总是返回 PJ_EINVAL
- 没有实际作用，反而增加了误导性日志

## 六、解决方案方向

### 方向 A：更早触发清理（不可行）

**想法**：在 PJSIP 开始清理之前就先清理 LocalVideoManager

**问题**：
- `onCallEnded()` 是最早的信号
- 无法更早获知通话即将结束
- ❌ 不可行

### 方向 B：不手动 remove，让 PJSIP 自动清理 ⭐

**想法**：
- 不调用 `pjsua_vid_conf_remove_port(custom_slot)`
- 不调用 `pjsua_vid_conf_disconnect()`（都是多余的）
- 只负责在合适时机释放 pool

**优势**：
- 避免与 PJSIP 的清理竞争
- 让 vid_conf 自动处理 port 的清理
- 我们只管 pool 的生命周期

**关键问题**：什么时候释放 pool？

#### 方案 B1：在 port_on_destroy 回调中释放（Fix 100.57 思路）

```cpp
static pj_status_t port_on_destroy(pjmedia_port *port)
{
    // 从 port->port_data 中取出 pool 指针
    pj_pool_t *pool = (pj_pool_t *)port->port_data.pdata;
    if (pool) {
        qDebug() << "📹 [FIX 100.62] port_on_destroy: Releasing pool";
        pj_pool_release(pool);
    }
    return PJ_SUCCESS;
}

// 在创建 port 时：
m_customPort->port_data.pdata = m_customPool;
```

**优势**：
- ✅ 等待 vid_conf 真正销毁 port 时才释放 pool
- ✅ 时机完全正确
- ✅ 不需要猜测延迟时间

**Fix 100.57 为什么失败？**
- Fix 100.57 访问了 `this` 指针（`LocalVideoManager *self`）
- this 指针可能在 on_destroy 执行前已析构
- 导致崩溃

**Fix 100.62 改进**：
- **不访问 this 指针**
- 只从 `port->port_data.pdata` 中取出 pool 指针
- pool 指针是稳定的，不依赖对象存活

#### 方案 B2：更长的延迟（500-1000ms）

```cpp
void LocalVideoManager::stopPreview()
{
    // 不手动 disconnect（多余）
    // 不手动 remove（让 PJSIP 自动清理）

    // 只标记为无效
    m_customPort = nullptr;
    m_customSlot = PJSUA_INVALID_ID;

    // 启动更长的延迟（1000ms）

```

**优势**：
- ✅ 简单直接
- ✅ 1000ms 足够 vid_conf 完成所有清理

**劣势**：
- ❌ 延迟太长，影响第二次通话
- ❌ 没有根本解决问题（只是延长了等待时间）

### 方向 C：立即禁用 port 的回调 ⭐

**想法**：
- 不 remove port（让 PJSIP 处理）
- 但立即将 port 的回调设置为 null
- 防止编码器访问回调时崩溃

```cpp

{
    // ✅ 立即禁用回调
    if (m_customPort) {
        m_customPort->put_frame = nullptr;
        m_customPort->get_frame = nullptr;
        m_customPort->on_destroy = nullptr;
        m_customPort->port_data.pdata = nullptr;  // 清空用户数据
        m_customPort = nullptr;
    }

    m_customSlot = PJSUA_INVALID_ID;

    // 不手动 disconnect（多余）
    // 不手动 remove（让 PJSIP 自动清理）

    // 更长的延迟释放 pool（500ms）
    m_delayedCleanupTimer->start(500);
}
```

**优势**：
- ✅ 立即切断 port 的所有对外接口
- ✅ 编码器即使访问到 port，也不会调用回调
- ✅ 结合方案 B2，等待足够时间

**劣势**：
- ⚠️ 修改 pjmedia_port 的内部字段可能不安全
- ⚠️ PJSIP 内部可能仍会访问这些字段

### ✅ 为什么 Fix 100.62 能彻底解决？

1. **完全避免与 PJSIP 的时序竞争**

   - 不手动 remove（让 vid_conf 自动清理）

   - stopPreview() 只做标记，不做实际清理
   - 真正的清理在 on_destroy 回调中
   - 职责分离明确

## 十、总结

### 🔑 核心洞察

1. **PJSIP 会自动断开所有连接**
   - 手动 disconnect 是多余的
   - 总是晚于 PJSIP 自动断开，导致 PJ_EINVAL

2. **手动 remove 与 PJSIP 清理竞争**
   - 无法控制时序
   - 异步操作导致崩溃发生在 remove 完成之前

3. **Pool 释放时机是关键**
   - 太早：异步竞态崩溃（Fix 100.56）
   - 太晚（200ms、500ms、1000ms）：仍然崩溃或延迟过长
   - **正确时机**：在 vid_conf 真正销毁 port 时（on_destroy 回调）

4. **不访问 this 指针是安全的关键**
   - Fix 100.57 崩溃原因：访问已析构的 this
   - Fix 100.62 解决：从 port_data 取 pool，不依赖对象
