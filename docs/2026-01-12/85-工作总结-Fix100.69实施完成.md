## 一、问题回顾

### VERSION 130 测试结果

**症状**：
- ✅ 第一次通话正常
- ❌ 第二次通话画面卡住，编码器 0 包发送
- ✅ 程序没有崩溃

**日志证据**：
```
05:13:03.459  🔍 [CODEC-CLOSE VERSION 130 ENTRY] Function called
05:13:03.459  🔍 [CODEC-CLOSE VERSION 130] codec pointer valid
05:13:03.459  🔍 [CODEC-CLOSE VERSION 130] Closing codec, enc_ctx=0x7ef4015b50
05:13:03.459  🔍 [FIX 100.66 DIAG] dec_ctx=0x7ef4015f10, enc_ctx=0x7ef4015b50
```

**关键发现**：
- ✅ dec_ctx 和 enc_ctx 都存在且有效（不是 NULL）
- ❌ **之后完全没有任何日志**

### 根本原因：死锁

**代码执行流程**：
```c
Line 3073: PJ_LOG(...dec_ctx, enc_ctx...);  // ✅ 打印成功
Line 3075: pj_mutex_lock(ff_mutex);          // ⚠️ 在这里被阻塞！
Line 3101: PJ_LOG(...Checking decoder...);  // ❌ 从未执行
```

**推测**：
`pj_mutex_lock(ff_mutex)` 被阻塞，无法获取锁，导致：
1. 清理代码从未执行
2. 第二次通话编码器无法使用资源
3. 编码器 0 包发送

## 四、如果确认死锁，下一步方案

### Fix 100.70 方案 A：使用 trylock + 超时（推荐）⭐

**核心思路**：
不等待锁，如果获取失败，直接强制清理

```c
pj_status_t status = pj_mutex_trylock(ff_mutex);
if (status != PJ_SUCCESS) {
    PJ_LOG(1, "⚠️ [FIX 100.70] Failed to acquire ff_mutex, forcing cleanup without lock");
    goto force_cleanup;
}

// ... 正常清理（持有锁）...

pj_mutex_unlock(ff_mutex);
return PJ_SUCCESS;

force_cleanup:
    PJ_LOG(1, "⚠️ [FIX 100.70] Force cleanup without mutex protection");

    // 不持有锁的清理
    if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
        PJ_LOG(1, "✅ [FIX 100.70] Skipping decoder flush");
        if (ff->dec_ctx->hw_frames_ctx) {
            av_buffer_unref(&ff->dec_ctx->hw_frames_ctx);
            ff->dec_ctx->hw_frames_ctx = NULL;
        }
        avcodec_close(ff->dec_ctx);
        av_free(ff->dec_ctx);
    }

    if (ff->enc_ctx) {
        avcodec_send_frame(ff->enc_ctx, NULL);
        // ... flush ...
        if (ff->enc_ctx->hw_frames_ctx) {
            av_buffer_unref(&ff->enc_ctx->hw_frames_ctx);
            ff->enc_ctx->hw_frames_ctx = NULL;
        }
        avcodec_close(ff->enc_ctx);
        av_free(ff->enc_ctx);
    }

    ff->enc_ctx = NULL;
    ff->dec_ctx = NULL;

    return PJ_SUCCESS;
```

**优势**：
- 不会被死锁阻塞
- 强制清理，确保资源释放
- 第二次通话可以正常工作

**风险**：
- 不持有锁的清理可能有竞态条件
- 但比死锁好得多

### Fix 100.70 方案 B：完全移除 ff_mutex（激进）⚠️

**核心思路**：
如果 PJSIP 保证不会并发调用 `ffmpeg_codec_close()`，锁是多余的

```c
// 完全移除 pj_mutex_lock(ff_mutex);
// 完全移除 pj_mutex_unlock(ff_mutex);

// 直接执行清理代码
```

**优势**：
- 完全避免死锁
- 简化代码

**风险**：
- 如果 PJSIP 确实会并发调用，可能导致竞态条件
- 需要确认 PJSIP 的线程模型

### Fix 100.70 方案 C：调查死锁源头（保守）

**核心思路**：
找到为什么 ff_mutex 被持有但未释放

**步骤**：
1. 检查之前的版本是否有提前返回路径
2. 检查是否有异常路径未 unlock
3. 检查是否有递归调用

**优势**：
- 从根本解决问题

**劣势**：
- 需要时间调查
- 可能找不到根本原因

## 五、技术细节

### ff_mutex 的作用

**定义**：
```c
pj_mutex_t *ff_mutex = ((struct ffmpeg_factory*)codec->factory)->mutex;
```

**目的**：
保护 `ffmpeg_private` 结构体的并发访问

**问题**：
如果之前的清理因为异常退出（崩溃、提前返回），`pj_mutex_unlock()` 未被调用，锁永远被持有。

### 为什么推荐方案 A（trylock）

**理由**：
1. ✅ 不会被死锁阻塞
2. ✅ 大部分情况下（锁可用）正常工作
3. ✅ 即使锁不可用，也能强制清理
4. ✅ 风险可控（只是不持有锁的清理）

**C 语言限制**：
- 没有 RAII（自动资源管理）
- 无法保证所有异常路径都 unlock
- trylock 是最实用的解决方案

### 洞察 2：死锁的隐蔽性

**特征**：
- 程序不崩溃
- 程序不报错
- 但功能完全失效

**检测方法**：
- 通过日志位置推断
- 在可疑位置前后添加日志
- 如果前有后无 → 确认阻塞位置

### 洞察 3：C 语言的资源管理挑战

**问题**：
- 没有 RAII（自动资源管理）
- 必须手动在每个路径 unlock
- 容易遗漏

**解决**：
- 使用 trylock 代替 lock
- 添加 force_cleanup 路径
- 最小化持有锁的时间
