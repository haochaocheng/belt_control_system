## 一、根本原因（源码分析结论）

经过对 **4805 行编解码器源码**的完整分析，识别出根本原因：

### 核心问题：不对称的清理流程

**对比表**：

| 对比项 | 编码器清理（Fix 100.50） | 解码器清理（修改前） | 状态 |
|--------|------------------------|-------------------|------|
| **Flush 缓冲区** | ✅ 有（avcodec_send_frame(NULL) + 循环）| ❌ **无** | ⚠️ 不对称 |
| **释放 hw_frames_ctx** | ✅ 有（av_buffer_unref + 设置 NULL）| ❌ **无** | ⚠️⚠️⚠️ **关键问题** |
| **手动释放 hw_device_ctx** | ❌ 无（Fix 100.50 正确移除）| ❌ 无 | ✅ 一致 |
| **清理完整性** | ✅ **完整** | ❌ **不完整** | ⚠️⚠️⚠️ **根本原因** |

### 关键问题

**解码器的 hw_frames_ctx 从未被释放**，导致：
1. 解码器的 `hw_frames_ctx` 内部持有对共享 `g_rkmpp_hwdevice` 的引用
2. 编码器的 `avcodec_close()` 先执行，尝试释放 `hw_device_ctx`
3. 但解码器的 `hw_frames_ctx` 仍持有引用 → **引用计数混乱**
4. FFmpeg 内部访问已部分释放的内存 → `free()` → SIGSEGV（Exit code 139）

**原因**：

### 修改 2：解码器完整清理流程（关键）

**修改前**（Line 3141-3144，仅 4 行）:
```cpp
if (ff->dec_ctx && ff->dec_ctx!=ff->enc_ctx) {
    avcodec_close(ff->dec_ctx);  // ← 只有这一行！

```

**修改后**（Line 3097-3141，共 45 行）:
```cpp
if (ff->dec_ctx && ff->dec_ctx != ff->enc_ctx) {
    /* ✅ Step 1: Flush 解码器缓冲区 */
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 1/3] Flushing decoder buffers"));
    avcodec_send_packet(ff->dec_ctx, NULL);  // 发送 flush 信号

    AVFrame frame;
    pj_bzero(&frame, sizeof(frame));
    int flush_count = 0;
    while (avcodec_receive_frame(ff->dec_ctx, &frame) == 0) {
        flush_count++;
        PJ_LOG(4,(THIS_FILE, "  [FIX 100.65] Discarding buffered frame #%d", flush_count));
        av_frame_unref(&frame);
    }
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 1/3] Decoder buffers flushed (%d frames)", flush_count));

    /* ✅ Step 2: 释放 hw_frames_ctx（关键！） */
    if (ff->dec_ctx->hw_frames_ctx) {
        PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 2/3] Releasing decoder hw_frames_ctx"));
        av_buffer_unref(&ff->dec_ctx->hw_frames_ctx);
        ff->dec_ctx->hw_frames_ctx = NULL;
        PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 2/3] hw_frames_ctx set to NULL"));
    } else {
        PJ_LOG(3,(THIS_FILE, "  [FIX 100.65 Step 2/3] hw_frames_ctx is NULL (already released or not set)"));
    }

    /* ❌ Step 3: 不手动释放 hw_device_ctx */
    if (ff->dec_ctx->hw_device_ctx) {
        PJ_LOG(3,(THIS_FILE, "  [FIX 100.65] hw_device_ctx will be released by avcodec_close() (shared, ref-counted)"));
    }

    /* ✅ Step 4: 关闭解码器 */
    PJ_LOG(3,(THIS_FILE, "✅ [FIX 100.65 Step 3/3] Closing decoder (avcodec_close handles hw_device_ctx)"));
    avcodec_close(ff->dec_ctx);
    av_free(ff->dec_ctx);
}
```

**关键步骤**：
1. ✅ **Flush 解码器缓冲区**：确保所有待处理帧被释放
2. ✅ **释放 hw_frames_ctx**：**核心修复**，解除对 hw_device_ctx 的引用
3. ❌ **不手动释放 hw_device_ctx**：让 avcodec_close() 自动处理（引用计数机制）
4. ✅ **调用 avcodec_close()**：触发 FFmpeg 内部清理

## 三、技术原理

### 共享硬件设备的引用计数

**创建**：
```c
static AVBufferRef *g_rkmpp_hwdevice = NULL;  // 全局共享设备

// 编码器引用
ff->enc_ctx->hw_device_ctx = av_buffer_ref(g_rkmpp_hwdevice);  // refcount +1

// 解码器引用
ff->dec_ctx->hw_device_ctx = av_buffer_ref(g_rkmpp_hwdevice);  // refcount +1

// 如果解码器有 hw_frames_ctx（内部持有 device_ref）
ff->dec_ctx->hw_frames_ctx->device_ref = av_buffer_ref(hw_device_ctx);  // refcount +1
```

**修改前的清理流程（问题）**：
```
1. 编码器清理（先）:
   avcodec_close(enc_ctx)  // 内部: av_buffer_unref(&enc_ctx->hw_device_ctx)
   ↓ refcount -1

2. 解码器清理（后）:
   avcodec_close(dec_ctx)  // 内部: av_buffer_unref(&dec_ctx->hw_device_ctx)
   ↓ refcount -1

   但！dec_ctx->hw_frames_ctx 从未释放！
   ↓ hw_frames_ctx->device_ref 仍持有引用
   ↓ FFmpeg 内部尝试释放 hw_frames_ctx
   ↓ 访问已部分释放的 hw_device_ctx → SIGSEGV
```

**修改后的清理流程（正确）**：
```
1. 解码器清理（先，LIFO）:
   avcodec_send_packet(NULL)  // Flush
   av_buffer_unref(&dec_ctx->hw_frames_ctx)  // ← 关键！释放 hw_frames_ctx
   ↓ hw_frames_ctx->device_ref 被释放，refcount -1
   avcodec_close(dec_ctx)  // 内部: av_buffer_unref(&dec_ctx->hw_device_ctx)
   ↓ refcount -1

2. 编码器清理（后）:
   avcodec_send_frame(NULL)  // Flush
   av_buffer_unref(&enc_ctx->hw_frames_ctx)  // 如果有
   avcodec_close(enc_ctx)  // 内部: av_buffer_unref(&enc_ctx->hw_device_ctx)
   ↓ refcount -1

   ✅ 所有引用正确释放，无内存错误
```

## 八、关键技术突破

### 突破 1：识别不对称性

**发现**：编码器有完整清理流程，解码器只有一行 `avcodec_close()`

**证据**：
- 编码器清理：91 行代码（Flush + 释放 hw_frames_ctx + avcodec_close）
- 解码器清理：2 行代码（只有 avcodec_close + av_free）

### 突破 2：理解引用计数机制

**关键理解**：
- `g_rkmpp_hwdevice` 是共享的全局资源
- 编码器和解码器都通过 `av_buffer_ref()` 引用它
- 解码器的 `hw_frames_ctx` 内部也持有引用
- 必须先释放 `hw_frames_ctx`，再让 `avcodec_close()` 释放 `hw_device_ctx`

### 突破 3：LIFO 清理顺序

**发现**：
- 打开顺序：先解码器，后编码器（Fix 81）
- 关闭顺序应该相反：先解码器，后编码器（LIFO）

**原因**：
- 资源管理的最佳实践
- 避免依赖关系混乱
- 确保引用计数正确
