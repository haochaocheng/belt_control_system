### 实现的三种检测机制

代码中实现了三层检测机制,以最大程度确保视频来电能被正确识别:

#### 1. PJSIP C API 层 - 最早检测 (最可靠)
**位置**: `src/risip/core/risipendpoint.cpp` lines 182-259

**方法**: `incoming_call_callback_wrapper`

**特点**:
- ✅ 直接解析 SIP INVITE 消息中的 SDP
- ✅ 检测 `m=video` 行并验证端口 > 0
- ✅ 在 SDP 协商之前就能检测到视频
- ⚠️ 可能被 PJSUA2 拦截导致未触发

**日志标识**: `[INCOMING CALL]`

#### 2. PJSIP 状态回调层 - 中间检测
**位置**: `src/risip/core/risipendpoint.cpp` lines 144-168

**方法**: `call_state_callback_wrapper` 当状态为 INCOMING 时

**特点**:
- ✅ 在呼叫状态变为 INCOMING 时触发
- ✅ 理论上此时 SDP 应已解析
- ⚠️ 实际测试中 `media_cnt` 可能仍为 0

**日志标识**: `[VIDEO DETECTION]`

#### 3. Risip SDK 层 - 最后检测
**位置**: `src/sip_phone/SipPhoneManager.cpp` lines 508-546

**方法**: Risip `incomingCall` 信号处理器

**特点**:
- ✅ 确保一定会触发
- ✅ 调用 `pjsua_call_get_info()` 获取媒体信息
- ⚠️ 此时 `media_cnt` 通常为 0 (SDP 尚未协商)

**日志标识**: `[RISIP INCOMING]`

## 📊 技术原理说明

### 为什么需要三层检测?

PJSIP 的 SDP 协商时机在不同版本和配置下可能不同:

1. **早期 SDP (Early SDP)**:
   - SDP 在 INVITE 请求中发送
   - `incoming_call_callback_wrapper` 可直接解析

2. **延迟 SDP (Delayed SDP)**:
   - SDP 在 180/183 响应中发送
   - 需要在状态回调中检测

3. **晚期 SDP (Late SDP)**:
   - SDP 在接听时才协商
   - 只能在 Risip 信号中检测 (但此时 `media_cnt` 可能仍为 0)

三层检测确保在任何情况下都能检测到视频。

### SDP 示例

**视频通话的 SDP**:
```
v=0
o=- 1234567890 1234567890 IN IP4 192.168.1.100
s=Call
c=IN IP4 192.168.1.100
t=0 0
m=audio 5002 RTP/AVP 0 8          ← 音频媒体
a=rtpmap:0 PCMU/8000
a=rtpmap:8 PCMA/8000
m=video 5004 RTP/AVP 125          ← 视频媒体 (端口 > 0)
a=rtpmap:125 H264/90000
a=fmtp:125 profile-level-id=42e01f
```

**音频通话的 SDP**:
```
v=0
o=- 1234567890 1234567890 IN IP4 192.168.1.100
s=Call
c=IN IP4 192.168.1.100
t=0 0
m=audio 5002 RTP/AVP 0 8          ← 仅音频媒体
a=rtpmap:0 PCMU/8000
a=rtpmap:8 PCMA/8000
```

## 💡 如果三层检测都失败

如果所有三个方法都显示 `media_cnt = 0` 或无法解析 SDP，可能的原因:

1. **SIP 服务器配置问题**
   - 服务器可能不转发 SDP (unlikely)
   - 检查服务器是否支持视频

2. **对方设备问题**
   - 对方可能没有真正发起视频通话
   - 让对方确认选择了视频呼叫

3. **PJSIP 版本问题**
   - 某些 PJSIP 版本的 SDP 处理时机不同
   - 需要查看 PJSIP 2.15.1 的具体行为

4. **延迟 SDP 协商**
   - 某些网络配置下 SDP 协商确实延迟到接听后
   - 这种情况下需要改用另一种方案: 默认显示3按钮，接听后再判断
