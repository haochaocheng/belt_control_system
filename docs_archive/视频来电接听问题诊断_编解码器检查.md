# 视频来电接听问题诊断 - 编解码器检查

## 问题现状

对方打视频电话到本机，本机点击"视频接听"后:
- ❌ 本机看不到对方视频
- ❌ 对方看不到本机视频
- ✅ 但双方音频正常
- ✅ 三按钮UI显示正确

**关键症状**:
```
✅ Answering incoming VIDEO call with PJSIP C API (vid_cnt=1)...
✅ Video call answered successfully (with video, vid_cnt=1)

BUT:
m=video 0 RTP/AVP 125    ← 端口是0,拒绝视频!
Video updated, stream #1:  (inactive)
[MEDIA STATE] Media 1 : type= 2 dir= 0 status= 0
```

即使我们调用了 `pjsua_call_answer2(vid_cnt=1)` 并刷新了账户视频配置,PJSIP 仍然在生成应答 SDP 时拒绝了视频流。

### 新增的诊断信息

#### 1. 视频编解码器列表
```cpp
📹 [VIDEO CODEC CHECK] Found X video codecs:
  Codec 0: H264/90000 Priority: 128
  Codec 1: VP8/90000 Priority: 127
  Codec 2: VP9/90000 Priority: 0  ← Priority 0 = disabled!
```

**关键检查点**:
- ❓ 是否有可用的视频编解码器?
- ❓ H264 和 VP8 的优先级是否 > 0?
- ❓ 如果所有编解码器优先级都是 0,说明视频编解码器未正确初始化

#### 2. 账户视频配置
```cpp
📹 [ACCOUNT CHECK] Found account 0
  vid_cap_dev: 0
  vid_rend_dev: -1
  vid_in_auto_show: 0
  vid_out_auto_transmit: 1  ← 必须是 1!
```

**关键检查点**:
- ❓ vid_cap_dev 是否是正确的摄像头设备? (应该是 0 或 1)
- ❓ vid_out_auto_transmit 是否是 1? (0 会导致视频编码器不启动)
- ❓ 这些配置是否在调用 pjsua_call_answer2() 之前已应用?

#### 3. 来电媒体流数量
```cpp
📹 [VIDEO CODEC CHECK] Checking call media info...
  Call has 0 media streams at INCOMING state
```

**说明**: 在 INCOMING 状态,`media_cnt` 通常是 0,因为媒体流要到接听后才初始化。这是正常的。

## 可能的根本原因

### 原因1: 视频编解码器未启用或优先级为0

**症状**: 所有视频编解码器的 priority 都是 0

**原因**: PJSIP 视频子系统未正确初始化,或者编解码器被禁用

**解决方案**:
```cpp
// 在 initializeEndpoint() 中确保视频编解码器已启用
pj_status_t status;

// 启用 H264 编解码器
pjmedia_vid_codec_info codec_info[32];
unsigned count = PJ_ARRAY_SIZE(codec_info);
status = pjmedia_vid_codec_mgr_enum_codecs(pjmedia_vid_codec_mgr_instance(), &count, codec_info, NULL);

for (unsigned i = 0; i < count; ++i) {
    pj_str_t codec_id = codec_info[i].encoding_name;
    pjsua_codec_set_priority(&codec_id, 128);  // 设置优先级
}
```

### 原因2: 编解码器协商失败

**症状**:
- 本机支持 H264/VP8
- 对方也支持相同编解码器
- 但 PJSIP 仍然拒绝视频

**原因**: SDP 编解码器参数不匹配(如 H264 profile-level-id)

**排查方法**:
1. 查看对方 INVITE 中的 SDP,找到视频编解码器参数
2. 比对本机编解码器配置是否支持相同参数
3. 检查 fmtp 行的参数是否兼容

### 原因3: 账户视频配置时机问题

**症状**: vid_cap_dev 配置正确,但视频仍被拒绝

**原因**: `pjsua_acc_modify()` 的修改可能不会立即影响正在进行的 SDP 协商

**尝试方案**:
在 `answerCall()` 之前,不仅要刷新账户配置,还要确保:
1. 视频设备已初始化并可用
2. 视频编码器已准备好
3. 使用 `pjsua_call_set_vid_strm()` 强制启用视频流

### 原因4: 视频设备未就绪

**症状**: vid_cap_dev=0,但设备实际不可用

**排查**:
```cpp
// 检查视频捕获设备是否真的可用
pjmedia_vid_dev_info dev_info;
pj_status_t status = pjmedia_vid_dev_get_info(vid_cap_dev, &dev_info);
if (status == PJ_SUCCESS) {
    qDebug() << "Video device:" << dev_info.name;
    qDebug() << "  Dir:" << dev_info.dir;  // 应该包含 PJMEDIA_DIR_CAPTURE
} else {
    qWarning() << "Video device not available!";
}
```

## 下一步行动

根据日志输出,采取相应措施:

1. **如果没有视频编解码器或优先级都是0**:
   - 检查 VideoCallManager::initVideoSubsystem() 是否正确初始化了编解码器
   - 添加代码显式启用 H264/VP8 编解码器

2. **如果 vid_out_auto_transmit = 0**:
   - 检查 configureAccountVideoDevice() 中的设置
   - 确保在 initializeEndpoint() 和 configureAccountVideoDevice() 中都设置为 PJ_TRUE

3. **如果配置都正确但仍失败**:
   - 启用更详细的 PJSIP 日志级别
   - 查看 SDP 协商的详细过程
   - 考虑使用 re-INVITE 方案: 先接听音频,然后立即发送 re-INVITE 添加视频

## 对比: 本机主叫视频通话(工作正常)

本机拨打对方时的关键区别:
1. 本机是 SDP offer 方,由我们主动提出视频
2. 对方只需要接受我们的 offer,不需要协商复杂参数
3. 视频编码器在拨号时就已启动

**来电时的挑战**:
1. 对方是 SDP offer 方,我们需要响应他们的 offer
2. 我们必须找到双方都支持的编解码器和参数
3. 视频编码器需要在接听瞬间启动
