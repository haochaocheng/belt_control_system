## 🐛 过滤原因分析

### `port_put_frame` 中的过滤条件

```cpp
pj_status_t RemoteVideoManager::port_put_frame(pjmedia_port *port, pjmedia_frame *frame)
{
    callback_count++;  // 统计所有回调

    if (!self) {
        return PJ_SUCCESS;  // this 指针为空
    }

    if (frame->type != PJMEDIA_FRAME_TYPE_VIDEO) {
        return PJ_SUCCESS;  // ❌ 非视频帧（可能是音频或控制帧）
    }

    if (!frame->buf || frame->size == 0) {
        return PJ_SUCCESS;  // ❌ 空帧或无效帧
    }

    video_frames++;
    self->onFrameReceived(frame, &port->info.fmt);
}
```

### 可能的原因

#### 原因 1: 大量非视频帧 ⭐ 最可能

PJSIP 可能在发送**占位帧**（placeholder frames）或**同步帧**（sync frames），类型不是 `PJMEDIA_FRAME_TYPE_VIDEO`。

**PJSIP 的帧类型**：
```c
#define PJMEDIA_FRAME_TYPE_NONE         0   // 无效帧
#define PJMEDIA_FRAME_TYPE_AUDIO        1   // 音频帧
#define PJMEDIA_FRAME_TYPE_VIDEO        2   // 视频帧
#define PJMEDIA_FRAME_TYPE_EXTENDED     3   // 扩展帧
```

可能大部分回调是 `PJMEDIA_FRAME_TYPE_NONE` 或 `PJMEDIA_FRAME_TYPE_EXTENDED`。

#### 原因 2: Video Conference Bridge 限速

PJSIP 的 video conference bridge 可能有内部的帧率限制器，实际只输出 15 FPS，但为了保持同步，仍然以 60 FPS 调用 `port_put_frame`，大部分是空帧。

从日志可以看到：
```
16:19:00.945 vid_conf.c .........Warning: frame rate of port SDL renderer is higher than video conference bridge (90 > 60)
16:19:03.087 vstdec000001aa Decoding format changed: 640x360 I420<- 60/1(~60)fps
16:19:03.095 vid_conf.c  Port 1 (vstdec...): updated frame rate 90 -> 60
```

Bridge 将帧率从 90 降到 60，但可能进一步降到 15。

#### 原因 3: 解码器输出不规律

H.264 解码器可能不是每次回调都输出帧，而是：
- 收到 I 帧（关键帧）→ 输出帧
- 收到 P 帧（差分帧）→ 输出帧
- 收到其他数据 → 不输出（占位回调）

## 💡 关键发现

### 1. 异步处理不是瓶颈

虽然实现了异步处理，但**瓶颈不在转换耗时**，而在：
- **80% 的帧被 PJSIP 过滤掉了**
- 实际有效视频帧只有 12-15 FPS

### 2. PJSIP bridge 行为

PJSIP video conference bridge 可能：
1. 以 60 FPS 调用 `port_put_frame`（保持同步）
2. 但只在 20% 的回调中提供有效视频帧
3. 其余 80% 是占位帧、同步帧或空帧

### 3. 为什么异步优化没效果？

因为：
```
PJSIP → 60 次回调
  ↓
  只有 12 帧是有效视频
  ↓
应用处理 12 帧
  ↓
显示 12 FPS
```

即使我们优化了处理速度，**输入只有 12 FPS**，输出也只能是 12 FPS。

## 🎯 真正的优化方向

### 方向 1: 检查 FreeSWITCH 配置 ⭐ 最重要

从之前的分析，FreeSWITCH 配置可能限制了帧率为 15 FPS。

**修改 vars.xml**：
```xml
<X-PRE-PROCESS cmd="set" data="video_fps=30"/>
<X-PRE-PROCESS cmd="set" data="video_bitrate=1536"/>
```

**预期效果**：
- FreeSWITCH 发送 30 FPS
- 应用接收 30 FPS（假设有效帧占比不变）

---

### 方向 2: 优化 PJSIP bridge 配置

检查 PJSIP 的 video conference bridge 设置：

```cpp
// 在创建 custom port 时
pjsua_conf_port_info cpi;

qDebug() << "Bridge port info:"
         << "clock_rate:" << cpi.clock_rate
         << "samples_per_frame:" << cpi.samples_per_frame;
```

---

### 方向 3: 接受现实

如果经过所有优化，仍然只有 12-15 FPS，可能是：
1. FreeSWITCH 真的只发送 15 FPS
2. PJSIP bridge 限制了帧率
3. 网络带宽不足

**解决方案**：
- 修改 FreeSWITCH 配置（最有效）
- 或接受 15 FPS（已经足够流畅）

## 🎓 经验总结

### 1. 性能优化的迷思

**错误假设**：PJSIP 发送 60 FPS，但应用处理慢导致只能处理 15 FPS。

**实际情况**：PJSIP 虽然调用 60 次/秒，但**只有 20% 是有效视频帧**，其余是占位帧。

### 2. 测量的重要性

只有通过**详细统计**才发现：
- 不是处理慢
- 而是输入本身就只有 12-15 FPS

### 3. 优化的方向

**优化应用侧**（当前尝试）：
- ❌ 异步处理 → 无效（瓶颈不在这里）
- ❌ 零拷贝 → 无效（瓶颈不在这里）

**优化数据源**（正确方向）：
- ✅ 修改 FreeSWITCH 配置
- ✅ 检查 PJSIP bridge 设置
