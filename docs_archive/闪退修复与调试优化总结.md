### 1. ✅ 修复应用关闭时的闪退问题

**问题描述**:
- 通话结束后，切换到历史页面并关闭应用时发生闪退
- 错误信息：`INVITE session already terminated (PJSIP_ESESSIONTERMINATED)`
- 原因：QML 在通话刚结束时立即访问 PJSIP 通话对象，但 session 已被销毁

**修复方案**:
使用 QTimer 延迟刷新历史记录模型，避免访问已终止的 PJSIP session

**修改文件**: [SipHistoryPage.qml](src/qml/components/sip_phone/pages/SipHistoryPage.qml)

**修改内容**:

```qml
// ✅ 监听账户注册状态，注册成功后刷新历史记录模型
Connections {
    target: SipPhoneManager
    function onIsRegisteredChanged() {
        if (SipPhoneManager.isRegistered) {
            // 使用 Timer 延迟刷新，确保通话资源已完全清理
            refreshTimer.start()
        }
    }
}

// 延迟刷新定时器，避免访问刚结束的通话对象导致崩溃
Timer {
    id: refreshTimer
    interval: 500  // 延迟 500ms
    repeat: false
    onTriggered: {
        try {
            console.log("📝 Refreshing call history model...")
            historyList.model = null

            var newModel = SipPhoneManager.getCallHistoryModel()
            if (newModel) {
                console.log("   ✅ Model retrieved, rowCount:", newModel.rowCount())
                historyList.model = newModel
            } else {
                console.log("   ⚠️ Model is null, no call history available")
            }
        } catch (e) {
            console.error("❌ Error refreshing call history:", e)
        }
    }
}
```

**关键修改**:
1. 不再立即调用 `getCallHistoryModel()`
2. 启动 500ms 延迟定时器
3. 添加 try-catch 错误处理
4. 添加 null 检查

## 技术细节

### 为什么延迟 500ms？

1. **PJSIP 资源清理时间**:
   - PJSIP 在通话结束时需要清理 INVITE session
   - 清理过程包括发送 BYE 消息、等待响应、释放资源
   - 通常需要 100-300ms

2. **Qt 事件循环处理**:
   - 信号发送和槽函数调用也需要时间
   - 500ms 提供了足够的缓冲

3. **用户体验**:
   - 500ms 对用户来说几乎无感知
   - 不影响界面响应性

### 为什么使用 try-catch？

QML 的 try-catch **只能捕获 JavaScript 异常**，无法捕获 C++ 异常。

但我们仍然添加 try-catch 的原因:
1. 防止 QML 内部的 JavaScript 错误
2. 防止 `newModel.rowCount()` 等调用失败
3. 提供更好的错误诊断

真正的 C++ 异常保护需要在 `SipPhoneManager::getCallHistoryModel()` 中添加，这是下一步的优化方向。
