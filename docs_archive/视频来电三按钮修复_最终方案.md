# 视频来电三按钮修复 - 最终方案

## 📋 问题描述

**症状**: 当对方打来视频通话时,本机只显示2个按钮（接听、挂断），而不是3个按钮（视频接听、语音接听、挂断）

**用户反馈**:
1. 第一次测试: "还是两个按钮，没有改变"
2. 第二次测试: "还是不行"

---

## 🔍 问题诊断过程

### 尝试1: 修改时机 - 在 call_state_callback_wrapper 中检测
**文档**: [视频来电三按钮修复_时机问题解决.md](视频来电三按钮修复_时机问题解决.md)

**方法**: 在 `risipendpoint.cpp` 的 `call_state_callback_wrapper` 中检测视频

**结果**: ❌ 失败 - 该回调中 `media_cnt = 0`，SDP尚未解析

### 尝试2: 移除自动接听 - 在 incoming_call_callback_wrapper 中检测
**文档**: [视频来电三按钮修复_真正的根因.md](视频来电三按钮修复_真正的根因.md)

**发现**: `incoming_call_callback_wrapper` 中有自动接听代码（lines 208-229），导致用户看不到来电界面

**修改**:
1. 移除自动接听逻辑
2. 添加视频检测和 SipPhoneManager 通知
3. 移除 call_state_callback_wrapper 中的重复检测

**编译**: ✅ 成功 (2025-12-08 16:06)

**测试结果**: ❌ 失败 - 用户报告"还是不行"

**日志分析**:
- ❌ **没有** `[INCOMING CALL]` 日志出现
- ✅ 但 Risip 的 `incomingCall` 信号**确实触发了**（看到 "Incoming call from:" 日志）

**根本原因**: `incoming_call_callback_wrapper` 根本没有被调用！

### 尝试3: 最终方案 - 在 Risip incomingCall 信号中检测 ✅

**分析**:
1. `incoming_call_callback_wrapper` 在 `risipendpoint.cpp:430` 注册
2. 但 PJSUA2 C++ 包装层在我们的包装器之前拦截了回调
3. PJSUA2 Account 对象可能在 `libStart()` 后重新注册了回调
4. 结果: 我们的包装器永远不会被调用

**解决**: 在 Risip SDK 的 `incomingCall` 信号处理器中检测视频（这个信号**确实**被触发）

---

## ✅ 最终解决方案

### 修改的文件: `src/sip_phone/SipPhoneManager.cpp`

**位置**: Lines 508-546（在 Risip incomingCall 信号的 lambda 处理器中）

**修改前**:
```cpp
qDebug() << "Incoming call from:" << call->buddy()->contact();
d->currentCall = call;

// ✅ Video detection is now handled in risipendpoint.cpp call_state_callback_wrapper()
// when state becomes INCOMING (after SDP has been parsed and media_cnt is populated)

// Emit incoming call signal to QML
```

**修改后**:
```cpp
qDebug() << "Incoming call from:" << call->buddy()->contact();
d->currentCall = call;

// ✅ Detect video in Risip incoming call signal (最终方案)
// incoming_call_callback_wrapper 没有被触发（被PJSUA2拦截），所以在这里检测
int callId = call->callId();
qDebug() << "📞 [RISIP INCOMING] RisipCall callId:" << callId;

if (callId >= 0) {
    pjsua_call_info ci;
    pj_bzero(&ci, sizeof(ci));
    pj_status_t status = pjsua_call_get_info(callId, &ci);
    qDebug() << "📞 [RISIP INCOMING] pjsua_call_get_info status:" << status << "media_cnt:" << ci.media_cnt;

    if (status == PJ_SUCCESS) {
        bool hasVideo = false;
        qDebug() << "📞 [RISIP INCOMING] Checking" << ci.media_cnt << "media streams...";

        for (unsigned i = 0; i < ci.media_cnt; ++i) {
            qDebug() << "📞 [RISIP INCOMING] Media" << i
                     << ": type=" << ci.media[i].type
                     << "dir=" << ci.media[i].dir
                     << "status=" << ci.media[i].status
                     << "(AUDIO=" << PJMEDIA_TYPE_AUDIO << ", VIDEO=" << PJMEDIA_TYPE_VIDEO << ")";

            if (ci.media[i].type == PJMEDIA_TYPE_VIDEO &&
                ci.media[i].dir != PJMEDIA_DIR_NONE) {
                hasVideo = true;
                qDebug() << "✅ Detected video media in Risip incoming call at index" << i;
            }
        }

        qDebug() << "📞 [RISIP INCOMING] Final result: hasVideo =" << hasVideo;
        setIsIncomingVideoCall(hasVideo);
    } else {
        qWarning() << "❌ Failed to get call info in Risip incoming signal, status:" << status;
        setIsIncomingVideoCall(false);
    }
} else {
    qDebug() << "⚠️ Invalid call ID in Risip incoming signal";
    setIsIncomingVideoCall(false);
}

// Emit incoming call signal to QML
```

**关键特性**:
- ✅ 在 Risip 的 `incomingCall` 信号中检测（这个信号**确实**被触发）
- ✅ 使用 PJSIP C API 直接调用 `pjsua_call_get_info()` 获取媒体信息
- ✅ 遍历 `ci.media[]` 数组查找 `PJMEDIA_TYPE_VIDEO`
- ✅ 通过 `setIsIncomingVideoCall()` 更新 UI 标志
- ✅ 详细的调试日志，显示每个媒体流的类型和状态

## 📊 技术架构解释

### PJSIP 回调层次结构

```
┌─────────────────────────────────────────────────────────────┐
│  1. PJSIP C API 层 (最底层)                                  │
│     pjsua_var.ua_cfg.cb.on_incoming_call                    │
│     ❌ 我们尝试在这里拦截，但被 PJSUA2 覆盖                  │
└─────────────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────────────┐
│  2. PJSUA2 C++ 包装层 (中间层)                               │
│     Account::onIncomingCall()                                │
│     ⚠️ PJSUA2 在这里重新注册回调，覆盖我们的包装器            │
└─────────────────────────────────────────────────────────────┘
                         ↓
┌─────────────────────────────────────────────────────────────┐
│  3. Risip SDK 层 (最上层)                                    │
│     RisipCallManager::incomingCall signal                    │
│     ✅ 我们在这里检测视频（最终方案）                        │
└─────────────────────────────────────────────────────────────┘
```

### 为什么 Risip 信号有完整的媒体信息？

虽然 Risip 的 `incomingCall` 信号在 PJSUA2 层触发，但此时:
1. PJSIP 已经完成了 SIP INVITE 请求的解析
2. SDP（Session Description Protocol）已经被解析
3. `pjsua_call_info` 结构体的 `media_cnt` 和 `media[]` 已填充
4. 我们可以直接调用 `pjsua_call_get_info()` 获取完整信息

**关键**: 不依赖回调拦截，而是**被动等待** Risip 信号触发，然后**主动查询** PJSIP 获取媒体信息

## 📝 总结

### 问题根源
1. **自动接听**: 早期代码自动接听所有来电，用户看不到 UI（已修复）
2. **回调被拦截**: PJSUA2 覆盖了我们在 PJSIP C API 层注册的回调
3. **检测位置错误**: 在 C API 回调中检测视频，但回调从未被调用

### 最终解决方案
- ✅ 在 Risip SDK 的 `incomingCall` 信号中检测视频
- ✅ 使用 `pjsua_call_get_info()` 主动查询媒体信息
- ✅ 不依赖回调拦截，而是利用已有的信号机制

### 核心改变
- **位置**: `src/sip_phone/SipPhoneManager.cpp` lines 508-546
- **方法**: 在 Risip `incomingCall` 信号的 lambda 中添加视频检测
- **效果**: 正确识别视频来电，显示 3 按钮 UI

## 💡 经验教训

1. **不要过度依赖回调拦截**
   - PJSUA2 这样的包装库可能会覆盖底层回调
   - 使用已有的信号机制比尝试拦截底层回调更可靠

2. **充分利用调试日志**
   - 详细的日志帮助我们发现 `incoming_call_callback_wrapper` 未被调用
   - 对比预期日志和实际日志是诊断问题的关键

3. **不要假设架构**
   - 最初假设 C API 回调会被调用，但实际被 PJSUA2 拦截
   - 需要通过日志验证每一层的行为

4. **使用已验证的机制**
   - Risip 的 `incomingCall` 信号是已验证可用的
   - 在可用机制的基础上构建解决方案更可靠

5. **主动查询 vs 被动等待**
   - 不要等待回调提供信息（可能被拦截）
   - 主动调用 API 查询信息更可靠
