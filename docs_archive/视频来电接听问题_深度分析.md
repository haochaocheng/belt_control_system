# 视频来电接听问题 - 深度分析

## 问题现象

对方打视频电话到本机,点击"视频接听"后:
- ❌ 本机看不到对方视频
- ❌ 对方看不到本机视频
- ✅ 双方音频正常
- ✅ 三按钮UI显示正确

## 已经排除的可能原因

通过多次测试和诊断,我们已经排除了以下可能原因:

### ✅ 已确认正常的部分

1. **视频编解码器已启用且优先级正确**
   ```
   📹 [VIDEO CODEC CHECK] Found 2 video codecs:
     Codec 0 : "H264/100" Priority: 200  ← 已提升到最高
     Codec 1 : "H263-1998/96" Priority: 128
   ```

2. **账户视频配置正确**
   ```
   📹 [ACCOUNT CHECK] Found account 0
     vid_cap_dev: 0                    ← 正确的摄像头
     vid_rend_dev: -2                  ← 自动选择渲染器
     vid_in_auto_show: 0
     vid_out_auto_transmit: 1          ← 自动传输已启用
   ```

3. **视频设备可用**
   - 本机摄像头工作正常
   - 本机主叫对方视频通话完全正常
   - 本机视频预览正常工作

4. **对方SDP提供了H264视频**
   ```
   m=video 19372 RTP/AVP 125
   a=rtpmap:125 H264/90000
   a=fmtp:125 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42001f
   ```

5. **调用流程正确**
   - ✅ 刷新账户配置: `configureAccountVideoDevice()`
   - ✅ 使用PJSIP C API: `pjsua_call_answer2(vid_cnt=1)`
   - ✅ 设置INCLUDE_DISABLED_MEDIA标志

### ❌ 问题根源

即使所有配置都正确,PJSIP仍然在SDP协商时拒绝视频:

```
09:07:26.643 pjsua_call.c  Answering call 0: code=200
09:07:26.647 inv...  ..SDP negotiation done: Success  ← 协商"成功"
09:07:26.697 pjsua_media.c  ....Video updated, stream #1:  (inactive)  ← 但视频被标记为inactive

发送给对方的SDP:
m=video 0 RTP/AVP 125  ← 端口0 = 拒绝视频!
c=IN IP4 127.0.0.1

[MEDIA STATE] Media 1 : type= 2 dir= 0 status= 0
                              ^^^
                              dir=0 表示 PJMEDIA_DIR_NONE (inactive)
```

## 真正的根本原因

**PJSIP的SDP协商器认为无法满足对方的视频要求,所以拒绝了视频流。**

可能的具体原因:

### 1. H264 fmtp参数不匹配

对方要求:
```
a=fmtp:125 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42001f
```

我们的H264实现可能:
- 不支持 `packetization-mode=1`
- 不支持 `profile-level-id=42001f` (Baseline Profile Level 3.1)
- 不支持 `level-asymmetry-allowed=1`

### 2. PJSIP的H264实现限制

PJSIP 2.15.1在Windows上使用的H264实现可能是:
- **OpenH264** - Intel的开源H264实现
- **FFmpeg** - 如果编译时启用了FFmpeg支持
- **自带的软件编解码器** - 功能受限

这些实现可能不支持对方要求的特定H264参数组合。

### 3. SDP协商时序问题

PJSIP在以下时刻做SDP协商决策:
1. 收到INVITE - 解析远程SDP
2. **准备200 OK应答** ← 这里决定接受还是拒绝视频
3. 发送200 OK
4. 收到ACK - 协商完成

在步骤2,PJSIP检查:
- 是否有可用的视频捕获设备? ✅ 有(device 0)
- 是否有匹配的视频编解码器? ✅ 有(H264 priority 200)
- **编解码器参数是否兼容?** ❌ 这里可能失败了!

## 对比:本机主叫视频通话(正常工作)

为什么本机打给对方时视频正常?

```
本机主叫流程:
1. 本机发送 INVITE with SDP offer
   - 我们提出H264参数 (可能是更通用的参数)
2. 对方发送 200 OK with SDP answer
   - 对方接受我们的参数 (对方通常支持更广泛的参数)
3. 本机发送 ACK
4. ✅ 视频通话建立

对方主叫流程:
1. 对方发送 INVITE with SDP offer
   - 对方提出特定的H264参数 (42001f, packetization-mode=1)
2. 本机发送 200 OK with SDP answer
   - ❌ 我们无法满足对方的参数要求
   - PJSIP拒绝视频: m=video 0
3. 对方发送 ACK
4. ❌ 只有音频通话
```

关键区别: **作为SDP answerer时,我们必须匹配对方的要求;作为offerer时,我们可以提出自己支持的参数。**

## 可能的解决方案

### 方案1: 修改PJSIP H264参数配置 (已尝试,未成功)

我们已经尝试:
- ✅ 提升H264优先级到200
- ✅ 设置`codec_param.dir = PJMEDIA_DIR_ENCODING_DECODING`
- ❌ 但没有办法直接设置fmtp参数(packetization-mode, profile-level-id)

**问题**: PJSIP的`pjsua_vid_codec_set_param()`不允许修改fmtp参数,这些是由底层H264实现(OpenH264/FFmpeg)决定的。

### 方案2: 重新编译PJSIP并启用更好的H264支持 (推荐但复杂)

如果PJSIP使用的是OpenH264,可能需要:
1. 重新编译PJSIP,启用FFmpeg H264支持
2. 或者更新OpenH264到支持更多参数的版本
3. 或者配置OpenH264支持Baseline Profile

这需要重新编译整个Risip SDK和PJSIP。

### 方案3: 使用re-INVITE添加视频 (可行但用户体验差)

```cpp
void SipPhoneManager::answerCall()
{
    if (d->isIncomingVideoCall) {
        // 步骤1: 先用vid_cnt=0接听(仅音频)
        qDebug() << "Step 1: Answering with audio only...";
        call_opt.vid_cnt = 0;
        pjsua_call_answer2(call_id, &call_opt, 200, NULL, NULL);

        // 步骤2: 等待通话建立
        QTimer::singleShot(500, [=]() {
            // 步骤3: 发送re-INVITE添加视频
            qDebug() << "Step 2: Sending re-INVITE to add video...";
            pjsua_call_vid_strm_op_param vidParam;
            pjsua_call_vid_strm_op_param_default(&vidParam);
            vidParam.med_idx = -1;
            vidParam.dir = PJMEDIA_DIR_ENCODING_DECODING;

            pjsua_call_set_vid_strm(call_id, PJSUA_CALL_VID_STRM_ADD, &vidParam);
        });
    }
}
```

**优点**:
- 绕过初始SDP协商的参数匹配问题
- 作为re-INVITE的发起方,我们可以提出自己的参数

**缺点**:
- 用户会先听到音频,几百毫秒后才看到视频
- 需要服务器和对方都支持re-INVITE
- 增加了信令复杂度

### 方案4: 降级到仅H263 (不推荐)

如果H263-1998的参数协商更简单,可以:
1. 禁用H264编解码器
2. 只使用H263-1998

**缺点**: H263视频质量远不如H264,且不是现代标准。

### 方案5: 检查PJSIP日志级别,获取更详细的协商失败原因 (诊断)

在`initializeEndpoint()`中添加:
```cpp
pjsua_logging_config log_cfg;
pjsua_logging_config_default(&log_cfg);
log_cfg.level = 5;  // 最详细的日志级别
log_cfg.console_level = 5;
pjsua_reconfigure_logging(&log_cfg);
```

这会输出SDP协商的详细过程,可能会显示具体哪个参数不匹配。

## 已实施的workaround (可能无效)

最新代码添加了"180 Ringing"workaround:
```cpp
// 先发送180 Ringing with video
pjsua_call_answer2(call_id, &call_opt, 180, NULL, NULL);
QThread::msleep(100);
// 再发送200 OK
pjsua_call_answer2(call_id, &call_opt, 200, NULL, NULL);
```

**预期效果**: 给PJSIP更多时间准备视频

**实际效果**: 可能无效,因为SDP协商发生在发送200 OK时,180只是临时响应

## 技术参考

### PJSIP SDP协商流程

```
pjsua_call_answer2()
  ↓
pjsip_inv_answer() - 准备200 OK响应
  ↓
pjmedia_sdp_neg_modify_local_offer() - 生成本地SDP answer
  ↓
对于每个media stream:
  1. 检查media type (audio/video)
  2. 查找匹配的编解码器
  3. ✅ 检查编解码器参数兼容性 ← 这里可能失败!
  4. 如果不兼容: 设置 m=... 0 (端口0 = 拒绝)
  ↓
发送200 OK with SDP answer
```

### H264 Profile-Level-ID详解

`profile-level-id=42001f`分解:
- `42` = 0x42 = Baseline Profile (66)
- `00` = Constraint flags (无额外限制)
- `1f` = 0x1F = Level 3.1 (支持720p@30fps)

常见profiles:
- `42` (66) = Baseline - 基础,移动设备常用
- `4d` (77) = Main - 主流,支持B帧
- `64` (100) = High - 高级,蓝光质量

### Packetization Mode

- Mode 0: Single NAL unit per RTP packet (简单)
- Mode 1: Fragmentation Units (FU-A), 支持大帧分片 (常用)
- Mode 2: Interleaved mode (罕见)

Mode 1是现代H264系统的标准。
