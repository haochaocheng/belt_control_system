# 远端视频画面定格问题诊断

**日期**: 2025-12-10
**问题**: 视频通话建立后，前3秒有画面，之后画面定格不动
**通话时长**: 27秒
**状态**: 🔍 已定位根因

---

## 📊 测试数据分析

### 完整通话统计（27秒）

```
🎯 [PJSIP CALLBACK FPS] "59.9"
   | Total callbacks: 1637
   | Video frames: 40      ← 只有40帧！
   | Non-video: 0
   | Empty: 1596            ← 97.5% 是空帧
   | Elapsed: 27307 ms
```

**关键发现**：
- ✅ PJSIP 以 60 FPS 持续回调（正常）
- ❌ **27秒只收到40个有效视频帧**（异常！）
- ❌ 实际 FPS = 40 / 27 = **1.5 FPS**
- ❌ 97.5% 的回调是空帧

## 🐛 根本原因

### 不是客户端应用的问题

✅ **客户端应用工作正常**：
- 异步处理线程正常运行
- PJSIP 回调正常
- 客户端能正确识别和处理视频帧
- 只要对方发送有效视频帧，客户端就能显示

❌ **问题在数据源**：
- 对方（FreeSWITCH 或 1006）在第3秒后**停止发送视频数据**
- 或者发送的数据全部损坏，无法解码

---

## 🔍 可能的原因

### 原因 1: 对方视频编码器故障 ⭐ 最可能

**现象**：
- 通话建立时，对方正常发送视频（前3秒）
- 突然停止发送有效视频数据（第3秒后）
- PJSIP 继续发送空帧（占位符）

**可能的具体原因**：
1. **对方 FreeSWITCH 的 H.264 编码器崩溃**
   - 编码进程异常退出
   - 但 SIP 会话仍然保持连接

2. **对方摄像头/视频源断开**
   - 摄像头掉线或被占用
   - FreeSWITCH 检测到没有视频输入
   - 停止发送视频数据，只发送空帧维持会话

3. **对方 CPU 过载**
   - 编码器无法跟上，停止编码
   - 或者进入保护模式

**验证方法**：
- 在对方（1006）的 FreeSWITCH 上查看日志
- 检查是否有视频编码器错误或警告

---

### 原因 2: re-INVITE 导致视频流中断

**日志证据**：

在通话建立后立即发送了 re-INVITE：
```
17:51:51.564 Call 0 sending re-INVITE for updating media session to use only one codec
```

re-INVITE 的目的：
```
Call 0: updating media..
Media stream call00:1 is destroyed         ← 旧的视频流销毁
Creating new video stream...                ← 创建新的视频流
Video updated, stream #1: H264 (sendrecv)
```

**时间对比**：
```
17:51:51.xxx  re-INVITE 开始
17:51:52.xxx  新视频流建立，开始接收视频（前40帧）
17:51:56.xxx  re-INVITE 完成（200 OK）
17:51:57.xxx  视频帧停止更新
```

**可能的问题**：
1. **re-INVITE 过程中视频流切换失败**
   - 旧流销毁了
   - 新流没有正确建立
   - 对方以为视频已恢复，但实际没有

2. **SDP 协商问题**
   - re-INVITE 后的 SDP 参数与对方不兼容
   - 对方编码器无法使用新参数

**证据**：
```
17:51:56.xxx  Media stream call00:1 is destroyed
17:51:56.xxx  Video channel update..
17:51:56.xxx  Encoder stream started
17:51:56.xxx  Decoder stream started
17:51:57.295  Decoding format changed: 640x360 I420<- 60/1(~60)fps
```
在解码格式变化后（re-INVITE 完成后），就再也没有有效帧了。

---

### 原因 3: H.264 解码错误导致后续帧无法解码

**日志中大量解码错误**：
```
17:51:51.382 vstdec  codec decode() error: Bad or corrupted bitstream
17:51:51.444 vstdec  codec decode() error: Bad or corrupted bitstream
17:51:51.537 vstdec  codec decode() error: Bad or corrupted bitstream
...（多次重复）
17:51:57.012 vstdec  codec decode() error: Bad or corrupted bitstream
```

**H.264 编解码特性**：
1. **I帧（关键帧）**：完整的图像，可独立解码
2. **P帧（预测帧）**：依赖前一帧，只包含差异

**可能的情况**：
- 前3秒收到了几个 I 帧和 P 帧（40帧）
- 之后的 I 帧丢失或损坏
- 解码器无法解码后续的 P 帧（因为没有参考帧）
- PJSIP 回调仍然发生，但 `frame->buf == NULL`（空帧）

**验证**：
- 查看网络抖动和丢包率
- 检查 RTCP 报告中的丢包统计

---

### 原因 4: PJSIP 内部 video conference bridge 问题

**日志提示**：
```
17:51:56.xxx  Remove video port 1 queued
17:51:56.xxx  Port 1 (vstdec) stop transmitting to port 5 (qt_remote_video_sink)
17:51:56.xxx  Removed video port 1 (vstdec), port count=3
```

在 re-INVITE 过程中：
- 旧的解码器端口（port 1）被移除
- 新的解码器端口（port 6）被添加

**可能的问题**：
- 新的解码器端口没有正确连接到自定义端口（qt_remote_video_sink）
- 导致后续视频帧没有路由到我们的应用

**验证**：
检查 re-INVITE 后，自定义端口是否仍然连接到新的解码器端口。

### 步骤 3: 分析 re-INVITE 的影响

**验证是否是 re-INVITE 导致的**：

修改客户端，**禁用 re-INVITE**：

在 PJSIP 账户配置中添加：
```cpp
// 在 src/risip/core/risipendpoint.cpp 或账户配置中
acc_cfg.call_hold_type = PJSUA_CALL_HOLD_TYPE_RFC3264;  // 默认
acc_cfg.allow_via_rewrite = PJ_FALSE;  // 禁止修改 Via
```

或者在 `pjsua_acc_config` 中：
```cpp
// 禁止自动 re-INVITE
acc_cfg.reg_retry_interval = 0;  // 不重试注册
```

**更简单的方法**：修改 PJSIP 源码，注释掉自动 re-INVITE：

在 `src/sip_phone/SipPhoneManager.cpp` 的 `onCallStateCallback` 中，找到：
```cpp
// 注释掉这一行，避免自动 re-INVITE
// pjsua_call_reinvite(call_id, PJSUA_CALL_REINVITE_UPDATE_VIA | PJSUA_CALL_REINVITE_UPDATE_CONTACT, NULL);
```

**测试**：如果禁用 re-INVITE 后视频不再定格，说明问题就是 re-INVITE 导致的。

---

### 步骤 4: 在 re-INVITE 后重新连接视频端口

**问题**：re-INVITE 后，解码器端口从 1 变成了 6，但我们的自定义端口可能没有重新连接。

**修复方法**：在 re-INVITE 完成后，重新检测并连接到新的解码器端口。

在 `RemoteVideoManager.cpp` 的 `onCallConnected()` 中：

```cpp
void RemoteVideoManager::onCallConnected(int callId)
{
    QMutexLocker locker(&m_mutex);
    m_currentCallId = callId;

    qDebug() << "📹 RemoteVideoManager: Call connected, callId =" << callId;

    // ✅ 每次 call connected 都重新连接
    disconnectFromVideoBridge();  // 先断开旧连接

    if (detectAndConnectToVideoBridge()) {
        qDebug() << "✅ RemoteVideoManager: Connected to video bridge (Push mode)";
        emit requestStartCheck();
    } else {
        qDebug() << "⚠️ RemoteVideoManager: Failed to connect to video bridge";
    }
}
```

**但问题**：日志显示我们的自定义端口（slot 5）一直存在，直到挂断才移除。所以可能不是端口连接的问题。

---

### 步骤 5: 检查 PJSIP 解码器是否真的在输出帧

**添加更详细的日志**：

在 `RemoteVideoManager::port_put_frame()` 中：

```cpp
pj_status_t RemoteVideoManager::port_put_frame(pjmedia_port *port, pjmedia_frame *frame)
{
    callback_count++;

    // 详细记录每一帧的信息
    static int detailed_log_count = 0;
    if (detailed_log_count < 100) {  // 只记录前100帧，避免日志爆炸
        qDebug() << "[FRAME DETAIL]"
                 << "type:" << frame->type
                 << "size:" << frame->size
                 << "buf:" << (void*)frame->buf
                 << "timestamp:" << frame->timestamp.u64;
        detailed_log_count++;
    }

    if (frame->type != PJMEDIA_FRAME_TYPE_VIDEO) {
        non_video_frames++;
        return PJ_SUCCESS;
    }

    if (!frame->buf || frame->size == 0) {
        empty_frames++;
        return PJ_SUCCESS;
    }

    video_frames++;
    self->onFrameReceived(frame, &port->info.fmt);
    return PJ_SUCCESS;
}
```

这样可以看到每一帧的详细信息，判断是 `frame->type` 不对还是 `frame->buf == NULL`。
